500 Internal Server Error in WordPress: How to Find the Cause and Fix It

How to fix a 500 Internal Server Error in WordPress: read the error log, enable WP_DEBUG_LOG safely, then check .htaccess, plugins, memory, PHP and limits.

Key takeaways
  • A 500 error is deliberately vague, so read the server error log first: the time, severity, message and file path usually name the cause.
  • Turn on WP_DEBUG_LOG with WP_DEBUG_DISPLAY off, ideally writing to a path outside the public folder, then switch it off and delete the log once you have the error.
  • Common causes are a bad .htaccess line, a plugin or theme fatal error, PHP memory, a PHP version mismatch and hosting limits; work through them in order with a backup in hand.

A 500 Internal Server Error is the server's way of saying "something went wrong" without saying what. Guessing at fixes wastes time, because the real reason is almost always written in an error log within seconds of the failure. Here's how to find and read that log, switch on WordPress's debug log safely, and recognise each common cause.

A 500 error or a critical error?

How the error appears is itself a clue:

  • "There has been a critical error on this website": WordPress caught a PHP fatal error itself. Start with the critical error guide
  • A plain "Internal Server Error" page from the server: the request failed before WordPress could respond, which points to .htaccess, server settings or a very early PHP failure
  • The browser's own "HTTP ERROR 500" page: the server sent an empty page with a 500 status, usually a PHP failure with error display switched off

Note the scope too. A 500 on every page suggests .htaccess, a damaged core file or server limits; one only in wp-admin, or after clicking a particular button, points to the plugin that runs there. For 502 or 504 errors, see fixing 502 and 504 gateway errors instead.

Find and read the server error log

Before changing anything, check the "Errors" or "Logs" section of your hosting panel, or an error_log file in the main site folder or wp-admin, which many shared hosts create automatically. Reload the broken page once, then read the newest entries, which look like this:

[11-Oct-2026 10:42:17 UTC] PHP Fatal error:  Uncaught Error: Call to undefined function old_helper() in /home/account/public_html/wp-content/plugins/example-plugin/includes/loader.php:88

Read it in four parts:

  1. Time: match it to when you loaded the page; logs often use UTC or the server's time zone rather than IST
  2. Severity: "Fatal error" and "Parse error" stop the page; warnings, notices and "Deprecated" lines are usually noise
  3. Message: what went wrong; see the table below
  4. File path: the folder after wp-content/plugins/ or wp-content/themes/ names the culprit, and the number at the end is the line a developer should check
Log message containsLikely cause
"Invalid command", "not allowed here" or a mention of .htaccessA bad line in .htaccess
"Allowed memory size ... exhausted"PHP memory limit
"Call to undefined function", or "Uncaught Error" in a plugin pathA plugin or theme that doesn't suit your PHP version or another plugin
"syntax error, unexpected ..."A broken code edit, or code that needs a newer PHP version
"Maximum execution time ... exceeded"A task running longer than the server allows
"End of script output before headers" or "Premature end of script headers"PHP crashed or was stopped, often by a server limit

Turn on WP_DEBUG_LOG safely

If the server log is empty or hard to reach, WordPress can write PHP errors to its own file. A typo in wp-config.php itself causes a 500, so:

  1. Download a copy of wp-config.php first
  2. Edit it in the file manager or a plain text editor, never a word processor, which turns straight quotes curly
  3. Replace the existing WP_DEBUG line rather than adding a second one, keeping it above the comment that says to stop editing
define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', '/home/account/logs/wp-errors.log' );
define( 'WP_DEBUG_DISPLAY', false );

Giving WP_DEBUG_LOG a file path, supported since WordPress 5.1, keeps the log outside your public folder; ask your host for a suitable path in a folder that already exists. If you set it to true instead, it writes to wp-content/debug.log, which anyone can often open in a browser, so delete it as soon as you've read it. WP_DEBUG_DISPLAY set to false keeps errors off visitors' screens.

Reproduce the error once, read the newest "Fatal error" line, then set WP_DEBUG back to false, remove the extra lines and delete the log. If the log stays empty, the failure happens before WordPress loads, usually in .htaccess or the server, and only the server log will show it.

Corrupt or invalid .htaccess

On Apache and LiteSpeed servers, one bad line in .htaccess takes down every page, including wp-admin. Typical culprits are typing mistakes, leftovers from removed plugins and php_value lines copied from tutorials, which cause an instant 500 on many servers that don't run PHP as an Apache module. PHP settings belong in your host's PHP options screen instead.

To test, rename .htaccess to .htaccess-old. If the site comes back, re-save Settings → Permalinks to create a clean file, then add back custom rules one at a time, testing after each. Rules that refuse access cause a different error; see fixing a 403 Forbidden error.

Plugin and theme fatal errors

When the log names a file inside wp-content/plugins or wp-content/themes, that code is the problem, often straight after an update:

  • Rename just that plugin's folder by file manager or SFTP, which deactivates it, and reload
  • If the theme is named, rename its folder so WordPress falls back to a default theme, provided one is installed
  • Then roll back, wait for a fixed release or replace the plugin

If the log doesn't point anywhere useful, the plugin conflict guide explains how to test plugins one by one on a staging copy. Errors in functions.php or a snippets plugin usually come from a recent manual edit, so undo it.

Memory, PHP version and server limits

PHP memory

"Allowed memory size exhausted" means a page needed more memory than PHP allows. Raising the limit helps, but finding what's using the memory matters more; see fixing memory limit errors.

PHP version mismatch

When a host retires an old PHP version, outdated plugins and themes that rely on removed functions can break. The reverse happens too, when a plugin update needs a newer PHP version than your server runs. Switching PHP back in the hosting panel is a quick temporary fix while the code is updated; see updating your PHP version safely.

Server limits

Shared hosting caps CPU, memory, simultaneous processes and script run time. Large imports, backups or a traffic spike can hit those caps, so the 500 comes and goes. Your panel's resource usage page shows whether limits were reached; if so, move heavy jobs to quiet hours or ask whether a larger plan is needed.

A safe fix order, and when to call your host

  1. Note the time, the URL and recent changes, and back up the site even though it's broken
  2. Read the server error log
  3. Test .htaccess by renaming it
  4. Deal with the plugin or theme named in the log, then check memory, PHP version and limits
  5. If the site must be online now, restore a working backup and investigate on staging; on a store, restoring the database can wipe out recent orders

Ask your host when you can't find the logs, when they mention script headers, resource limits or "Permission denied", when the error started after the host changed something, or when it only appears at busy times. Give them the exact time and URL.
