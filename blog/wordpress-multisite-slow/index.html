WordPress Multisite Slow? Why Networks Slow Down and How to Fix It

Why a WordPress Multisite network gets slow, from the shared database and network plugins to cron and domain mapping, and how Redis, caching and hosting help.

Key takeaways
  • Multisite networks slow down because every site shares one database, one set of network-activated plugins, per-site cron and one server.
  • A Redis object cache and page caching that properly supports Multisite usually make the biggest difference, followed by database clean-up on every site.
  • If one site dominates or sites need very different plugins and hosting, splitting the network can be the most effective speed fix.

A WordPress Multisite network often starts fast and gets slower as sites, users and plugins are added. Pages take longer to load, the network admin drags and scheduled tasks run late. The causes differ from a single slow site, because everything in a network shares one database, one set of plugins and one server. Here's why WordPress Multisite gets slow and what to do about it. For causes that apply to any site, see why your WordPress site is slow.

Why WordPress Multisite gets slow

Most slow networks have a combination of these:

  • The shared database. Every site's content lives in one database. Users are shared too: one users table and one user meta table for the whole network, with extra rows recording each user's role on each site. On networks with many sites and users these tables grow large, and queries that touch them slow down.
  • Large options tables. Each site has its own options table, and plugins add autoloaded settings to every one of them. A plugin that stores heavy autoloaded data does it once per site.
  • Network-activated plugins. A plugin activated across the network loads on every page of every site, including sites that never use it.
  • Cron across sites. WP-Cron runs separately for each site and only when that site gets a visit, so busy sites run scheduled tasks during page loads while quiet sites fall behind.
  • Domain mapping. WordPress first has to work out which site a request belongs to from its domain and path. That is normally quick, but misconfigured mapping can add redirect chains between old and new addresses, and older networks may still rely on a legacy domain-mapping plugin.

Database tables per site

Each new site gets its own set of tables named with the site's ID (wp_2_posts, wp_2_options and so on), plus any tables its plugins create. A network of a few dozen sites can easily have hundreds of tables, and very large networks thousands.

  • Autoloaded options on each site, not just the main one. Site Health can warn about large autoloaded data.
  • Leftover tables from deleted sites or removed plugins; review these carefully before deleting anything
  • Revisions, transients and logs across every site, not only the busiest
  • Slow queries, found with a tool like Query Monitor on a staging copy

The clean-up steps in WordPress database optimisation apply to each site in the network; back up the whole database first. Very large networks sometimes spread tables across several databases with a database drop-in such as HyperDB or LudicrousDB, but that is specialist work.

Object caching (Redis) on multisite

A persistent object cache keeps the results of database queries in memory between page loads. On a network it often makes the biggest difference, because so much is shared: site lookups, network options, users and each site's settings would otherwise be fetched from the database on every request.

  • Your host needs to provide Redis (or Memcached), plus a connector plugin that supports Multisite; check the plugin's documentation for network setup
  • Cached data must be kept separate for each site, which good connector plugins handle using the site ID
  • If other WordPress installs share the same Redis server, give each install its own cache key prefix so they don't overwrite each other's data
  • It helps the admin and logged-in users most, since they bypass page caching

See WordPress caching explained for how object caching fits with the other layers.

Page caching on multisite

Page caching serves ready-made copies of pages instead of running WordPress for every visitor, which takes a lot of load off the shared database. Points to check on a network:

  • Multisite support: not every caching plugin supports networks; some must be network-activated, and settings may be network-wide or per site
  • Server-level caching (LiteSpeed, Nginx or Varnish, depending on the host) usually works across the network, but purge rules must clear the right site's pages when content changes
  • Mapped domains need including in your cache, CDN and SSL setup, or they may miss out on caching
  • Logged-in users skip the page cache, and on a subdirectory network someone logged in to one site is usually logged in across the domain, so editors see uncached pages everywhere
  • Cache preloading across many sites can itself strain a small server; schedule it for quiet hours

Cron across sites

Scheduled tasks such as publishing posts, sending emails and running backups use WP-Cron. On a network, a common fix is to stop visits triggering cron and have a real server cron job run due tasks for each site in turn, for example with WP-CLI:

for url in $(wp site list --field=url); do
  wp cron event run --due-now --url="$url"
done

Your developer can run this every few minutes from the server's scheduler after setting DISABLE_WP_CRON to true in wp-config.php. Stagger heavy jobs such as backups and imports so they don't run on every site at the same moment. WP-Cron explained covers the basics.

Hosting resources for a network

All sites in a network share one server's CPU, memory, PHP workers and database. A traffic spike, an import or a bot attack on one site slows every other site. Signs the plan is too small:

  • Resource limit warnings from your host, or 502 and 504 errors at busy times
  • Slow uncached pages and a slow admin, even after caching and database clean-up
  • A network admin that is sluggish for everyone, not just one user

Shared hosting is rarely a good fit for a busy network. A managed host that explicitly supports Multisite, or a VPS or cloud server with enough memory for PHP, the database and Redis, is usually the next step. Check Multisite support before you buy, as some plans don't allow it.

When to split the network

Sometimes the best speed fix is a smaller network. Consider moving sites out when:

  • One site has far more traffic, content or orders than the rest and keeps slowing them down
  • Sites need very different plugins, so every site carries code it doesn't use
  • Sites belong to different businesses or clients with different budgets and hosting needs
  • The network has outgrown one server and tuning hasn't helped

Moving a site out means exporting its content, media and users, re-creating its settings on a new install and redirecting any URLs that change. Some migration tools can extract a single subsite; check their current features and test on staging first.
