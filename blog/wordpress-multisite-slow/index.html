WordPress Multisite Slow? Why Networks Slow Down and How to Speed Up WordPress Multisite

Key takeaways
  • A slow WordPress multisite is usually caused by something shared: under-sized hosting, network-activated plugins, a large database, no object cache or piled-up cron jobs.
  • To speed up WordPress multisite, measure server response time on several subsites first, then fix plugins, caching, database, cron and PHP in that order.
  • If subsites need very different plugins, traffic or owners, separate installs may be faster and simpler than one network.

If your WordPress multisite is slow, the cause is usually something shared across the whole network: hosting that wasn't sized for many sites, plugins activated network-wide, a database with thousands of tables and bloated options, no persistent object cache, or scheduled tasks piling up on every subsite. To speed up WordPress multisite, measure server response time on a few subsites, find which shared resource is the bottleneck and fix that first. Because all sites run on one codebase, one database and one server, a problem on one subsite often slows the others too.

This guide explains why networks slow down, how to diagnose the bottleneck and the fixes that usually help most. If you are still deciding whether multisite is right at all, read WordPress multisite: when a business needs it first.

Why WordPress multisite gets slow

A single WordPress site has one set of database tables. In multisite, each subsite gets its own set of around ten tables, while users and network settings are shared. A network with 50 subsites can have hundreds of tables in one database, and every network-activated plugin runs on every page load of every subsite.

Step 1: measure before you change anything

Guessing wastes time on a network because changes affect every site. Collect a few numbers first:

  • Server response time (TTFB) on the main site and three or four subsites, both cached and logged in. A slow TTFB points at PHP, the database or hosting rather than images or front-end code. Reducing server response time explains how to test it.
  • Slow queries using the Query Monitor plugin on a staging copy or briefly on live while logged in. It shows which plugin or theme function causes slow database queries.
  • Server resources in your hosting panel: CPU, memory and PHP worker usage over the day.
  • Which subsites get the most traffic, since one popular site can starve the rest.

Step 2: review network-activated plugins

Network activation is convenient but expensive. A plugin activated for the network loads on every request across every subsite, even sites that never use it.

  • List network-activated plugins under Network Admin, Plugins.
  • For each one, ask whether every subsite needs it. If not, deactivate it network-wide and activate it only on the sites that use it.
  • Look for overlapping plugins, such as two SEO or security plugins, and remove one.
  • Be careful with page builders, related-post plugins, statistics plugins and anything that writes to the database on each page view.

Test changes on a staging copy of the network first. Deactivating a plugin network-wide can change how subsites look or behave.

Step 3: add persistent object caching

WordPress repeats many of the same database queries on each request. A persistent object cache (Redis or Memcached) stores those results in memory, which particularly helps the admin area and logged-in users, where page caching doesn't apply. On multisite, make sure the cache uses a key prefix so subsites don't share entries by mistake; the usual object cache plugins handle this when configured properly.

Page caching still matters for visitors. Check that your caching plugin or server cache supports multisite and is set up for each subsite and mapped domain. WordPress caching explained covers the different layers.

Step 4: clean the database

Large networks accumulate clutter quickly: post revisions, expired transients, orphaned tables from deleted subsites and plugins, and large autoloaded options that load on every page.

  • Check autoloaded options size per subsite and remove data left by uninstalled plugins.
  • Limit post revisions in wp-config.php.
  • Remove tables left behind by subsites that were deleted.
  • Make sure the database uses the InnoDB engine and that tables have proper indexes.

Always back up first. WordPress database optimisation explains each step in more detail.

Step 5: replace WP-Cron with a real cron

By default, WordPress runs scheduled tasks when someone visits a page. On multisite, every subsite has its own schedule, so visitors on busy subsites can trigger heavy jobs, while quiet subsites miss them entirely. Disable WP-Cron in wp-config.php and set up a server cron job that runs due events for every subsite at regular intervals, usually with WP-CLI looping through the sites. Your host's support can often help set this up.

Step 6: check hosting and PHP

Many networks start on shared hosting and outgrow it. Signs you need more resources include resource limit warnings, slow admin across all sites and slowdowns at the same times each day. Look at:

  • Enough PHP workers and memory for the number of subsites and simultaneous logged-in users.
  • A current, supported PHP version; see updating your PHP version.
  • Server-level caching and a database on fast storage.
  • Data centre location close to your main audience, for example India for Indian visitors.

Shared vs VPS vs managed WordPress hosting compares options. A network of many active subsites usually belongs on a VPS or managed plan rather than basic shared hosting.

Step 7: deal with the slow admin

Network admins often notice the dashboard is slow even when the front end is fine. Common causes are the "My Sites" menu loading many sites, dashboard widgets from plugins, the Heartbeat API and update checks for many plugins. Reducing dashboard widgets, slowing Heartbeat and using object caching help. Why WordPress admin is slow covers the general fixes, which apply to each subsite.

A safe order of work

Because every change on a network reaches every subsite, the order matters. A sequence that keeps risk low:

  1. Take a full backup of files and the database, and confirm you can restore it.
  2. Create a staging copy of the network, including mapped domains if possible.
  3. Record baseline numbers: TTFB on several subsites, admin load time and server resource graphs.
  4. Make low-risk changes first: real cron, object caching, PHP version, revision limits.
  5. Then move network-activated plugins to per-site activation, one at a time, checking affected subsites after each.
  6. Clean the database last, once you know which plugins are staying.
  7. Repeat the measurements and compare with the baseline before applying changes to live.

Tell subsite owners or editors when changes are planned, especially if a plugin they rely on is moving from network to per-site activation. Keep a short change log so that if something breaks a week later, you know what changed and when.

When multisite is the wrong structure

Sometimes slowness is a sign that the network should be split. If subsites have very different traffic, plugins and owners, or one large shop shares a network with many small sites, separate installations may be faster and easier to maintain. Splitting a site out of multisite is a migration project, so plan it with backups and redirects. Before deciding, compare the effort of maintaining one network against several separate sites, including updates, security monitoring and who manages each site day to day.

How to speed up WordPress multisite: a quick checklist

  1. Record server response time (TTFB) for the main site and three busy subsites, logged out and logged in.
  2. List network-activated plugins and move any that only some sites need to per-site activation.
  3. Turn on a persistent object cache such as Redis, with a separate key prefix for the network.
  4. Delete spam and archived subsites you no longer need, and clean expired transients and autoloaded options.
  5. Switch WP-Cron to a real server cron that loops through subsites.
  6. Update PHP to a supported version and check memory and worker limits.
  7. Add page caching that understands multisite, and a CDN for images and static files.
  8. Measure again and compare with your first numbers.

Work on a staging copy and keep a full backup, because a network-wide change affects every subsite at once.

Multisite on Indian hosting

Many Indian businesses start a network on a shared hosting plan bought for one site. That is often where the slowdown begins: the plan's CPU, memory and process limits are shared by every subsite, so one busy site or a heavy import slows the rest. Choose a data centre close to your visitors (Mumbai or Singapore for most Indian audiences), check whether Redis is available, and move to a VPS or managed plan once the network grows. FAQs

Why is my WordPress multisite slow?

Usually because of shared resources: hosting too small for the network, plugins activated network-wide, a large database without object caching, or scheduled tasks on many subsites. Measure TTFB and slow queries to find which applies.

Does multisite make WordPress slower than single sites?

Not by itself. A well-configured network can be fast. It becomes slow when many subsites share under-sized hosting or load plugins they don't need.

Should I use Redis object caching on multisite?

For most active networks, yes. A persistent object cache reduces repeated database queries, especially for logged-in users and the admin area. Configure it with proper key prefixes.

Can one subsite slow down the whole network?

Yes. All subsites share the server and database, so a busy, badly coded or attacked subsite can affect the others.

How do I find which plugin slows down multisite?

Use Query Monitor on a staging copy to see slow queries by plugin, and test by moving network-activated plugins to per-site activation one at a time.

Running a slow network? A careful, staging-first speed audit is part of WordPress speed optimisation.

How do I speed up WordPress multisite?

Measure TTFB first, then reduce network-activated plugins, add a persistent object cache, clean the database, replace WP-Cron with a server cron, update PHP and size hosting for the whole network. Test each change on staging.
