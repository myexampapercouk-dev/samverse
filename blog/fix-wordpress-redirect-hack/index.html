WordPress Site Redirecting to Spam? How to Find and Remove the Redirect Hack

WordPress site redirecting to spam? Why redirect malware hides, where it lives (.htaccess, wp-config, theme files, database) and how to remove it for good.

Key takeaways
  • Redirect malware usually targets mobile, logged-out visitors from Google, so test on mobile data in a private window.
  • Check .htaccess, wp-config.php, theme header and footer files, JS files, the database, fake plugins and mu-plugins.
  • Clean every location, purge all caches and close the entry point, or the redirect will come back.

Customers tell you your website sends them to a gambling, dating, fake prize or "your phone has a virus" page. When you open it yourself, everything looks normal. That's the classic WordPress redirect hack: malicious code that sends some visitors elsewhere while hiding from the site owner, so it survives as long as possible.

Here's why you might not see it, how to catch it, where the code hides and how to remove it for good.

First, make sure it's really a hack

A few harmless things can look like a redirect hack. Rule them out quickly:

  • A redirect plugin rule or a rule your developer added. Check any redirect plugin's list and your SEO plugin's redirect settings.
  • "Too many redirects" errors are a settings loop, not spam; see fixing ERR_TOO_MANY_REDIRECTS.
  • Ads or third-party scripts. If you run ads or embed widgets, a bad ad or a compromised third-party script can redirect visitors without your site being hacked.
  • Only one person sees it. A browser extension or adware on their own phone or computer may be the cause. Ask whether it happens on other devices.
  • Domain or DNS problems. An expired domain, or DNS records changed at your registrar, can send all visitors to someone else's server; see domain expired: what to do.

If it happens to different people on different devices and you didn't set it up, treat it as malware.

Why the redirect only happens on mobile or to logged-out visitors

Redirect malware is usually conditional. The code checks who is visiting before deciding whether to redirect:

  • Device: it reads the browser's user agent and targets phones, because owners mostly check their site on a computer
  • Where the visitor came from: it redirects people arriving from Google, Facebook or other search engines, but not people who type your address directly
  • Logged-in status: it looks for the WordPress login cookie and leaves administrators alone
  • Once per visitor: it sets a cookie so the second visit looks normal, which makes the problem hard to reproduce
  • Location or IP address: it targets certain countries, or skips IP addresses that have used the dashboard

Caching adds another layer. Logged-out visitors usually get cached copies of pages while logged-in admins bypass the cache, so an infected cached page can keep redirecting visitors even after the code is removed. Browsers can also remember a permanent redirect and keep sending a visitor there.

How to catch the redirect

  • Phone test: switch off Wi-Fi, open a private tab, search Google for your business and tap your result. Use a fresh private tab for each attempt.
  • Desktop test: in Chrome's developer tools, turn on device emulation, open the Network tab, tick "Preserve log", then visit your site from a Google result and watch for unfamiliar domains.
  • View the page source: search for script tags loading from unfamiliar domains, and for long scrambled code containing things like eval(, atob( or String.fromCharCode.
  • Remote scanner: an online scanner fetches your pages as a visitor would and flags known redirect code.

If you're comfortable with a terminal, you can pretend to be a mobile visitor arriving from Google:

curl -sI -A "Mozilla/5.0 (iPhone)" -e "https://www.google.com/" https://yourdomain.com/

A Location: header pointing to another domain means a server-side redirect. This won't reveal JavaScript redirects, which only run in a browser, so use the browser tests as well.

.htaccess files

On Apache and LiteSpeed hosting, .htaccess controls redirects before WordPress even loads. A malicious rule often looks something like this:

RewriteEngine On
RewriteCond %{HTTP_REFERER} (google|bing|facebook) [NC]
RewriteCond %{HTTP_USER_AGENT} (android|iphone|mobile) [NC]
RewriteRule ^(.*)$ https://spam-domain.example/ [R=302,L]

That rule redirects only mobile visitors arriving from search engines or Facebook. Check the .htaccess file in your main folder and in subfolders such as wp-content and uploads, and in any folder above your site. Keep the standard # BEGIN WordPress to # END WordPress block and rules you can explain, such as those from your caching or security plugin.

wp-config.php and index.php

These files load on every request, which makes them attractive. Look for code before the normal opening <?php line, long encoded strings, or an include of a strange file, often disguised with an image or icon extension:

<?php @include "/home/account/public_html/wp-content/uploads/2024/03/.cache.ico"; ?>

The root index.php in a normal WordPress install is only a few lines long. If yours is much longer, compare it with a fresh download of WordPress.

Theme files

Check header.php, footer.php and functions.php in your active theme and child theme. Injected scripts are often disguised as jQuery, analytics or a CDN file:

<script src="https://cdn-jquery-min.example/jquery.min.js"></script>

Also look for PHP that reads HTTP_USER_AGENT or HTTP_REFERER in a theme that has no reason to.

Attackers also append long, scrambled lines to legitimate .js files in themes and plugins. Sort by last modified date and compare suspicious files with clean copies.

The database

Redirect scripts are often injected into post content, widgets, theme options or the settings of plugins that add code to every page. Your table prefix may differ from wp_. In phpMyAdmin, queries like these find likely places:

SELECT ID, post_title FROM wp_posts WHERE post_content LIKE '%<script%';
SELECT option_name FROM wp_options WHERE option_value LIKE '%<script%';

With WP-CLI, you can search the whole database and check the site address settings:

wp db search "<script" --all-tables
wp option get siteurl
wp option get home

Some results will be legitimate embeds, such as maps or booking widgets, so review each one rather than deleting everything. Take a database backup before editing anything.

Rogue plugins and mu-plugins

Look in wp-content/plugins for folders you didn't install, especially with generic names that mimic real plugins. Some malware hides itself from the Plugins screen, so compare the folders on the server with the list in your dashboard.

Then check wp-content/mu-plugins. "Must-use" plugins load automatically, can't be deactivated from the dashboard and are easy to miss. If you didn't knowingly add any, an unexpected file here is a strong warning sign. Also check drop-in files directly inside wp-content, such as advanced-cache.php and object-cache.php: they're normal if your caching setup created them, suspicious if not.

Scheduled tasks

If the redirect returns within hours of cleaning, look for a cron job in your hosting control panel that downloads or rewrites files, and list WordPress scheduled events with wp cron event list or a cron viewer plugin. Remove anything you can't account for.

How to fix the WordPress redirect hack, step by step

  1. Back up the infected site (files and database) and note the redirect destinations and dates.
  2. Change every password: hosting, SFTP, database (then update wp-config.php) and all WordPress admins. Generate new security keys in wp-config.php to log everyone out.
  3. Remove admin users you don't recognise.
  4. Replace WordPress core: fresh wp-admin and wp-includes folders for your version, then check root files by hand or with wp core verify-checksums.
  5. Reinstall plugins and themes from official sources, and delete unused or nulled ones. If your theme has custom changes, compare it with a known clean copy.
  6. Clean .htaccess, wp-config.php and index.php as described above.
  7. Remove PHP files from uploads and anything suspicious in mu-plugins.
  8. Clean the database: injected scripts, spam posts and changed site URLs.
  9. Remove malicious cron jobs and scheduled events.
  10. Purge every cache: your caching plugin, your host's server cache and your CDN.
  11. Test again on mobile data, from Google, in fresh private windows, and repeat over the next few days.

Backdoors are what usually bring the redirect back, so read finding and removing WordPress backdoors as well. The complete process is in how to remove malware from WordPress step by step.

Why the redirect keeps coming back

  • A backdoor was missed: attackers usually leave several ways back in
  • The entry point is still open: an outdated plugin or theme, or a reused password
  • Another site in the same hosting account is infected and keeps reinfecting yours; see cleaning a whole hosting account
  • A cron job reinstalls the code
  • A computer with saved FTP or hosting passwords is infected, so new passwords get stolen too

Check Google once it's clean

Redirect hacks often lead to a red browser warning or "This site may be hacked" in search results. Once the site is clean, check Search Console's Security issues report and request a review; see fixing "Deceptive site ahead" and removing "This site may be hacked". If rankings dropped, see recovering rankings after a hack.

How to prevent redirect hacks

  • Keep WordPress, plugins and themes updated, and delete anything you don't use
  • Never use nulled plugins or themes; see the risks
  • Use two-factor authentication for admins; see securing your WordPress login
  • Disable file editing in the dashboard and protect wp-config.php; see hardening wp-config.php
  • Block PHP from running in the uploads folder, and set sensible file permissions
  • Use a firewall and file-change monitoring

FAQs

Why is my WordPress website redirecting to another site?

If you didn't set up the redirect, the most likely cause is malware injected into .htaccess, a core or theme file, a plugin or the database. Less often it's a bad ad, a compromised third-party script, or a domain or DNS problem. Test on several devices to tell them apart.

Why does the redirect only happen on mobile?

The malware checks the visitor's device and where they came from, and deliberately targets mobile visitors from search engines. Site owners mostly check on a computer while logged in, so the infection goes unnoticed for longer.

Can a security plugin remove redirect malware automatically?

It can detect and remove some known infections, but redirect code in the database, .htaccess or a fake plugin is often missed, and plugins don't close the hole the attacker used. Use a scanner to help, then check the locations above by hand.

Will a redirect hack hurt my Google rankings?

It can, through browser warnings, visitors bouncing straight back and spam pages indexed under your domain. Rankings usually recover after a thorough clean-up and a successful review, though how long that takes varies.

Do I need to reinstall WordPress to fix it?

You should replace WordPress core, plugins and themes with clean copies, but you don't need to start from scratch. Your posts, pages and media can be kept once the database and uploads folder are cleaned.

The redirect came back after I removed it. What now?

Something was missed: usually a backdoor, a cron job, an infected neighbouring site or an unpatched plugin. Change passwords again from a clean device and work through every location in this guide.
