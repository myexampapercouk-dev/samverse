Search Console Says Sitemap "Couldn't Fetch"? Causes, Checks and When to Wait

Search Console says your sitemap couldn't be fetched, or shows a General HTTP error? See the usual causes, the checks to run in order and when to simply wait.

Key takeaways
  • "Couldn't fetch" or a General HTTP error means Google didn't get a usable sitemap file back; it doesn't mean your pages have been removed from Google.
  • Open the exact submitted URL in a private window, check its status code, robots.txt and the URL Inspection live test before changing anything else.
  • If the sitemap loads cleanly, returns 200 and passes the live test, resubmit once and wait rather than resubmitting every day.

You submit your XML sitemap in Google Search Console, and instead of "Success" the Sitemaps report says "Couldn't fetch", or shows a "General HTTP error". Usually the cause is something small: a wrong address, a redirect, a security rule, or simply a sitemap Google hasn't got round to yet. This guide covers what the messages mean, the checks to run in order, and when waiting is the right answer. For a refresher on what a sitemap is and what belongs in it, start with XML sitemaps explained.

What "Couldn't fetch" and "General HTTP error" mean

Both messages say the same basic thing: when Google tried to download your sitemap, it didn't get a usable file back.

  • Couldn't fetch means Google couldn't retrieve the sitemap, or hasn't managed to yet.
  • General HTTP error means your server answered with an error instead of the file. That could be a "not found", "forbidden" or server error response, and the status code tells you which.

Neither message means your pages have been removed from Google. A sitemap is a helpful list, not a requirement: Google also finds pages by following links. Check how your important pages are doing in URL Inspection and the Pages report, which Search Console page indexing errors explained walks through.

The common causes

1. The wrong URL was submitted

Each sitemap system uses its own address: WordPress's built-in sitemap lives at /wp-sitemap.xml, while SEO plugins often use /sitemap_index.xml or something similar. If you switched SEO plugins, or someone submitted /sitemap.xml out of habit, Google may be asking for a file that doesn't exist. Typos, http instead of https, and www versus non-www count too. Note that WordPress also switches off its built-in sitemap while "Discourage search engines" is ticked under Settings → Reading.

2. Robots.txt blocks it

If a Disallow rule covers the sitemap's path, or a leftover staging rule blocks the whole site, Googlebot isn't allowed to request the file. Robots.txt explained shows how the rules work.

3. Redirects

The sitemap URL redirects somewhere else: from http to https, from an old plugin's sitemap to the homepage, or round in a loop. A redirect that ends on an ordinary web page hands Google HTML instead of XML. Submit the final address, and make sure no redirect plugin rule catches it.

4. Server errors and blocked bots

WordPress sitemaps are usually generated on the fly, so a slow or overloaded server, a PHP error or a plugin conflict can make the request fail. Security plugins, hosting firewalls and CDN bot protection can also answer Googlebot with "forbidden", or with a challenge page a crawler can't pass. Maintenance and "coming soon" modes do the same.

5. A new property or sitemap still processing

On a newly verified property, or soon after you submit, the report can show "Couldn't fetch" even when the file is perfectly fine. It often just means Google hasn't processed it yet.

Checks to run, in order

  1. Copy the exact URL from the Sitemaps report and open it in a private browser window, so you aren't seeing it as a logged-in admin. You should see a plain list of links or of smaller sitemap files.
  2. Check the status code. A free online HTTP header checker, or the Network tab in your browser's developer tools, shows what the server returns. You want 200. A 301 or 302 is a redirect, 403 means something is refusing access, 404 means the URL is wrong, and 500 or 503 point to a server problem.
  3. Open the child sitemaps. A sitemap index lists several smaller sitemaps for posts, pages or products. One broken child can be the real problem.
  4. Read your robots.txt at yourdomain.com/robots.txt and look for Disallow rules matching the sitemap path or the whole site. Search Console's robots.txt report shows the version Google last fetched.
  5. Run the sitemap URL through URL Inspection and click Test live URL. This checks whether Googlebot can fetch it, whether crawling is allowed and what it actually receives.
  6. Check the property. A URL-prefix property only covers addresses starting with that exact prefix, so a sitemap on the www version doesn't belong to a non-www property. A Domain property covers every version.
  7. Ask your host about blocks. If the file loads for you but not for Google, server or firewall logs will show whether Googlebot's requests were refused.

When to simply wait

If the sitemap loads in a private window with a 200 status, the XML is clean, robots.txt allows it and the live test in URL Inspection fetches it successfully, there's nothing left to fix on your side. In that case:

  • Resubmit it once, then leave it alone. There's no sign that removing and re-adding it every day gets it read any sooner.
  • Watch the "Last read" date in the Sitemaps report; once the status changes to Success, you're done.
  • Check whether your key pages are getting indexed in URL Inspection, since that matters more than the sitemap's status label.

There's no fixed timescale for this, especially on a new domain. For a brand-new site, the steps in how to get your website indexed faster help more than repeated resubmissions. If it stays stuck for weeks despite every check passing, revisit firewall and hosting rules.
