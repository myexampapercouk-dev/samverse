reCAPTCHA Not Working on WordPress? Fixing "Invalid Domain", Key Type Errors and Forms That Won't Send

reCAPTCHA not working on WordPress? Fix invalid domain or key type errors, a missing badge, failed submissions, v3 score settings and spam getting through.

Key takeaways
  • "Invalid domain for site key" means the domain is missing from the key's list, and "Invalid key type" means a v2 key and a v3 integration, or vice versa, have been mixed.
  • Script delay, lazy-loading, caching and cookie consent tools often stop reCAPTCHA loading or leave tokens expired, so exclude its scripts and test in a private window.
  • Start v3 near the 0.5 threshold Google suggests, make sure submissions are verified on the server, and consider Turnstile or a honeypot as lower-friction alternatives.

Google reCAPTCHA is meant to stop bots quietly. When it's set up wrongly, it does the opposite: a red "ERROR for site owner" box appears on your contact form, the form refuses to send, or real enquiries are rejected while spam carries on. Here's how to find the cause. Google has been moving reCAPTCHA keys into Google Cloud, so screens may differ from older tutorials.

Read the error first

What you seeUsual cause
"ERROR for site owner: Invalid domain for site key"Your domain isn't on the key's list of allowed domains
"ERROR for site owner: Invalid key type"The key's type doesn't match the integration, such as a v3 key in a v2 widget
"ERROR for site owner: Invalid site key"A typo, a stray space, the secret key pasted into the site key field, or a deleted key
"Localhost is not in the list of supported domains"Testing on a local or staging copy with the live key
No checkbox or badge, and no errorThe script isn't loading: blocked, delayed or held back by a consent tool
The form spins, fails or says the message looks like spamThe server-side check is failing: wrong secret key, low v3 score, expired token or no connection to Google

v2 and v3 keys can't be mixed

reCAPTCHA comes in different types, and each key is created for one of them:

  • v2 "I'm not a robot": the familiar checkbox, sometimes followed by an image challenge.
  • v2 Invisible: no checkbox; a badge appears and a challenge shows only when traffic looks suspicious.
  • v3: never shows a challenge. It gives each visit a score from 0.0 (likely a bot) to 1.0 (likely a person), and your form plugin decides what to do with it.

The type is chosen when the key is created, and a v2 key won't work with a v3 integration or the other way round. Check which type your form plugin expects; some built-in integrations support only one. If the key doesn't match, create a new key of the right type rather than forcing it. Each key also comes as a pair: the site key goes in the page, the secret key is used by your server, and both must come from the same key.

Load reCAPTCHA once per page. If a form plugin, a separate reCAPTCHA plugin and a security plugin each add their own script, possibly with different versions or keys, they clash and produce key type errors or widgets that never appear. Pick one integration and switch reCAPTCHA off in the others.

Check the domains in the admin console

Sign in to the reCAPTCHA admin console with the Google account that created the key. Often that's a former developer's or agency's account; if nobody can get in, create new keys under an account the business owns and update them in your plugin.

  • Enter domain names only, such as example.com, without https:// or paths. A registered domain generally covers its subdomains, including www.
  • Add the new domain after a rebrand or domain change; the old key won't follow you.
  • Use a separate key for staging, or add the staging domain deliberately, and remember to tidy it up later.
  • Domain changes can take a little while to apply, so wait before deciding they didn't work.

Badge missing or form not loading: caching, script delay and consent

Speed and privacy tools are a common cause of reCAPTCHA failing on a site that worked before:

  • Delay or defer JavaScript: settings that hold scripts until the visitor scrolls or taps can stop the checkbox appearing, or leave the v3 token missing when the form is sent. Exclude scripts containing "recaptcha" and your form plugin's scripts from delay, defer and combine settings.
  • Lazy-loading iframes: the checkbox and challenge load inside iframes, which some lazy-loading features rewrite. Exclude them.
  • Page caching: reCAPTCHA tokens are valid for only about two minutes, so a token created when the page loads can be stale by the time a visitor sends a long message. Good integrations request a fresh token on submit. Cached pages can also carry expired security tokens from the form plugin; see WordPress caching explained for exclusions.
  • Cookie consent tools: if reCAPTCHA is blocked until visitors accept cookies, anyone who declines may be unable to send the form. How to categorise it is partly a legal question, so check current privacy rules with your lawyer.
  • Security headers: a Content Security Policy must allow the Google domains reCAPTCHA uses.

A badge can also be hidden with CSS. Google's FAQ allows that only if you show its required notice and links near the form; check the current wording. Then clear every cache, including the CDN, and test in a private window.

Forms failing or spam getting through: v3 scores

With v3, your form plugin rejects submissions below a threshold. Google's documentation suggests 0.5 as a starting point. Set it too high and visitors on VPNs, privacy-focused browsers or shared office networks may be rejected with a vague error, and you'll never hear about the enquiry. Set it too low and bots get through. Google also notes that scores improve as reCAPTCHA sees real traffic on your site, so results on staging or just after setup may differ.

If spam still arrives, check that:

  • The secret key is entered and the plugin verifies every submission on the server; a script on the page alone protects nothing
  • Your server can reach Google to verify, since some hosts block outgoing connections; the error log will show failed requests
  • Every form is covered, including comments, registration, newsletter sign-ups and WooCommerce forms

No CAPTCHA stops people paid to fill in forms by hand. For layered defences, see how to stop contact form spam.

Alternatives: Turnstile, honeypots and layers

  • Cloudflare Turnstile: a low-friction challenge that can be used even if your site doesn't run through Cloudflare. Many form plugins support it directly or through an add-on; check current plans and terms.
  • Honeypot fields and time checks: invisible to visitors and verified on the server. They stop many simple bots and suit low-traffic forms well.
  • Spam-filtering services: check the content of submissions and keep a spam folder you can review.

Whatever you use, mention it in your privacy policy, then send a test enquiry on desktop and mobile after every change. A form that silently rejects real people costs more than spam; why a contact form stops getting enquiries covers the other checks.
