WordPress Block Themes and Full Site Editing Explained: theme.json, Templates, Patterns and When Agencies Should Use Them

WordPress block themes and full site editing explained: the Site Editor, theme.json, templates, parts and patterns, and when to choose them over Elementor.

Key takeaways
  • A block theme builds the whole site, including headers, footers and templates, from blocks, with design settings in theme.json and editing in the Site Editor.
  • Changes made in the Site Editor are saved in the database, not the theme files, so agencies need a clear rule for where template changes live.
  • Choose a block theme for lean, structured sites with a stable design system; choose Elementor when non-technical clients must rearrange layouts themselves.

A block theme is a WordPress theme built entirely from blocks: headers, footers and page templates are block markup rather than PHP files, global design settings live in a theme.json file, and the whole site can be edited visually in the Site Editor, which WordPress calls full site editing. For agencies, block themes suit lean, structured sites with a stable design system and clients who mainly edit content; a page builder such as Elementor still suits clients who want to rearrange layouts themselves, and a classic theme suits builds that depend on custom PHP templates.

When I build for agencies as a white-label WordPress developer, sites are built with global styles and a clean structure in Elementor or the block editor, so clients can edit without breaking the layout. A block theme is also one of the three build approaches compared on my Figma to WordPress page. This guide explains how block themes work and how to decide when to use one.

Full site editing arrived in WordPress 5.9 in early 2022 and has changed with almost every release since, so check the details below against the version you run.

What full site editing changes

In a classic theme, the block editor only handles the content area of posts and pages. The header, footer, sidebars and archive layouts come from PHP template files, and changing them means editing code or using the Customizer and widgets. In a block theme, those parts are blocks too, and an administrator can change them under Appearance > Editor, the Site Editor, with the same tools used for page content.

The parts of a block theme

PartWhere it livesWhat it does
theme.jsonTheme rootGlobal settings and styles: colour palette, font sizes, spacing, layout widths, and which design options editors see
Templates/templates folder, as .html filesLayouts for page types: index, front page, single post, page, archive, search, 404

The minimum a block theme needs is a style.css file and a templates/index.html file; everything else is added as the design requires. A functions.php file is optional, used for things such as registering pattern categories or enqueueing extra assets.

theme.json: the design system in one file

theme.json is where a block theme turns a design system into rules. It defines the palette, font families and sizes, spacing scale and content widths, and it can switch off the options that let editors drift off-brand, such as custom colours or arbitrary font sizes. A trimmed example:

{
  "$schema": "https://schemas.wp.org/trunk/theme.json",
  "version": 3,
  "settings": {
    "color": {
      "palette": [
        { "slug": "primary", "color": "#1d4ed8", "name": "Primary" },
        { "slug": "ink", "color": "#111827", "name": "Ink" },
        { "slug": "paper", "color": "#ffffff", "name": "Paper" }
      ],
      "custom": false,
      "customGradient": false,
      "defaultPalette": false
    },
    "typography": {
      "customFontSize": false,
      "fontSizes": [
        { "slug": "small", "size": "0.875rem", "name": "Small" },
        { "slug": "large", "size": "1.5rem", "name": "Large" }
      ]
    },
    "layout": { "contentSize": "720px", "wideSize": "1200px" }
  }
}

With custom colours and font sizes turned off, editors pick from the brand palette and type scale only. The schema version changes as WordPress adds features, so match it to the oldest WordPress version you support. For agencies working from Figma, colour styles, text styles and spacing tokens map onto these settings almost one to one.

Templates and template parts

Templates are HTML files made of block markup. A simple single post template looks like this:

<!-- wp:template-part {"slug":"header","tagName":"header"} /-->
<!-- wp:group {"tagName":"main","layout":{"type":"constrained"}} -->
<main class="wp-block-group">
  <!-- wp:post-title {"level":1} /-->
  <!-- wp:post-featured-image /-->
  <!-- wp:post-content {"layout":{"type":"constrained"}} /-->
</main>
<!-- /wp:group -->
<!-- wp:template-part {"slug":"footer","tagName":"footer"} /-->

WordPress chooses templates using the same hierarchy as classic themes, so a single-product.html or category-news.html file works as you would expect. Custom templates can be registered in theme.json, so editors can pick a "Landing page" or "Full width" layout from the page settings.

The database catch

When anyone edits a template, part or global styles in the Site Editor, WordPress saves that version in the database, and it overrides the file in the theme. That has three consequences for agencies:

  • Changes you later make to the theme's files don't appear on templates that were edited in the Site Editor, until those customisations are cleared.
  • Edits made on staging in the Site Editor don't travel with the theme files; they need exporting into the theme, or the database moving with them.
  • A client who edits the header in the Site Editor has changed it for the whole site, with no approval step.

Agree one rule per project: either templates live in theme files under version control and the Site Editor is used only to try changes that are then copied into the files, or the client owns certain templates in the editor and you never edit those files. Tools such as the Create Block Theme plugin can export Site Editor changes back into theme files.

Patterns: where editors actually work

Patterns are saved arrangements of blocks, such as a hero, a service grid or a testimonial band, that editors insert from the pattern library. In a block theme, a PHP file in the /patterns folder with a short header comment is registered automatically. Patterns can be locked so editors change text and images but not the layout, and synced patterns let one section, such as a site-wide call to action, update everywhere at once.

When core blocks can't produce a component, such as a pricing table with structured fields or a filtered project list, that becomes a custom block. Custom Gutenberg blocks compares patterns, ACF blocks and native blocks, and how to lock them.

When agencies should choose a block theme

  • Choose a block theme for content-led sites with a stable design system, strict speed targets, clients who edit text and images rather than layouts, and long-term projects where avoiding a builder licence matters.
  • Choose Elementor when the client's marketing team wants to build new landing pages and rearrange sections without a developer, or when whoever maintains the site later knows Elementor best.
  • Choose a classic or custom theme when the build depends on complex PHP templates, heavy custom fields or plugins that don't yet support block templates well, or when you are extending an existing classic site; custom theme development covers that route.

Check plugin support before committing. Most current plugins work with block themes, and WooCommerce provides block templates for the shop, product, cart and checkout, but some older plugins still assume classic theme hooks or widgets. A sensible workflow for agency block theme builds

  1. Turn the Figma colour, text and spacing styles into theme.json before building pages.
  2. Build header, footer and core templates as files, under version control.
  3. Build a pattern library for repeated sections, and custom blocks only where core blocks fall short.
  4. Lock patterns and switch off custom colours and font sizes in theme.json.
  5. Give the client the Editor role for day-to-day content. By default the Site Editor needs the capability to edit theme options, which administrators have and editors don't.
  6. Record in the handover note which templates the client may change in the Site Editor, and how to reset one.

FAQs

What is the difference between a block theme and a classic theme?

A block theme builds every part of the site, including headers, footers and templates, from blocks that can be edited in the Site Editor. A classic theme uses PHP template files, and the block editor only handles post and page content.

Where is the Site Editor in WordPress?

Under Appearance > Editor, when a block theme is active. With a classic theme you see the Customizer and, depending on the theme, Widgets and Menus instead.

Can I use Elementor with a block theme?

It can work, but mixing two systems for headers, footers and templates gets confusing. Elementor builds usually sit on a light classic theme, and block theme builds use the Site Editor.

Do block themes need a child theme?

Not for design changes made in the Site Editor, which are saved in the database. For code changes to a third-party block theme, a child theme still protects your work from updates; see WordPress child themes explained.

How do I stop clients breaking the design in a block theme?

Turn off custom colours and font sizes in theme.json, lock patterns and templates, and give clients the Editor role so they edit content without access to the Site Editor.
