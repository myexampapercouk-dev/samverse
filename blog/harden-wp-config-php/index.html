Hardening wp-config.php: Security Settings Every WordPress Site Should Use, and Which Ones to Skip

Harden wp-config.php: fresh salts, DISALLOW_FILE_EDIT, FORCE_SSL_ADMIN, debug settings, database user rights, file protection, and the myths you can skip.

Key takeaways
  • Add DISALLOW_FILE_EDIT, keep debugging off on the live site, force HTTPS for the admin area and refresh the salts after a hack or when someone with access leaves.
  • DISALLOW_FILE_MODS also blocks dashboard updates and automatic updates, so use it only when updates are handled by WP-CLI, deployments or a maintenance routine.
  • Changing the table prefix or moving wp-config.php up a folder adds little real protection; deleting leftover backup copies of the file and setting tight permissions matter more.

To harden wp-config.php, make sure it has fresh, unique security keys and salts, add DISALLOW_FILE_EDIT to remove the dashboard code editors, keep debugging switched off on the live site, force HTTPS for logins with FORCE_SSL_ADMIN, use a database user that can only reach this site's database, and protect the file itself with tight permissions and no leftover backup copies. DISALLOW_FILE_MODS goes further but stops dashboard updates, and changing the table prefix or moving the file up a folder add less protection than people think.

wp-config.php is also a favourite hiding place for injected code. If your site may already be hacked, clean it before you harden it; checking wp-config.php and the other core files is part of my WordPress malware removal service.

Before you edit wp-config.php

  • Back up the file and keep a copy on your computer. One missing semicolon can take the whole site down, and the fix is putting the old file back.
  • Edit it over SFTP or your host's File Manager, with a plain-text editor, not a word processor.
  • Put new lines above the comment that says "That's all, stop editing! Happy publishing." Anything below the line that loads wp-settings.php comes too late to take effect.
  • Check a setting isn't already defined. Defining the same constant twice produces a warning, and the first definition wins.

A recommended security block

For a typical live business site, these lines are a good starting point:

define( 'DISALLOW_FILE_EDIT', true );
define( 'FORCE_SSL_ADMIN', true );
define( 'WP_DEBUG', false );
define( 'WP_DEBUG_DISPLAY', false );

Each setting is explained below, along with the ones to think about before adding. The rest of the hardening, from logins to backups, is in the WordPress security checklist.

Security keys and salts

The eight keys and salts (AUTH_KEY, SECURE_AUTH_KEY, LOGGED_IN_KEY, NONCE_KEY and four matching salts) secure login cookies. They should be long and random. You can get a fresh set from WordPress.org's generator at api.wordpress.org/secret-key/1.1/salt/ and paste them over the old ones, or use WP-CLI:

wp config shuffle-salts

Changing them logs everyone out, which is what you want after a hack or when someone with access leaves. It doesn't change anyone's password, so do that separately.

DISALLOW_FILE_EDIT

The Theme File Editor and Plugin File Editor let any administrator edit PHP from the dashboard. If an attacker gets into an admin account, that is the quickest way to plant a backdoor. Setting this to true removes both editors. You lose nothing important: code changes belong in a child theme or a small plugin, made over SFTP and tested first.

DISALLOW_FILE_MODS: stronger, with a trade-off

This blocks installing, updating and deleting plugins and themes from the dashboard, and it also switches off automatic updates, including core security releases. It implies DISALLOW_FILE_EDIT too. That makes the dashboard far less useful to an attacker, but updates must then happen another way: WP-CLI, a deployment process or a developer who updates on a schedule. If nobody does that, the site falls behind on security fixes, which is worse than the risk you were trying to remove. Read WordPress auto-updates before deciding.

FORCE_SSL_ADMIN, and the proxy problem

This makes logins and admin pages always use HTTPS. The whole site should already be on HTTPS, so on most sites nothing visible changes. The catch comes behind a proxy, CDN or load balancer, where WordPress may not realise the visitor is on HTTPS and keeps redirecting. If the admin area loops after you add it, the proxy is usually passing a header WordPress isn't reading. Adding this above the security block tells WordPress to trust it:

if ( isset( $_SERVER['HTTP_X_FORWARDED_PROTO'] ) && 'https' === $_SERVER['HTTP_X_FORWARDED_PROTO'] ) {
    $_SERVER['HTTPS'] = 'on';
}

Use it only behind a proxy you control, and see fixing ERR_TOO_MANY_REDIRECTS if the loop continues.

Debug settings on a live site

PHP errors shown to visitors reveal file paths, plugin names and sometimes more. On a live site, WP_DEBUG should be false. If you need to troubleshoot, log errors privately instead of showing them, and write the log outside the public folder, because the default wp-content/debug.log can be downloaded by anyone who knows where to look:

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', '/home/account/logs/wp-debug.log' );
define( 'WP_DEBUG_DISPLAY', false );

Switch it back off when you're done, and delete any debug.log left in wp-content.

Automatic updates and outgoing connections

WordPress installs minor core releases, which include security fixes, automatically by default. Leave that alone: don't add AUTOMATIC_UPDATER_DISABLED, and if WP_AUTO_UPDATE_CORE is set to false, someone has switched off those security releases, so find out why. For tightly controlled sites there is also WP_HTTP_BLOCK_EXTERNAL, which stops WordPress making outgoing requests to anywhere not listed in WP_ACCESSIBLE_HOSTS:

define( 'WP_HTTP_BLOCK_EXTERNAL', true );
define( 'WP_ACCESSIBLE_HOSTS', 'api.wordpress.org,*.wordpress.org' );

It can stop some malware fetching instructions, but it also breaks licence checks, payment gateways, email services and anything else that calls an outside API until you add each host. It suits sites a developer looks after closely, not a typical small business site.

DISALLOW_UNFILTERED_HTML and staging copies

On a normal single site, administrators and editors can save raw HTML, including scripts, in posts and widgets. Setting DISALLOW_UNFILTERED_HTML to true stops that, which limits the damage if an editor account is taken over. It can break legitimate embeds, so test after adding it. On staging copies, set WP_ENVIRONMENT_TYPE to staging, so plugins that check it can keep live-only features, such as sending emails or payments, switched off.

Protect the file itself

  • Permissions: tighter than other files, often 600, 640 or 440 depending on how your host runs PHP; see WordPress file permissions explained.
  • Delete leftover copies. Files such as wp-config.php.bak, wp-config.old or wp-config.php.save aren't run as PHP, so the server may show them as plain text, database password included. List them with ls -la | grep -i config in the site root.
  • Block web access on Apache or LiteSpeed with a rule in the root .htaccess file, shown below.
  • Use a unique database user for each site, with access only to that site's database, so one leaked wp-config.php can't be used to read your other sites.
<Files wp-config.php>
  Require all denied
</Files>

Check wp-config.php after a hack

Attackers like this file because it loads on every request. Look for code before the opening <?php line or after the final line, include or require lines pointing to unfamiliar files (often disguised with an image or icon extension), long encoded strings, and settings you don't recognise. Compare it with wp-config-sample.php from a fresh WordPress download, then change the database password and the salts. Finding and removing backdoors covers the other places to check.

wp-config.php on shared hosting in India

Most Indian small business sites run on shared cPanel or hPanel hosting, and that shapes which hardening steps are practical.

  • Database user rights. cPanel's MySQL Databases screen lets you create a separate user for each site. Give each WordPress install its own user and database, so a hacked site cannot read another site's tables on the same account.
  • Several sites in one account. If one hosting plan holds your main site, a staging copy and an old landing page, each has its own wp-config.php. Harden all of them, and delete old copies you no longer use, because attackers often get in through the forgotten one.
  • Host-level settings. Some hosts add their own lines for caching or object cache. Leave those in place and add your security block above the "That's all, stop editing" comment.
  • Backups that include the file. Many host backups cover public_html. If you moved wp-config.php one level up, confirm that your backup still includes it, or a restore will not boot.

After any change, load the home page, log in, save a post and run a plugin update. If something fails, restore your copy of the file first, then add the lines back one at a time. If the site has already been hacked, or you are unsure what an unfamiliar line in the file does, get help from a WordPress developer in India before you edit further.

A typo in wp-config.php is a common cause of a WordPress critical error. Keep a copy of the original file so you can roll back quickly.

FAQs

Where is wp-config.php?

In the main folder of your WordPress install, usually public_html on cPanel hosting, next to wp-admin and wp-content. If it isn't there, check the folder above, where WordPress also looks.

Is it safe to edit wp-config.php?

Yes, if you back it up first and edit carefully. A typo can take the site down, but restoring the backup copy fixes it straight away.

What does DISALLOW_FILE_EDIT do?

It removes the theme and plugin file editors from the dashboard, so someone who gets into an admin account can't edit PHP files from there. It doesn't affect updates.

Should I change the WordPress table prefix?

Not on an existing site. It adds little protection and the change can break things. Setting a different prefix on a new install does no harm.

Should I move wp-config.php above public_html?

It's optional. WordPress supports it and it adds a small layer of protection, but some hosts and tools expect the file in the site root, and it does nothing against an attacker with file access.

What happens when I change the salts?

Everyone is logged out and has to log in again. Passwords stay the same, so change those separately if they may have leaked.
