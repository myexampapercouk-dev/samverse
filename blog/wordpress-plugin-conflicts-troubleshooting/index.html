How to Fix WordPress Plugin Conflicts Safely: Staging, Troubleshooting Mode, Debug Logs and Prevention

Fix WordPress plugin conflicts without risking your live site: test on staging, use Health Check mode, halve your plugins, read the debug log and console.

Key takeaways
  • Never hunt for a plugin conflict on a busy live site: take a backup, then reproduce the problem on staging or in Health Check troubleshooting mode.
  • Deactivate plugins in halves rather than one by one, then read the debug log and the browser console to confirm which plugin, file or script is failing.
  • Most conflicts are prevented by updating one plugin at a time on staging, avoiding overlapping plugins and removing anything abandoned or nulled.

To fix a WordPress plugin conflict, first protect the live site with a backup, then reproduce the problem on a staging copy or in Health Check troubleshooting mode. Switch to a default theme and deactivate plugins in halves until the problem disappears, re-enable them to find the exact pair that clashes, and confirm it in the PHP debug log or the browser console. Then update, replace or roll back one of the two plugins, and change how you update so it doesn't happen again.

A conflict happens when two plugins, or a plugin and your theme, each work alone but break something together: a form stops sending, a layout falls apart, checkout hangs or the site shows a critical error. Finding and fixing these safely is a routine part of my WordPress maintenance work, and this guide is the same method written out so you can follow it yourself.

Is it really a plugin conflict?

Several problems look like conflicts but aren't. Rule these out early, because the fix is completely different.

SymptomLikely a conflict ifCould also be
Critical error or white screenIt started right after a plugin install or updatePHP version change, memory limit, a hack
Sliders, menus or pop-ups stop workingThe browser console shows a red JavaScript errorA caching or minification setting
Layout broken on some pagesIt returns after switching one plugin back onA stale cached CSS file
Forms don't submit or emails don't arriveSubmission fails with an errorEmail delivery, which needs SMTP
Two sets of meta tags or duplicate lazy loadingTwo plugins do the same jobTheme features overlapping a plugin
Admin very slowOne plugin's screens are slowHosting limits or a bloated database

A blank page with no message at all is covered in fixing the WordPress white screen of death; "allowed memory size exhausted" messages are a hosting limit rather than a clash. If forms submit but no email arrives, the cause is usually delivery rather than a conflict.

Before you touch anything: a five-minute safety routine

  1. Take a fresh backup of files and database. The backup and restore guide covers the options.
  2. Write down what changed recently: a new plugin, an update, a theme change, a PHP upgrade on the host, or a new CDN or caching rule.
  3. Clear every cache (plugin, hosting and CDN), then check in a private browser window. A surprising number of "conflicts" are an old cached file.
  4. If customers can't buy or book, restore service first. Roll back the last update or restore the backup, then investigate on a copy.

Reproduce it on a staging site

Switching plugins on and off on a live store or booking site breaks things for real visitors. A staging copy lets you test freely; many hosts create one in a few clicks, and staging sites explained walks through the setup.

Confirm the problem appears on staging. If it doesn't, suspect something that differs between the two: server-level caching, a CDN rule, PHP settings, or a licence tied to the live domain.

Or use Health Check troubleshooting mode

When staging isn't available, the free Health Check & Troubleshooting plugin from the WordPress.org community is the next safest option. In troubleshooting mode it turns off every plugin and loads a default theme, but only for your own logged-in session; visitors keep seeing the normal site.

  1. Install and activate Health Check & Troubleshooting.
  2. Go to Tools, then Site Health, open the Troubleshooting tab and enable troubleshooting mode.
  3. Check whether the problem has gone. If it has, a plugin or the theme is responsible.
  4. From the Troubleshooting menu in the admin bar, enable plugins one at a time (or in groups) and recheck after each.
  5. Disable troubleshooting mode when you finish.

It has limits: server caching, scheduled tasks and anything that runs for logged-out visitors may behave differently. Treat it as a strong first step, not the final word.

Find the culprit quickly: the halving method

Turning plugins on one at a time works, but on a site with 30 plugins it is slow. Halving is faster:

  1. Check the theme first. Switch to a default "Twenty" theme. If the problem disappears, the theme is involved, alone or with a plugin.
  2. Deactivate all plugins except any the broken feature depends on, such as WooCommerce for a checkout problem. If the problem goes, a conflict is confirmed.
  3. Reactivate half of the remaining plugins. If the problem returns, the culprit is in that half; if not, it is in the other half.
  4. Keep halving the suspect group until you are down to one plugin.
  5. Confirm the pair: with only the suspect and its partner (or the theme) active, the problem should appear; with either one off, it should not.

Each round halves the suspects, so even a large plugin list narrows down in a handful of rounds. Deactivate, don't delete: deleting some plugins also removes their settings and data.

Locked out of the admin? Plugins can be disabled by renaming their folders in wp-content/plugins through hosting file access, or with WP-CLI if your host provides it:

wp plugin list --status=active
wp plugin deactivate --all
wp plugin activate woocommerce contact-form-7

The critical error guide covers recovery mode and the folder-rename method step by step.

Read the evidence: debug log, console and Query Monitor

The PHP debug log

On staging, turn on logging in wp-config.php so errors are written to a file instead of shown to visitors:

define( 'WP_DEBUG', true );
define( 'WP_DEBUG_LOG', true );
define( 'WP_DEBUG_DISPLAY', false );

Reproduce the problem, then open wp-content/debug.log. A fatal error usually names the file and line, and the path tells you the plugin, for example a line containing wp-content/plugins/some-plugin/. "Cannot redeclare" or "Class already declared" errors often mean two plugins bundle the same library. Turn debugging off afterwards; never leave errors displaying on a live site.

The browser console

For buttons, sliders, menus and checkouts that "do nothing", open the broken page, right-click, choose Inspect and open the Console tab. Red errors name the script that failed. A common pattern is one plugin loading its own copy of a library, or an optimisation plugin deferring a script another plugin needs early, so everything after the first error stops running.

Query Monitor

The free Query Monitor plugin shows PHP errors, slow database queries, hooks and the scripts loaded on each page. It is very useful on staging for seeing which plugin is responsible for what.

Theme conflicts

If the problem disappears with a default theme, look at what your theme adds: bundled plugins, custom WooCommerce template overrides, its own sliders or lazy loading, or code in functions.php. Older themes with outdated template files are a frequent cause after a WooCommerce or page builder update. Elementor layout broken after an update covers the builder-specific version of this problem.

Caching and optimisation conflicts

Caching, minification and "combine JavaScript" options cause a large share of front-end breakage, because they change how other plugins' files load. Common signs and fixes:

  • Works when logged in, broken when logged out: administrators are normally served uncached pages, so visitors may be seeing an old file. Purge all caches and recheck.
  • Broke after enabling "delay" or "defer" JavaScript: exclude the affected plugin's script from that option rather than turning optimisation off entirely.
  • Two plugins doing the same job: two caching plugins, or a caching plugin plus host caching with overlapping settings, often clash. Keep one.
  • Cart, checkout or account pages acting oddly: these pages must not be cached; most caching plugins exclude them, but check.

WordPress caching explained describes the layers involved.

Fixing it once you know the pair

  1. Check for updates to both plugins on staging; the conflict may already be fixed.
  2. Roll back the plugin that changed to its last working version, if that is safe and you can get it from the developer.
  3. Change a setting: exclude a script from optimisation, or switch off the overlapping feature in one plugin.
  4. Report it to both developers with your WordPress, PHP, theme and plugin versions (Tools, Site Health, Info lists these), exact steps to reproduce, and the log or console error.
  5. Replace one plugin if it looks abandoned, or if a small piece of custom code would do the job more cleanly; see plugin or custom code.

Preventing the next conflict

  • Update on staging first, one important plugin at a time, and test forms, checkout and key pages afterwards. How to update WordPress safely sets out the order.
  • Keep one plugin per job: one SEO plugin, one caching plugin, one security plugin.
  • Remove plugins you no longer use, rather than leaving them deactivated for years.
  • Choose actively maintained plugins tested with recent WordPress versions.
  • Never install nulled premium plugins: they skip official updates and often carry hidden code.
  • Keep a short log of what was updated and when, so the next problem starts with "what changed?"

FAQs

How do I know which plugin is causing the problem?

Switch to a default theme and deactivate plugins in halves on staging or in Health Check troubleshooting mode until the problem disappears, then narrow down to one. Confirm it in the debug log or browser console, which usually names the file or script.

Can I fix a plugin conflict without deactivating plugins on my live site?

Yes. Use a staging copy, or Health Check troubleshooting mode, which disables plugins only for your logged-in session while visitors see the normal site.

Will deactivating a plugin delete my settings?

Deactivating normally keeps settings. Deleting a plugin can remove its settings and data, so deactivate while troubleshooting and only delete once you are sure.

Why does my site break only for logged-out visitors?

Usually caching or JavaScript optimisation, because logged-in users often bypass the page cache. Purge every cache and test the optimisation settings one by one.

What if the conflicting plugins are both essential?

Check for updates, report it to both developers, and try changing the overlapping setting or excluding a script from optimisation. If nothing works, replace the less important plugin or use a small piece of custom code.
