WordPress File Permissions Explained: 644, 755, wp-config.php, Ownership and How to Fix Permission Errors

WordPress file permissions explained: 644 for files, 755 for folders, 600 or 440 for wp-config.php, why 777 is dangerous and how to fix permission errors.

Key takeaways
  • For most WordPress sites, folders should be 755, files 644 and wp-config.php tighter at 600 or 440 where your host allows it; 777 is never the right answer.
  • Ownership matters as much as the numbers: if WordPress asks for FTP details or cannot create folders, the files usually belong to the wrong user, which chmod 777 does not fix.
  • You can check and reset permissions in cPanel File Manager, an SFTP client such as FileZilla or over SSH, and you should recheck them after a hack or a migration.

The correct WordPress file permissions for most sites are 755 for folders, 644 for files and a tighter 600 or 440 for wp-config.php, with every file owned by your hosting account's user. Those settings let WordPress update itself and save uploads, while stopping other users on the server from changing your files. Never set anything to 777, even when a forum post suggests it as a quick fix.

The rest of this guide explains what the numbers mean, how to check and change them in cPanel, FileZilla or over SSH, and what the common permission errors are telling you. If you'd rather not touch the server yourself, I can check and fix permissions and ownership as part of a WordPress maintenance plan, which starts with a health check of your site.

Permissions are one part of hardening a site, not the whole of it. For the bigger picture, see the WordPress security checklist.

The right values can differ slightly depending on how your server runs PHP, so if your host publishes its own recommendations, follow those.

What 644, 755 and 600 actually mean

Each permission has three digits. The first is for the file's owner, the second for its group and the third for everyone else. Each digit adds up three rights: read is 4, write is 2 and execute is 1.

DigitRightsShown in File Manager or FileZilla as
7Read, write and executerwx
6Read and writerw-
5Read and executer-x
4Read onlyr--
0No access---

So 644 (rw-r--r--) means the owner can read and write while everyone else can only read. 755 (rwxr-xr-x) adds execute, which on a folder means permission to open it and list what's inside. 600 (rw-------) and 440 (r--r-----) shut out everyone except the owner, or the owner and the group.

Ownership matters as much as the numbers

Permissions only make sense alongside ownership. WordPress writes files as whatever user PHP runs as. On most cPanel and similar shared hosts, PHP runs as your own account user, so 644 and 755 already give WordPress all the access it needs.

Problems start when files belong to a different user, which often happens after a migration, a manual upload as the root user, or a VPS where the web server runs as www-data. WordPress then can't write to its own folders, so updates fail, uploads fail, or WordPress asks for FTP connection details every time you install a plugin. Changing permissions to 777 hides the symptom and creates a security hole. The real fix is to give the files back to the right user:

chown -R youruser:youruser /home/youruser/public_html

That needs root access, so on shared hosting ask your host to do it. Some hosting panels include a one-click "fix permissions" or "fix file ownership" tool for exactly this.

How to check and change file permissions

In cPanel File Manager or your host's panel

File Manager shows a Permissions column next to each file. Select a file or folder, choose Change Permissions, tick the boxes or type the number, and save. This is fine for a single file such as wp-config.php, but slow for a whole site.

With FileZilla or another SFTP client

Right-click a file or folder and choose File permissions. For a folder, you can tick "Recurse into subdirectories" and then choose "Apply to directories only" to set 755, and run it again with "Apply to files only" to set 644. Use SFTP rather than plain FTP, so your password isn't sent unencrypted.

Over SSH

If you or your developer have SSH access, these commands, run from the site's root folder, reset everything to the standard values and then tighten wp-config.php:

find . -type d -exec chmod 755 {} +
find . -type f -exec chmod 644 {} +
chmod 600 wp-config.php
stat -c "%a %U %n" wp-config.php

The last line shows the permission number and the owner, so you can confirm the change. If the site shows an error after you tighten wp-config.php, your server needs the web server's group to read it: set it to 640 and ask your host which value they support. To find files and folders that anyone can write to, which should usually return nothing:

find . -perm -o+w -not -type l

Why you should never use 777

777 means read, write and execute for everyone. On shared hosting, "everyone" can include other accounts on the same server and any compromised script running on it. A world-writable folder is an open invitation for malware to drop files into your site, and it is one of the first things attackers look for.

It often doesn't even work. Many servers refuse to run PHP files that anyone can write to, so setting 777 can turn an upload error into a 500 Internal Server Error. If something only works at 777, the real problem is ownership or a server setting, and that's what needs fixing.

Extra hardening for wp-config.php and core files

  • Lock wp-config.php down to 600, 440 or 400 if your host allows it. WordPress also looks for wp-config.php one folder above the site's root, so on some hosts you can move it out of the public folder.
  • Turn off the theme and plugin file editors with DISALLOW_FILE_EDIT, so a stolen admin login can't be used to edit PHP files; see hardening wp-config.php.
  • Block PHP from running in the uploads folder, where only images and documents belong.
  • Don't make all core files read-only. Setting everything to 444 sounds secure, but it breaks WordPress's own updates, and an unpatched site is a bigger risk than writable files.

Check permissions after a hack or a migration

Attackers sometimes set their own files to read-only so they're harder to delete, or open folders up to 777 so they can keep writing to them. Resetting permissions and ownership is part of a proper malware clean-up, after the malicious files themselves are gone.

Migrations are the other common cause. Copying files as the wrong user, or unpacking an archive with its old permissions, leaves a site that loads but can't update or upload. Checking ownership and permissions is a standard step after moving a site; see WordPress migration if you'd like the move handled for you.

File permissions on cPanel and hPanel hosting

On most Indian shared hosting, files uploaded through the host's file manager or SFTP are owned by your account automatically, so the standard 644 and 755 settings work out of the box. Problems usually appear in specific situations.

  • After a restore or migration. Files copied from another server can keep their old permissions. Run a quick check across wp-content after any move.
  • Files created by root on a VPS. If you or a developer ran commands as root, some files may be owned by root and WordPress cannot update them. Fix the owner, not the permission number.
  • Host security tools. Some hosts reject 777 outright and return a 500 error for scripts with loose permissions, which is a good thing.
  • Bulk fixes. cPanel's File Manager can change permissions for one item at a time. For a whole site, ask your host or use SSH carefully, setting folders and files separately.

If you are not comfortable running commands on a live site, note the error, take a backup and ask your host's support or a developer to correct ownership.

FAQs

What are the correct file permissions for WordPress?

755 for folders, 644 for files and 600 or 440 for wp-config.php, with all files owned by your hosting account's user. Some servers need wp-config.php at 640, so follow your host's advice if a stricter value causes an error.

What permission should wp-config.php have?

As strict as your server allows: 600 or 440 on many hosts, 400 on some, and 640 where the web server needs group read access. Never leave it writable by everyone, because it contains your database password.

Should WordPress folders be 755 or 775?

755 by default. 775 lets the group write as well, which a few server setups need when the web server and your account share a group. Use it only if your host recommends it.

Why does WordPress ask for FTP details to install plugins?

Because it can't write to its own files as the user PHP runs as, usually because the files are owned by someone else. Fixing ownership makes the prompt go away. Don't solve it by setting folders to 777.

What permissions does the wp-content/uploads folder need?

755 for the folder and its subfolders, and 644 for the files inside, with the right owner so WordPress can create the year and month folders. If uploads fail at 755, check ownership and disk space rather than opening the folder up.

Is chmod 777 ever okay?

Not on a live website. It lets anyone on the server change the file and is a common way malware spreads. Some servers also refuse to run PHP from world-writable folders, which causes 500 errors.
