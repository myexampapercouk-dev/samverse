Website Security Headers Explained: HSTS, CSP, X-Frame-Options and How to Add Them to WordPress

Security headers explained: what HSTS, CSP, X-Frame-Options, Referrer-Policy and Permissions-Policy do, and how to add them in .htaccess or Cloudflare.

Key takeaways
  • Five headers are quick, low-risk wins: X-Content-Type-Options, X-Frame-Options set to SAMEORIGIN, Referrer-Policy, a simple Permissions-Policy and HSTS once HTTPS works everywhere.
  • Content-Security-Policy is the most powerful and the easiest to get wrong on WordPress, so run it in report-only mode and fix every violation before enforcing it.
  • Add headers in one place, test them with securityheaders.com and your browser, and remember they harden a clean site but never replace updates, 2FA and backups.

Security headers are instructions your server sends with every page, telling the browser to behave more safely: always use HTTPS (Strict-Transport-Security), don't let other sites load this page in a frame (X-Frame-Options or frame-ancestors), don't guess file types (X-Content-Type-Options), share less with other sites (Referrer-Policy), switch off browser features you don't use (Permissions-Policy) and load scripts only from approved places (Content-Security-Policy). Five of them can be added safely in a few minutes; Content-Security-Policy needs testing in report-only mode first.

Headers harden a clean site; they don't fix a hacked one. HSTS: force HTTPS, but only when you're ready

Your site probably already redirects http:// to https://, but that redirect happens after the browser has made an insecure first request. HSTS tells the browser to skip plain HTTP entirely for your domain from then on. It also stops visitors clicking past certificate warnings, which is exactly why you need to be ready before switching it on.

  • Fix HTTPS first. Every page should load securely without mixed content warnings; see fixing mixed content. Your certificate should renew automatically.
  • Be careful with includeSubDomains. It applies HSTS to every subdomain, including old staging sites and mail or shop subdomains. Any without a valid certificate become unreachable in browsers that have seen the header.
  • Ramp up the max-age. Start with five minutes (max-age=300), move to a week (604800), then a year (31536000) once nothing has broken.
  • Think twice about preload. Submitting your domain to the browser preload list at hstspreload.org builds HTTPS-only into browsers themselves. It requires a max-age of at least a year and includeSubDomains, and it takes a long time to undo.

If visitors already see certificate errors, sort those out before adding HSTS; see fixing SSL certificate errors.

X-Frame-Options and frame-ancestors: stop clickjacking

Clickjacking loads your page invisibly inside another site, so a visitor who thinks they're clicking one thing is actually clicking a button on your page. X-Frame-Options stops that. Use SAMEORIGIN on WordPress rather than DENY, because the Customizer and page builders such as Elementor load your own site in a frame to show previews. WordPress already sends SAMEORIGIN on the login page and dashboard; the header extends that protection to the rest of the site.

The modern replacement is the frame-ancestors directive inside Content-Security-Policy. Modern browsers follow frame-ancestors when both are present, so send both for older browsers. If a partner genuinely needs to embed one of your pages, such as a booking form, frame-ancestors can list their domain; X-Frame-Options can't.

X-Content-Type-Options, Referrer-Policy and Permissions-Policy

  • X-Content-Type-Options: nosniff has only one value and rarely causes trouble. If something stops loading afterwards, the server is sending that file with the wrong type, which is worth fixing anyway.
  • Referrer-Policy: strict-origin-when-cross-origin passes the full address within your own site but only your domain name to other sites. Modern browsers already default to it, so setting it simply makes the behaviour consistent. Stricter values such as no-referrer hide your site in other sites' analytics, which matters if partners send you referral reports.
  • Permissions-Policy should list only features you're sure you don't use. Leave geolocation alone if a store finder asks for location, and don't switch off payment if your checkout shows Google Pay or Apple Pay buttons.

Two headers you can skip: X-XSS-Protection, which modern browsers no longer use, and Expect-CT, which is obsolete. Some scanners still mention them.

Content-Security-Policy: powerful, but test it first

A CSP tells the browser which domains may supply scripts, styles, images, fonts and frames. If an attacker injects a script tag that loads code from their own server, as some checkout skimmers do, a good CSP can stop the browser running it. That's the appeal.

The difficulty on WordPress is that core, themes, Elementor and plugins all print inline scripts, and most business sites load third-party code too: Google Tag Manager and GA4, the Meta Pixel, YouTube and Google Maps embeds, reCAPTCHA, payment gateway scripts and WhatsApp or chat widgets. A strict policy written without testing breaks some of them, often a form or the checkout. If reCAPTCHA stops appearing after you add a policy, the Google domains it needs are missing; see fixing reCAPTCHA on WordPress.

  1. Enforce the low-risk directives now. frame-ancestors 'self', object-src 'none', base-uri 'self' and upgrade-insecure-requests don't touch your scripts and are safe on most sites.
  2. Run everything else in report-only mode. The Content-Security-Policy-Report-Only header applies a policy without blocking anything, and the browser console lists what would have been blocked.
  3. Click through every important page over a week or two: the home page, contact and quote forms, the checkout with a test payment, pages with video and maps, and the Elementor editor. Add each legitimate domain to the policy.
  4. Enforce only when the console is quiet, and revisit the policy whenever you add a new tool.

A report-only starting point for a site using Google Analytics, Google Fonts and YouTube embeds might look like this. Your list will differ:

Content-Security-Policy-Report-Only: default-src 'self'; script-src 'self' 'unsafe-inline' https://*.googletagmanager.com; style-src 'self' 'unsafe-inline' https://fonts.googleapis.com; font-src 'self' https://fonts.gstatic.com; img-src 'self' data: https:; connect-src 'self' https://*.google-analytics.com https://*.analytics.google.com https://*.googletagmanager.com; frame-src https://www.youtube-nocookie.com

Be honest with yourself about 'unsafe-inline'. Most WordPress sites need it, and it means injected inline scripts can still run. The policy still blocks scripts from domains you haven't approved, which is a real improvement, but it isn't the strict CSP security guides describe.

How to add security headers

.htaccess on Apache or LiteSpeed hosting

Most shared hosting runs Apache or LiteSpeed, which read the .htaccess file in your site's main folder. Back the file up first, then add this outside the "BEGIN WordPress" block, because WordPress rewrites that section. A typing mistake in .htaccess can take the site down with a 500 error, so check the site straight away and restore the backup if anything goes wrong:

<IfModule mod_headers.c>
  Header always set Strict-Transport-Security "max-age=300"
  Header always set X-Content-Type-Options "nosniff"
  Header always set X-Frame-Options "SAMEORIGIN"
  Header always set Referrer-Policy "strict-origin-when-cross-origin"
  Header always set Permissions-Policy "camera=(), microphone=(), geolocation=()"
  Header always set Content-Security-Policy "frame-ancestors 'self'; object-src 'none'; base-uri 'self'; upgrade-insecure-requests"
</IfModule>

Raise the HSTS max-age in stages once you're confident.

Nginx

On Nginx servers the same headers go in the server block as add_header lines ending in "always". One trap: if a location block has any add_header lines of its own, it stops inheriting the server-level ones, so headers can quietly disappear on some URLs. On managed hosting, ask support to add them.

Cloudflare

If your site runs through Cloudflare, HSTS has its own setting under SSL/TLS, Edge Certificates, and the other headers can be added with a response header transform rule that applies to every request. Menu names change, so check Cloudflare's current documentation. Headers set this way apply to cached pages and static files too; see setting up Cloudflare on WordPress.

A plugin or PHP code

Some security and SSL plugins can add headers from a settings screen. That's convenient, but headers added in PHP have two gaps: static files such as images and scripts never pass through WordPress, and some page caches serve stored pages without running PHP, so the headers can go missing exactly where you expect them. Whatever you choose, set headers in one place only. Duplicates confuse scanners, and two different CSPs both apply, so the stricter combination wins.

How to test your headers

  • securityheaders.com gives a letter grade and lists missing headers. Use it as a checklist, not a target worth breaking the site for.
  • Your browser: open developer tools, go to the Network tab, reload, click the first request and read the Response Headers.
  • The command line: curl -I https://example.com prints the headers for any address.
  • Test several page types: the home page, a cached page, a page with a form and, on a store, the checkout. After Cloudflare changes, purge the cache before testing.

Headers are one layer, not the whole wall

Updates, strong passwords with two-factor authentication, tested backups and a firewall do far more to keep a site safe than any header. Add headers alongside the basics in the WordPress security checklist, not instead of them.

FAQs

Which security headers should a WordPress site have?

Start with X-Content-Type-Options, X-Frame-Options set to SAMEORIGIN, Referrer-Policy and a simple Permissions-Policy, then add HSTS once HTTPS works everywhere. Add a Content-Security-Policy after testing it in report-only mode.

Do security headers help SEO?

Not directly. Google treats HTTPS as a ranking signal, but security headers themselves aren't a ranking factor. They protect visitors and your reputation, which matters more than any ranking boost.

Will a Content-Security-Policy break my WordPress site?

It can, if it's too strict or untested. Analytics, embeds, forms, payment scripts and page builders all need their domains allowed. Running it in report-only mode first shows what would break without breaking it.

Do I still need X-Frame-Options if I use frame-ancestors?

Modern browsers follow frame-ancestors when both are present, but sending X-Frame-Options as well covers older browsers. Use SAMEORIGIN, not DENY, so WordPress previews keep working.

Can security headers stop my site being hacked?

No. They make some browser-based attacks harder, but most WordPress hacks come through outdated plugins and stolen passwords, which headers do nothing about. Treat them as one layer of hardening.
