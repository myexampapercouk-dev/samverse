WordPress Search Not Working? Fixing Missing, Wrong and Slow Results

WordPress search showing no results, the wrong results or loading slowly? See how default search works and fix WooCommerce, page builder and caching causes.

Key takeaways
  • Default WordPress search only looks at titles, content and excerpts with basic ordering, so custom fields, attributes and often SKUs are not found without help.
  • Check WooCommerce catalog visibility, out-of-stock hiding, the search results template's query and the form itself before blaming WordPress, and test with the ?s= address directly.
  • Keep search URLs and live search requests out of page and CDN caches, rebuild search indexes after imports, and use a relevance plugin or a dedicated search engine only when the catalogue needs it.

When site search fails, visitors rarely tell you. They type a product name, see "Nothing found" or a list of unrelated posts, and leave. Search problems usually fall into three groups: no results for things that exist, wrong results, and slow search. Here are the usual causes of each, starting with the checks that cost nothing.

How default WordPress search works

Knowing what WordPress actually does explains most "missing" results:

  • It searches the title, content and excerpt of published posts, pages and other public content types. It doesn't look in custom fields, product attributes, categories, tags or the text inside PDFs
  • It matches what you type fairly literally, with no typo tolerance and only limited handling of different word forms
  • Its ordering is basic: posts with the search words in the title come first, then the rest, newest first. It has no real sense of which result is most useful
  • Drafts, private posts and content types set to be excluded from search don't appear for visitors

A quick test: type your address followed by "/?s=" and a word from a page title, such as "yoursite.com/?s=pricing", into the browser's address bar. If that finds the page but your search box doesn't, the problem is the search form or widget, not WordPress itself.

Products or SKUs not found in WooCommerce

WooCommerce product search builds on the same system, so the same limits apply, plus some store-specific causes:

  • Catalog visibility: each product has a visibility setting in the Publish box. Products set to "Shop only" or "Hidden" won't appear in search results
  • Out-of-stock hiding: if "Hide out of stock items from the catalog" is ticked in the inventory settings, those products vanish from search too
  • SKUs: the admin product search finds SKUs, but depending on your WooCommerce version and theme, the storefront search may not. Variation SKUs are even less likely to be searched
  • Attributes and brands stored only as attributes or custom fields aren't searched by default
  • Mixed results: a general search box can return blog posts and pages alongside products, while a product search form limits results to products

If your buyers search by model or part number, as they often do in B2B and spare-parts stores, plan for SKU search rather than hoping it works.

Page builders, themes and search widgets

Many "search is broken" reports turn out to be the template, not the search:

  • The search results template: with a theme builder such as Elementor Pro, the results page is often a custom archive template. If its posts or loop widget uses its own query instead of the current query, it shows the same posts whatever someone types
  • The form itself: a custom form must send the search term in a field named "s" to your own site. Forms copied from a demo import or another site may point somewhere else
  • Hidden filters: some widgets and themes quietly limit search to one post type or category
  • Theme and plugin code: plugins and themes can change the search query. If results changed after an update, look for a conflict on a staging copy; see how to find plugin conflicts safely

When caching gets in the way

Search results should be built fresh for every query. Many caching plugins don't cache search results by default, but problems appear when:

  • A CDN or server cache is set to cache everything, or to ignore query strings, so different searches return the same cached page
  • A live search box, where results appear as you type, stops working on cached pages because the page holds an expired security token. It works for a while after you clear the cache, then fails again
  • A search plugin's index is out of date, so new or edited products don't show until it's rebuilt

Exclude search URLs and your search plugin's background requests from page and CDN caching, and read the plugin's documentation on caching. See WordPress caching explained for what should never be cached.

Fixing slow search

Default search runs a fresh database query that has to check the text of every published post, page and product for a match, and it can't use the shortcuts the database uses for most WordPress queries. On a large site that gets slow, and every search bypasses the page cache. Things that help:

  • Use a search plugin that builds its own index instead of scanning content on every search
  • Make live search wait until the visitor has typed a few characters, so it isn't querying on every keystroke
  • Watch for bots hammering search URLs with spam terms. A firewall rate limit helps, and search results pages should be set to noindex, which most SEO plugins do

For online stores, search is one part of overall store speed; see WooCommerce speed optimization.

Better relevance with a search plugin

If the basics are fixed and results are still poor, a dedicated search plugin is the usual next step. Well-known options include Relevanssi and SearchWP, which build their own index and can search custom fields and weight title matches above body text, and FiboSearch, a live product search for WooCommerce. Features differ between free and paid versions and change over time, so check current details and test on a staging copy with your real content.

For very large catalogues, or instant search across many thousands of products, sites move search off the WordPress database to a dedicated search engine. Common routes are Elasticsearch through a plugin such as ElasticPress, or a hosted search service. These add running costs and setup work, so they're usually worth it only when the catalogue and traffic justify them. For synonyms, Hinglish terms and fixing zero-result searches, see how to improve site search on WordPress.

Track what visitors search for

Search terms show what people expected to find. GA4's enhanced measurement can record site searches when the term appears in the page address, and WordPress's standard "s" parameter is one it looks for by default. Searches are recorded as a view_search_results event, and an Exploration report is usually the easiest place to read the terms. Live search boxes that never load a results page may not be captured.

Many search plugins also keep their own log, including searches that returned nothing. That's the most useful list of all: each zero-result search is a missing synonym, a product search can't find, or a gap in what you offer. Review it monthly.
