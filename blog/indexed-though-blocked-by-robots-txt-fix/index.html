"Indexed, Though Blocked by robots.txt" and "Blocked by robots.txt": What They Mean and How to Fix Them

What Search Console's "Indexed, though blocked by robots.txt" and "Blocked by robots.txt" mean, when to use noindex instead, and how to fix and validate them.

Key takeaways
  • Robots.txt controls crawling, not indexing, so a blocked URL can still be indexed from links, and a noindex tag on a blocked page is never seen.
  • Common WordPress causes are SEO plugin robots.txt edits, a physical file overriding the virtual one, leftover staging rules, blocked wp-content or CSS and JavaScript, and broad parameter rules.
  • Fix the rule in one place, confirm the live file, use the robots.txt report and URL Inspection, then click Validate fix and allow days or weeks.

Two statuses in Search Console's Pages report cause a lot of confusion: "Blocked by robots.txt" and "Indexed, though blocked by robots.txt". The second sounds like a contradiction. How can Google index a page it isn't allowed to visit? The answer explains both statuses, and tells you whether you need to fix anything. If robots.txt itself is new to you, start with robots.txt explained; for the other statuses in the report, see Search Console page indexing errors.

What the two statuses mean

  • Blocked by robots.txt: Google found the URL, your robots.txt told it not to crawl the page, and the URL isn't indexed. That's correct for admin, cart and account URLs. It's a problem when service pages, products or blog posts appear in the list.
  • Indexed, though blocked by robots.txt: Google still isn't allowed to crawl the page, but it has added the URL to its index anyway, usually because links point to it. Because Google can't read the page, the search result often appears with no proper description. Search Console treats this as a warning on indexed pages rather than an error.

Robots.txt blocks crawling, not indexing

Robots.txt asks crawlers not to fetch certain URLs. It doesn't tell Google to keep those URLs out of search results. If other pages link to a blocked URL, Google can index the address based on those links alone.

The key detail: Google only sees a noindex tag when it crawls the page. Block a page in robots.txt and add noindex, and the noindex is never read. Google also doesn't support noindex rules written inside robots.txt. So choose the tool by what you actually want:

GoalUse
Keep a page out of search resultsA noindex meta tag (or an X-Robots-Tag header for PDFs), with crawling allowed
Remove a page for goodDelete it so it returns 404 or 410, or 301 redirect it to the closest relevant page
Keep content privateA password or login; robots.txt is public and secures nothing
Stop Google wasting crawling on endless low-value URLsA robots.txt Disallow rule
Hide a URL from results urgentlySearch Console's Removals tool, which is temporary, plus one of the permanent fixes above

First decide: should these URLs be in Google?

Click each status and look at the example URLs.

  • Important pages in either status: remove the rule that blocks them. This is the urgent case.
  • Low-value URLs under "Blocked by robots.txt": usually fine. Leave them.
  • Low-value URLs under "Indexed, though blocked": often harmless, because these results rarely show for real searches. If you want them gone, allow crawling, add noindex and stop linking to them. Once URL Inspection shows they've dropped out, you can decide whether to block them again.

Common WordPress causes

  • An SEO plugin's robots.txt editor: rules added there, sometimes from old advice or a copied template. Depending on the plugin, edits change WordPress's virtual file or write a real one.
  • A physical file overriding the virtual one: WordPress only generates robots.txt when no real file exists. If a robots.txt sits in the site's root folder, the server sends that instead, and changes made in WordPress may never appear. Some hosts and CDNs can also add rules of their own, for example for AI crawlers, so always check the live file.
  • Staging rules left in: a Disallow: / written for a staging copy and carried over at launch. Staging sites are better protected with a password.
  • Blocking /wp-content/, /wp-includes/ or CSS and JavaScript: old advice that stops Google rendering pages properly. Blocking /wp-content/ also blocks your images in /wp-content/uploads/ from image search.
  • Parameter and filter URLs: rules for sort orders, internal search (?s=), add-to-cart links or WooCommerce filter URLs. Sensible in moderation, but a broad rule such as Disallow: /*? blocks every URL containing a question mark, including every post on a site still using "Plain" permalinks. URLs that were indexed before a rule was added often move to "Indexed, though blocked". For planning filters, see WooCommerce product filters.

Google supports the * and $ wildcards, paths are case-sensitive, and when an Allow and a Disallow rule both match, the more specific (longer) rule wins. A simple WordPress file often needs little more than this:

User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php

Sitemap: https://www.example.com/sitemap.xml

Use your own sitemap address, which depends on your SEO plugin.

Testing with Search Console

Tools change, so treat these menu names as a guide rather than gospel:

  • Open the live file: visit yourdomain.com/robots.txt in a private window. Each host has its own file, so check the version your site actually uses, with or without www.
  • Robots.txt report: in Settings, the robots.txt report shows the files Google found, when it last fetched them and any problems. It also lets you ask Google to recrawl the file after an urgent fix. The older robots.txt Tester has been retired.
  • URL Inspection: inspect an affected URL. The crawl details show whether robots.txt blocked it, and Test live URL checks against your current file.

Google generally caches robots.txt for up to a day, so a fix may not register instantly. If robots.txt returns a server error, Google may slow or pause crawling of the whole site; a 404 is simply treated as having no rules.

Fix it and validate

  1. Copy your current robots.txt somewhere safe before editing.
  2. Edit the rule in one place only: the physical file or your SEO plugin, not both.
  3. Clear your site and CDN caches, then reload the live file to confirm the change.
  4. In the robots.txt report, request a recrawl if the fix is urgent.
  5. Run an important URL through URL Inspection, use Test live URL, then request indexing.
  6. Open the status in the Pages report and click Validate fix where it's offered. Validation can take days or weeks.

If you chose the noindex route, expect URLs to move to "Excluded by 'noindex' tag" over time. Don't add the block back until they have.
