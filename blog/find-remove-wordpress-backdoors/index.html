How to Find and Remove Backdoors in a Hacked WordPress Site: Where They Hide and How to Check

Find and remove WordPress backdoors: where they hide, from uploads and mu-plugins to .user.ini, cron and rogue admins, and the WP-CLI checks to find them.

Key takeaways
  • A backdoor is hidden code or access that lets an attacker back in after a cleanup, and a missed one is the usual reason malware returns days later.
  • Check core and plugin files against official checksums, then look where backdoors hide: PHP in uploads, mu-plugins, fake plugins, wp-config includes, .htaccess and .user.ini, cron jobs, rogue admins and the database.
  • Remove every backdoor in one session, replace files rather than editing them, then change all passwords and salts, or the attacker simply uses the one you missed.

A backdoor is anything an attacker leaves behind so they can get back in after you've cleaned up: a small PHP file that runs commands, a hidden admin account, a cron job that reinstalls malware, or a setting that loads their code before WordPress starts. To find them, compare core and plugin files with the official checksums, look for PHP files where they don't belong, check wp-config.php, .htaccess and .user.ini for files loaded automatically, list recently changed files, search for obfuscated code, and review users, scheduled tasks and the database. Then remove them all at once and change every password.

What a WordPress backdoor looks like

Backdoors are usually small and designed to look boring. A few lines added to a genuine file are harder to spot than a big, obviously malicious script.

TypeWhat it doesWhere it usually sits
Code runnerRuns whatever PHP the attacker sends in a request or cookieA one-line addition to a theme, plugin or core file
Uploader or web shellA hidden file manager for uploading, editing and deleting filesA PHP file in uploads, a fake plugin or a random folder
Admin creatorCreates an administrator when a secret address is visitedA mu-plugin, functions.php or a fake plugin
Auto-loaderLoads the attacker's file before every pagewp-config.php includes, .htaccess or .user.ini
ReinfectorDownloads the malware again on a scheduleHosting cron jobs or WordPress scheduled events
Access left openLets them log straight back inHidden admin users, extra SFTP accounts, SSH keys, application passwords

Where WordPress backdoors hide

PHP files in wp-content/uploads

Uploads should hold images, PDFs and other media. A PHP file here is almost always malicious, whatever its name. Watch for disguises such as image.jpg.php, an index.php inside a year folder, or a file with an icon or image extension that another file includes.

The mu-plugins folder

Must-use plugins in wp-content/mu-plugins load on every request, can't be deactivated from the dashboard and appear only under a separate Must-Use tab. Some managed hosts add their own files here, so check names against your host's documentation before deleting anything.

Fake and modified plugins

Look for plugin folders you didn't install, often with names that sound like caching, SEO or security tools. Some malware hides itself from the Plugins screen, so compare the folders in wp-content/plugins with the list in your dashboard. Genuine plugins and themes can also have a few malicious lines added to an existing file, typically the theme's functions.php.

wp-config.php and core files

Check the very top and bottom of wp-config.php for extra code or an include of an odd file, often with an image or icon extension. Core files in wp-admin and wp-includes should never change except during an update, so any modification there is serious.

.htaccess, .user.ini and auto_prepend_file

PHP has a setting called auto_prepend_file that loads a chosen file before every PHP request. Attackers set it in .htaccess on Apache servers, or in a .user.ini or php.ini file on servers running PHP-FPM, and point it at their own script. Because it runs before WordPress, nothing in the dashboard shows it. A malicious line looks like this:

auto_prepend_file = "/home/account/public_html/wp-content/uploads/2024/05/.cache.php"

One legitimate use is common: Wordfence's firewall, in its extended protection mode, sets auto_prepend_file to a file called wordfence-waf.php in your site's root. Anything pointing into uploads, a hidden file or a random folder is not legitimate. Check .htaccess files in subfolders too, not only the root.

Cron jobs and scheduled events

Check Cron Jobs in your hosting control panel for commands you didn't create, especially ones that download files with wget or curl. Then list WordPress scheduled events and look for hooks you can't connect to any plugin you use.

Users and other access

Hidden administrators are common. So are application passwords added to a genuine admin account, extra SFTP or FTP accounts, SSH keys and hosting sub-users. All of them survive a file cleanup.

The database

Some backdoors store their code in wp_options, widgets or post content, with a tiny file elsewhere that reads and runs it. Others grant admin rights by editing user metadata directly. Cleaning files alone won't remove these.

How to find backdoors, step by step

These steps assume SSH access and WP-CLI, which many hosts offer. Run them from the site's root folder after taking a full backup of the infected site. The next section covers what to do with File Manager only.

1. Verify core and plugin files

wp core verify-checksums
wp plugin verify-checksums --all

Both compare your files with the official copies on WordPress.org and list anything modified or extra. The plugin check only works for plugins from WordPress.org, and WP-CLI has no equivalent for themes, so reinstall premium plugins and all themes from the vendor or the official directory.

2. Look for PHP where it shouldn't be, and for auto-loaded files

find wp-content/uploads -type f -name "*.php"
ls -la wp-content/mu-plugins
find . -name ".user.ini" -o -name "php.ini"
grep -rln "auto_prepend_file" --include=".htaccess" --include="*.ini" .

3. List recently changed files

find . -type f -name "*.php" -ctime -14 -not -path "./wp-content/cache/*"

Attackers can fake a file's modified date, which is what most file managers show. The ctime used here records when the file's details last changed and can't be backdated as easily. Widen the window until it covers the date the problem started.

4. Search for obfuscated code

grep -rlE "base64_decode|gzinflate|str_rot13" --include="*.php" .
grep -rlF "eval(" --include="*.php" .

Backdoors often hide their real code behind functions such as eval, base64_decode, gzinflate and str_rot13, usually next to a long random-looking string or data taken from the request. Genuine plugins use some of these too, so expect matches and judge each by context: a file in uploads, or a single line hundreds of characters long, is suspicious; a well-known plugin's library file usually isn't.

5. Check users, application passwords and scheduled events

wp user list --role=administrator --fields=ID,user_login,user_email,user_registered
wp cron event list

Compare the administrator count with the number shown in the dashboard; a hidden account makes them differ. Open each admin's profile and check the Application Passwords section for entries nobody recognises. The WordPress user account audit explains what each person should have.

6. Search the database

wp db search "base64_decode" --all-tables
wp db search "eval(" --all-tables

7. Read the access logs

Requests that send data (POST requests) to odd PHP files, especially in uploads or plugin folders, often show a backdoor being used. The earliest of them can point to the request that planted it, and so to the entry point.

No SSH? Checking with File Manager

  • Sort folders by last modified date and open anything changed around the time the problem began
  • Browse wp-content/uploads year by year for anything that isn't media
  • Open wp-config.php, .htaccess and mu-plugins and read them in full
  • Run a security plugin scan, which compares files with the repository copies; WordPress malware scanners compared explains what scanners can and can't see
  • Ask your host for its malware scan report and access logs

How to remove backdoors safely

  1. Back up the infected site first and label it, so nothing real is lost and you can study how the attack worked.
  2. Remove everything in one session. Taking one backdoor out a day warns the attacker, who simply uses another.
  3. Replace rather than edit. Reinstall core, plugins and themes from clean sources instead of cutting lines out of infected files.
  4. Delete the access as well as the code: rogue users, application passwords, cron jobs, SFTP accounts and SSH keys.
  5. Then change every password and the salts in wp-config.php, from a device you trust. Doing this after the cleanup matters, because a working backdoor lets the attacker see new passwords.
  6. Close the way in: update everything, remove nulled software and turn off file editing; see hardening wp-config.php.

If the account holds several neglected sites, or you can't tell what is genuine any more, a fresh WordPress install with only your content and media copied across (no PHP files) can be quicker and safer than cleaning file by file.

Afterwards, block PHP in uploads, keep an activity log and turn on file-change alerts, so a new backdoor gets noticed in days rather than months. The WordPress security checklist covers the rest of the hardening.

FAQs

What is a backdoor in WordPress?

Hidden code or access that lets an attacker get back into your site without your password, such as a small PHP file, a hidden admin user or a scheduled task that reinstalls malware.

Can a security plugin find backdoors?

Some, especially known ones and modified WordPress.org files. Scanners often miss backdoors in the database, in premium plugin files they can't compare, in .user.ini files or in custom code that doesn't match a known signature. Treat a scan as one check, not the only one.

Why does malware keep coming back after I clean it?

Usually because a backdoor, a rogue account or a cron job was missed, the original hole was never closed, or another site in the same hosting account reinfected yours.

Is base64_decode always malicious?

No. Plenty of genuine plugins use it to handle images, data or licence keys. It is suspicious when it sits in an unexpected file, decodes a long random string and passes the result straight to something that runs code.

Should I change passwords before or after removing backdoors?

Both. Change the hosting password straight away to slow the attacker down, then change every password and the salts again once the backdoors are gone, because a working backdoor can capture new ones.
