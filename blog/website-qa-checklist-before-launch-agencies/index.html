Website QA Checklist for Agencies: A Real Testing Process for Functionality, Forms, Devices, Speed, SEO, Accessibility, Redirects, Analytics, Backups and Sign-off

A website QA process for agencies: test passes for forms, devices, browsers, speed, SEO, redirects, accessibility, analytics and backups, then sign-off.

Key takeaways
  • Run QA as a series of focused passes on staging, each with its own checklist, rather than one long click-around the day before the client review.
  • Log every issue with page, device, expected result and severity, and agree in advance which severities block a review or a launch.
  • Finish with a written sign-off that lists what was tested, what is known and deferred, and who approved it.

A dependable QA process for an agency website is a set of focused test passes run on staging by someone other than the builder: functionality, forms and integrations, devices and browsers, performance, SEO and redirects, accessibility, analytics, and backups. Each pass has its own checklist, every issue goes into one log with a severity, fixes are retested, and the round ends with a written sign-off. Done this way, the client review is about content and feel, not broken buttons.

I run this kind of process on white-label builds before handing them back, as described on the WordPress developer for agencies page, but it works just as well for in-house teams. It complements the website launch checklist, which covers the go-live steps themselves.

Where QA sits in the project

QA is not one moment. It is a series of gates, each with a clear owner and a pass condition.

GateWhenWhoPasses when
Developer self-testBuild marked completeThe developerEvery template loads, forms submit, no console errors
Internal QABefore the client sees stagingDesigner and project managerNo blockers or majors open
Client reviewAfter internal QAClient, through the agencyContent and design approved in writing
Pre-launch checkDay before go-liveProject managerRedirects, analytics, backups and access ready
Post-launch smoke testWithin an hour of go-liveDeveloper and project managerLive forms, tracking and key pages confirmed

Internal QA should happen on a password-protected, noindexed copy of the site; staging sites explained covers the setup.

Prepare before anyone tests

  • A test matrix: the devices and browsers agreed in the proposal, so testing has a defined end
  • The approved designs at each breakpoint, and the sitemap with final URLs
  • Test data: sample names, a test email inbox, a test phone number, and the payment gateway's test mode details if there is a store
  • The redirect map, if this is a redesign
  • One shared issue log, set up before testing starts

Pass 1: Functionality

  • Every menu item, footer link and button goes where it should; no links point at the staging domain or to "#"
  • Mobile menu opens, scrolls and closes; sticky headers do not hide content
  • Accordions, tabs, sliders, pop-ups and modals open, close and work with the keyboard
  • Site search returns sensible results and has a helpful empty state
  • The 404 page exists and helps visitors find their way
  • Blog, archive, category, single post and legal page templates all render correctly, not just the homepage
  • No placeholder text, demo images or lorem ipsum left anywhere
  • Favicon and social sharing image appear

Pass 2: Forms and integrations

Forms are where client trust is lost fastest, because a broken one quietly loses leads. Test each one, not a sample.

TestExpected result
Submit with valid dataSuccess message or thank-you page; notification reaches the right inbox, not spam
Submit with a field empty or wrongClear error next to the field; other entries kept
Phone with spaces or +91Accepted, or a helpful message
AutoresponderArrives, with correct branding and reply-to
CRM, sheet or email list connectionEntry appears with fields mapped correctly
Spam protectionPresent, and does not block real submissions
Payments or bookings in test modeSuccess, failure and cancellation each handled, with the right emails
Click-to-call, WhatsApp and email links on a phoneOpen the right app with the right number or address

Note which notification addresses will change at launch, and add switching them to the pre-launch list.

Pass 3: Devices, browsers and builder checks

Agree the matrix in the proposal so testing is finite. A typical one for Indian and UK audiences looks like this:

EnvironmentPriorityWhat to look for
Android phone, ChromeMust passLayout, tap targets, forms, speed on mobile data
iPhone, SafariMust passSticky elements, video, date fields, font rendering
Desktop Chrome and EdgeMust passWide-screen layout, hover states
Desktop Safari and FirefoxShould passSpacing and font differences
Tablet, portrait and landscapeShould passThe breakpoint most often forgotten

Also resize a desktop browser slowly from wide to narrow. Layouts often break between the designed widths, not at them.

Extra checks on Elementor builds

  • Colours and typography come from global styles, not set widget by widget
  • Elements hidden on mobile are not heavy sections still loading in the background
  • Tablet and any custom breakpoints were reviewed, not only desktop and mobile
  • Theme Builder conditions apply the right header, footer and templates to every page type
  • No unused add-on plugins left active

Builds that need this cleaned up are the kind of work covered under Elementor development.

Pass 4: Performance

  • Run the homepage and one of each main template through Lighthouse (PageSpeed Insights cannot reach a password-protected staging site)
  • Check the largest image on each template is sized and compressed for its slot
  • Count font families and weights, and question every one beyond what the design needs
  • List third-party scripts: chat, heatmaps, embeds, and confirm each is wanted
  • Note that staging may lack the live server's caching and CDN, so recheck after launch

Pass 5: SEO and redirects

  • Unique title and meta description on each key page
  • One H1 per page; headings follow structure, not font size
  • Meaningful alt text on informative images
  • URLs match the agreed sitemap
  • Staging is noindexed now, and removing that is on the launch list
  • Canonical tags point to the live domain once launched, not to staging

Testing the redirect map

For a redesign, every important old URL needs a permanent redirect to its closest new page. Test from a list, not from memory: paste each old URL, confirm it lands on the intended new page in one hop, and mark it in the sheet. Look out for chains and for redirects to the homepage that should go somewhere specific. 301 vs 302 redirects explains which type to use.

Pass 6: Accessibility

  • Tab through each template: focus visible, nothing trapped, menus and forms usable
  • Text and button contrast checked, especially text over images
  • Every form field has a visible label
  • Link text makes sense out of context
  • Page usable at 200% zoom

For a fuller review, use the website accessibility audit checklist.

Pass 7: Analytics and consent

  • The correct GA4 property, Meta Pixel and ad tags are present, or ready to switch on at launch
  • Key events fire once each: form submissions, calls, WhatsApp clicks, purchases; check in debug view
  • Staging visits are excluded from live reports
  • If there is a consent banner, tags respect the visitor's choice

If event names and parameters are new to your team, GA4 events explained is a short primer.

Pass 8: Backups, access and recovery

  • Automatic backups configured on the live host, stored off the server, including the database
  • A restore tested at least once, on staging
  • Admin accounts personal, with strong passwords; no shared "admin" login
  • Premium licences registered to the client, with renewal dates recorded
  • Domain, hosting and DNS access documented for whoever maintains the site

Backup tools differ in how they handle restores; WordPress backup plugins compared covers the trade-offs.

Logging, severity and retesting

Each issue needs page URL, device and browser, a marked-up screenshot, what you expected and what happened. Then a severity, agreed in advance:

SeverityExampleRule
BlockerContact form sends nothing; checkout failsStops client review and launch
MajorMobile menu will not close; layout broken on iPhoneFixed before client review
MinorSpacing differs from design on tabletFixed before launch
PolishHover colour slightly offFixed if time allows, or listed for later

Mark anything outside the agreed scope as a change request rather than a bug; bug vs change request helps draw that line. Send issues to the developer in one batch, retest each fix, and close it only after retesting.

Sign-off

End the round with a short written record, kept with the project:

  • Date, staging URL and build version tested
  • Which passes were completed, and on which devices
  • Open issues, each marked deferred or accepted, with a reason
  • Name of the person signing off internally, and later the client's written approval

When the project then moves to the client or a maintenance team, the agency developer handoff checklist covers what to pass on.

FAQs

How long should website QA take?

It depends on the number of templates, forms and integrations. A brochure site with a few templates is much quicker than a store with payment and shipping flows. Plan a fix-and-retest round before the client review date, not after it.

Should the developer do QA on their own work?

They should self-test, but internal QA works best when someone else does it. Builders tend to follow the path they built and miss the odd ones visitors take.

Which browsers should we test?

Whatever is agreed in the proposal. At minimum, Chrome on Android and Safari on iPhone, plus a desktop browser or two. Check your client's analytics for what their visitors actually use.

Can QA be automated?

Partly. Link checkers, uptime monitors and accessibility scanners catch some issues. Forms, layouts and real-device behaviour still need a person.

What if the client finds bugs after sign-off?

Log them in the same sheet with the same severities. The sign-off record shows what was tested, which makes it easier to agree whether something is a bug or a new request.
