WordPress XML-RPC Explained: Should You Disable xmlrpc.php?

What xmlrpc.php does, what still uses it, how to spot attacks in your logs, and safe ways to disable or restrict XML-RPC in WordPress without breaking anything.

Key takeaways
  • XML-RPC is an older remote-access feature that most business sites no longer need; Jetpack, some apps and pingbacks are the main things that may still use it, and the REST API has replaced it for most jobs.
  • Floods of POST requests to xmlrpc.php in your access logs, slowdowns or resource-limit errors are signs that bots are using it for password guessing that can bypass login protection.
  • Block it at the server or firewall to save resources, or switch it off with a security plugin or code snippet, then test Jetpack, apps and connected services; restrict instead of blocking if something needs it.

If you've looked at your security plugin's reports or your hosting logs, you may have noticed a file called xmlrpc.php being hit again and again. It's a part of WordPress that most business sites no longer use, yet it's switched on by default and bots love it. Here's what it is, how to tell whether anything on your site still relies on it, and how to switch it off or restrict it safely.

The short answer: if nothing on your site uses XML-RPC, which is true for most business sites that don't use Jetpack or publish from an app, block it at the server or firewall, or at least turn it off with a security plugin. If you do rely on Jetpack or a publishing app, restrict it rather than blocking it outright.

What xmlrpc.php actually is

XML-RPC is an older way for other programs to talk to your WordPress site remotely: publishing posts, uploading images, reading comments and so on, by sending XML messages to a single file, xmlrpc.php, in your site's main folder. It dates from the days when people wrote blog posts in desktop apps and sent them to their site, and it has been enabled by default in WordPress for many years.

Today, most of that work is done by the WordPress REST API, a newer system used by the block editor and most modern plugins and apps. XML-RPC is still included for backwards compatibility, which is why it sits on almost every WordPress site, used or not.

To see whether it responds on your site, open yoursite.com/xmlrpc.php in a browser. If you see the message "XML-RPC server accepts POST requests only.", the file is reachable. A 403 or 404 page usually means something already blocks it. Note that some plugin settings switch off XML-RPC features inside WordPress while the file still shows that message.

What still uses it

  • Jetpack: the Jetpack plugin has historically relied on XML-RPC to connect your site to WordPress.com for features such as stats, backups and downtime monitoring. It has moved parts of that connection to the REST API, but blocking xmlrpc.php completely can still break it, so check Jetpack's current documentation first.
  • Some mobile and desktop apps: older versions of the WordPress mobile app, and some third-party blogging or publishing tools, use XML-RPC to log in and publish. Newer app versions can connect through the REST API instead, but setups vary, so test any app you use.
  • Pingbacks: the automatic notifications one WordPress blog sends another when it links to it travel over XML-RPC.
  • Older integrations: a few auto-posting and remote management services still use it.

The block editor, WooCommerce, contact forms and most modern plugins don't need XML-RPC at all.

Why attackers like it

Password guessing at scale

XML-RPC accepts a username and password with each request, so bots treat it as a second login page. A method called system.multicall lets one request carry many calls at once, which attackers have used to try many passwords in a single request. Recent WordPress versions have reduced how far a single request can be abused this way, but xmlrpc.php remains a favourite target, and every request still loads WordPress and uses server resources. On budget shared hosting, a steady flood of these requests can slow the whole site.

There's another catch: some login protection, such as attempt limits, CAPTCHAs or two-factor authentication, only covers the normal wp-login.php page. Unless your security setup also covers XML-RPC, it can be a side door around those defences. The steps in how to secure your WordPress login work best when this side door is closed too.

Pingback abuse

The pingback feature makes your server send a request to whatever address it's asked to check. Attackers have abused this to get large numbers of WordPress sites to flood a victim with traffic, and to reveal a site's real server address when it's hidden behind a firewall or CDN. Your site ends up as a tool in someone else's attack, on your server's resources.

How to tell whether xmlrpc.php is being attacked

Bots try xmlrpc.php on almost every WordPress site, so its appearance in your logs isn't proof of a problem; volume and impact are what matter. Warning signs:

  • Large numbers of POST requests to /xmlrpc.php in your access logs, often from many different IP addresses
  • Slowdowns, 503 errors or "resource limit reached" pages on shared hosting, or CPU spikes in your hosting dashboard while real visitor numbers are normal
  • Security plugin alerts about failed logins when nobody has used the login page

In cPanel, raw access logs are usually under Metrics; other hosts have a log viewer in their dashboard. A bot request looks something like this (the IP address is an example):

203.0.113.45 - - [10/Oct/2026:02:14:07 +0530] "POST /xmlrpc.php HTTP/1.1" 200 412

A 200 status means WordPress processed the request. Once you block the file, the same requests should show 403, meaning they were refused. With SSH access, a developer can count requests per IP address to see whether it's a handful of bots or a large distributed attack:

grep "POST /xmlrpc.php" access.log | awk '{print $1}' | sort | uniq -c | sort -rn | head -20

Steady requests from one recognisable source, such as Jetpack's servers or a service you use, suggest something genuine depends on XML-RPC. Your security plugin's traffic or login log, or an activity log, can show the same pattern without touching server files; see WordPress activity logs.

How to check whether you need it

  1. Check your plugins: is Jetpack installed and connected? Does any other plugin describe a connection to an external service or app?
  2. Ask how content gets published: does anyone post from a mobile app, a desktop editor or an automation tool rather than the dashboard?
  3. List external services that publish to, back up or monitor your site, and check their documentation for XML-RPC requirements.
  4. Look at your access logs as described above: random IP addresses are bots, a known service is genuine.

For a typical brochure site, clinic site or WooCommerce store without Jetpack, the answer is usually that nothing needs it.

Safe ways to disable or restrict XML-RPC

Option 1: a security plugin setting

Most well-known WordPress security plugins include an option to disable XML-RPC entirely, or to switch off just its login methods or pingbacks. This is the easiest route for most site owners, and it's easy to reverse. Option names vary, so check your plugin's documentation.

Option 2: a code snippet

Developers sometimes add this filter in a small site-specific plugin:

add_filter( 'xmlrpc_enabled', '__return_false' );

Know its limits: it switches off the XML-RPC methods that need a username and password, which stops password guessing through xmlrpc.php, but pingbacks still work and every request still loads WordPress. It's a reasonable step, not a full block.

Option 3: a server rule

Blocking xmlrpc.php before WordPress loads saves the most server resources, because bot requests are refused without running any PHP. On Apache or LiteSpeed hosting, a developer can add a rule like this to the .htaccess file:

<Files xmlrpc.php>
  Require all denied
</Files>

Nginx servers use an equivalent location rule. A mistake in .htaccess can take the whole site offline, so take a backup first (see the backup and restore guide) or ask your developer. If a rule ends up blocking more than intended, 403 Forbidden errors on WordPress explains how to trace it.

Option 4: your host or a cloud firewall

Cloud firewalls such as Cloudflare let you block or challenge requests to the /xmlrpc.php path before they reach your server at all, which is the best option when bot traffic is heavy. Some managed WordPress hosts block or rate-limit xmlrpc.php by default, and others will add a block on request. See WordPress firewalls explained for how these layers fit together.

Option 5: restrict rather than block

If you use Jetpack or an app that needs XML-RPC, it doesn't have to be all or nothing. You can disable pingbacks only, rate-limit xmlrpc.php at the firewall, or allow only the services you rely on, such as Jetpack's published IP addresses. Check Jetpack's current documentation before restricting anything, since its requirements can change.

Test afterwards

  • Open the website and the dashboard, and save a test draft
  • Check Jetpack's connection status, if you use it, and try any app or tool that publishes to your site
  • Confirm that backup, monitoring and auto-posting services still report normally over the next few days
  • Watch your logs: requests to xmlrpc.php should now be refused before they reach WordPress

If something stops working, undo the change and switch to restricting instead of blocking.

The REST API: XML-RPC's modern replacement

The WordPress REST API does most of what XML-RPC was built for. It's what the block editor uses to save your pages, and what most current plugins, apps and integrations use to talk to WordPress. It also handles app logins more safely: external tools can use application passwords, built into WordPress since version 5.6, which work only for API requests, can be revoked one at a time and never expose your main password. XML-RPC tools, by contrast, typically send your real username and password.

That's why you shouldn't disable the REST API along with XML-RPC, as some guides suggest. The block editor, WooCommerce and many plugins depend on it, and turning it off completely can break your dashboard and checkout. Restricting parts of it, such as the public user list, is a separate, more delicate job; see the WordPress REST API explained.

One small step in a bigger picture

Disabling XML-RPC reduces bot noise and closes a side door, but it won't protect a site with outdated plugins or weak passwords. Treat it as one item alongside updates, two-factor authentication, backups and a firewall, as in the WordPress security checklist. And if bots hammering xmlrpc.php make you suspect someone has already got in, work through the guide to finding and removing backdoors.

FAQs

Is xmlrpc.php a virus or a sign of a hack?

No. It's a standard WordPress core file found on almost every WordPress site, and requests to it only mean bots are knocking. Unfamiliar PHP files with odd names in other folders are a different matter and worth investigating.

Can I just delete xmlrpc.php?

It's better not to. It's a core file, so WordPress updates will put it back. Blocking it with a server rule, firewall or plugin is cleaner and easy to undo.

Does disabling XML-RPC affect SEO?

No. Google doesn't use xmlrpc.php to crawl or index your site. Pingbacks have no real SEO value for a business site; you can switch them off under Settings > Discussion, and see whether a business site should enable comments.

Why do I still see xmlrpc.php requests after disabling it?

Bots don't check first. What changes is the response: requests should now get a 403 or an error instead of being processed. To stop them reaching your server at all, block the path at a cloud firewall.
