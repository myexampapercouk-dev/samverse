Why Is My WordPress Site Slow? 12 Common Causes and How to Fix Them

WordPress site slow? Diagnose it in 5 minutes with free tools, then fix the 12 most common causes, plus a slow admin, slow mobile pages and slow WooCommerce.

Key takeaways
  • Diagnose before fixing: PageSpeed Insights, browser DevTools and Query Monitor show whether hosting, plugins, the theme, images, scripts or the database is the bottleneck.
  • Slow hosting, missing caching and oversized images are the usual culprits, followed by heavy themes, page builders, plugins and third-party scripts.
  • A slow admin, a slow WooCommerce store or a site that slowed after an update each have specific causes, so back up and test fixes on staging.

A slow WordPress site loses visitors before they've read a word, especially on mobile data, and speed is part of Google's page experience signals. The good news: WordPress itself isn't slow. Most slow sites share the same handful of problems, and once you know which one you have, the fix is usually straightforward.

Start with the 5-minute diagnosis below, then work through the 12 common causes in order of impact. There are also specific fixes for slow mobile pages, a slow admin, a site that slowed down after an update and a slow WooCommerce store.

The short answer

A slow WordPress website is almost always down to one or more of these:

  • Hosting: the server is slow to build and send each page
  • Plugins: too many, or one badly built plugin doing heavy work
  • Theme or page builder: bloated code and complex layouts
  • Images: large, uncompressed photos and sliders
  • Third-party scripts: chat widgets, tracking pixels and embeds
  • The database: years of leftover data slowing every query

A missing or broken page cache makes all of these worse. Don't guess which applies to you: spend five minutes finding out.

Quick 5-minute diagnosis: what's slowing your site?

Test in a private or incognito window while logged out, because logged-in users usually bypass the cache.

Step 1: Run Google PageSpeed Insights (1 minute)

Test your homepage and one key inner page at pagespeed.web.dev, then check:

  • Core Web Vitals: LCP (how quickly the main content appears), INP (how quickly the page responds to taps) and CLS (whether the layout jumps). Google's "good" thresholds are an LCP within 2.5 seconds, an INP within 200 milliseconds and a CLS of 0.1 or less.
  • Real users vs the lab test: the top section shows real Chrome users' experience if your site has enough traffic; the lab test below it simulates a mid-range phone.
  • Diagnostics: warnings about server response, image sizes, render-blocking requests, unused JavaScript and third-party code each point at a cause below.

See speed test tools explained and Core Web Vitals explained.

Step 2: Check server response time (1 minute)

In Chrome, press F12, open the Network tab and reload. Click the first item (the page itself) and open Timing. "Waiting for server response" is your time to first byte (TTFB).

  • Long wait on every page, even simple ones: a server-side problem, such as hosting, caching, plugins or the database.
  • Short wait, but the page still appears slowly: a front-end problem, such as images, scripts, fonts or CSS.

Step 3: Look for heavy files and third parties (1 minute)

In the same tab, sort by Size. Images measured in megabytes point to an image problem. Many requests to chat tools, pixels, video players or maps point to third-party scripts. Dozens of files from /wp-content/plugins/ and your theme suggest plugin or theme bloat.

Step 4: Check Query Monitor (2 minutes)

Install the free Query Monitor plugin, load a slow page while logged in and open its menu in the admin bar. Look at the page generation time, queries by component (which plugin or theme does the most database work), slow queries and HTTP API calls to outside services. Use it on staging if you can, and deactivate it afterwards.

12 common causes of a slow WordPress site, and how to fix them

Listed roughly in order of impact for a typical business site. Start with whatever your diagnosis pointed to, take a full backup before changing caching, optimisation or database settings, and re-test after each change.

1. Slow or overloaded hosting

Cheap shared hosting puts many sites on one server, and no plugin can fully make up for a server that's underpowered or far from your visitors.

Fix: if server response stays slow with caching on, ask your host about your plan's resources, or move to better hosting near your audience. See reducing server response time (TTFB) and shared vs VPS vs managed hosting. On Hostinger? See Hostinger-specific speed fixes. Moving hosts? See migrating to Hostinger.

2. No page caching, or caching that isn't working

Without a page cache, WordPress builds every page from scratch for every visitor.

Fix: use your host's server caching or one caching plugin, such as LiteSpeed Cache on LiteSpeed servers or WP Rocket elsewhere, never two at once. Many setups show a cache "HIT" in the response headers in DevTools, so you can check it's working. See WordPress caching explained.

3. Huge, unoptimised images

A photo straight from a phone can be several megabytes, and the main image is often what LCP measures.

Fix: resize images to their display size, compress them and serve WebP. Lazy-load images lower down the page, but never the main hero image. See image optimisation for WordPress and lazy loading explained.

4. A heavy theme or page builder setup

Multipurpose themes load code for features you never use, and page builder layouts with many nested sections, widgets and animations get heavy quickly.

Fix: use a lightweight theme (such as Hello Elementor, Astra or GeneratePress), turn on the builder's performance features and simplify your heaviest pages. Built with Elementor? These Elementor-specific fixes help too.

5. Too many plugins, or one badly built plugin

What plugins do matters more than how many you have. One plugin running heavy queries or loading its files on every page can slow down the whole site.

Fix: find the worst offenders in Query Monitor, delete unused plugins, replace heavy ones and stop plugins loading files where they aren't needed. See reducing unused CSS and JavaScript.

6. Too many third-party scripts

Chat widgets, tracking pixels, YouTube embeds, maps and social feeds load code from servers you don't control.

Fix: remove what you don't use, delay the rest until after the main content and swap embeds for click-to-load previews. See how third-party scripts slow your website.

7. Render-blocking CSS and JavaScript

Files in the page head must load before the browser can show anything.

Fix: minify files, defer non-essential JavaScript and remove unused CSS, then test menus, sliders and forms, as aggressive settings can break them. See eliminating render-blocking resources.

8. Too many web fonts

Every font family and weight is another file to download.

Fix: use one or two families and only the weights you need, host them locally and preload the main one. See web fonts and performance.

9. A bloated database

Revisions, spam, expired transients and leftovers from old plugins slow down queries. Large "autoloaded" options are a common hidden cause, as they load on every request, including in the admin.

Fix: take a backup, then clean up revisions, transients, spam and orphaned tables, and review autoloaded data. See WordPress database optimisation.

10. Outdated PHP or WordPress

Newer PHP versions are generally faster, and updates often include performance improvements.

Fix: keep everything updated and run a current, supported PHP version, after testing on staging. See updating your PHP version safely.

11. Visitors far from your server, with no CDN

If most visitors are in a different country from your server, every request travels further.

Fix: host close to most of your visitors, and use a CDN to serve images, CSS and JavaScript from nearer locations.

12. Background jobs and bot traffic

Backups, security scans, scheduled tasks and imports compete with visitors for server resources, and so do bots hammering the login page or site search.

Fix: schedule heavy jobs for quiet hours, run scheduled tasks from a real server cron job on busy sites and use a firewall or bot protection. See WordPress cron explained.

WordPress site slow only on mobile?

Lower mobile scores are normal, as PageSpeed Insights simulates a mid-range phone on a slower connection. If real visitors find the site slow on their phones, check for:

  • Large hero images, sliders and background videos at the top of the page
  • Phones being sent full desktop-size images
  • Heavy JavaScript and animations, which make taps feel sluggish on less powerful phones
  • Sections hidden on mobile, which still add code to the page and may still download their images
  • Popups and chat widgets that load immediately

See speed on Indian mobile networks, fixing LCP and fixing INP.

WordPress admin dashboard slow?

If the front end is fast but the dashboard crawls, page caching won't help, because it doesn't apply to the admin. Common causes:

  • Plugins adding heavy dashboard widgets, notices or licence checks on every screen
  • Large amounts of autoloaded data in the database
  • The Heartbeat API running often while editors are open
  • Too little PHP memory or server resources
  • Page builder editors loading very long pages

Query Monitor works in the admin too. For the full checklist, see why the WordPress admin is slow.

WordPress site slow after an update?

If the slowdown started right after updating WordPress, a plugin, the theme or PHP:

  1. Clear every cache: plugin, server, CDN and any combined CSS and JavaScript files
  2. Give one-off background tasks, such as a database upgrade, time to finish
  3. On staging, or with the Health Check & Troubleshooting plugin (which disables plugins only for you), turn plugins off one at a time to find the culprit
  4. Check that plugin's changelog and support forum, and roll it back to the previous version until a fix is released

Next time, test updates on staging first; see updating WordPress safely and troubleshooting plugin conflicts.

WooCommerce store slow?

Cart, checkout and account pages are different for every shopper, so they can't be served from the page cache, and logged-in customers often bypass caching entirely. Hosting and plugin quality matter even more.

  • Test product, category, cart and checkout pages, not just the homepage
  • Exclude cart, checkout and account pages from the cache, but cache everything else
  • Watch for slow filters, search and large catalogues with many variations
  • Check WooCommerce → Status → Scheduled Actions for a backlog of pending or failed tasks
  • Choose hosting with resources for uncached traffic, ideally with an object cache such as Redis

See WooCommerce speed optimization for store-specific fixes.

FAQs

Why is WordPress so slow?

WordPress itself isn't slow; a clean install on decent hosting is quick. Sites slow down because of what's added on top: cheap hosting, heavy themes, page builders, plugins, large images and third-party scripts, often without caching.

How do I fix a slow WordPress site?

Diagnose first with PageSpeed Insights, the browser's Network tab and Query Monitor. Then fix in order of impact: server response and caching, images, theme and plugin bloat, scripts and fonts, then the database. Re-test after each change.

Do too many plugins slow down WordPress?

They can, but quality matters more than quantity. Many small, well-built plugins can be faster than a few heavy ones, and Query Monitor shows which are doing the most work.

Will a caching plugin fix my slow site?

It often helps visitors a lot, but it won't fix slow hosting, heavy images or third-party scripts, and it doesn't speed up the admin, cart or checkout.

Why is my site fast for me but slow for others?

Visitors may be further from your server, on slower mobile connections or landing on uncached pages. The reverse also happens: logged-in users usually bypass the cache, so admins often see a slower site than visitors do.

How fast should a WordPress site be?

Aim for Google's "good" Core Web Vitals for real visitors rather than a perfect PageSpeed score. The score is a lab test; what matters is how quickly real people can see and use your pages.
