WordPress CSS Changes Not Showing? Caches, Elementor and Overrides Explained

CSS or design changes not showing in WordPress? Clear browser, page and CDN caches safely, regenerate Elementor CSS, and fix child theme order and specificity.

Key takeaways
  • Use the browser's Inspect tool first: a missing rule means an old stylesheet is being served, while a crossed-out rule means another rule is overriding yours.
  • Clear layers in order: regenerate Elementor CSS, clear minified and combined files, then purge the page cache, hosting cache and CDN, and change the stylesheet version so visitors get the new file.
  • Overridden rules come down to loading order and specificity, so load child theme styles after the parent, target a class you added and keep !important for rare cases.

You've added CSS in the Customizer, your child theme or Elementor, saved it, refreshed the page, and nothing has changed. Styling changes go missing more often than text changes for two reasons: stylesheets are separate files that every layer of caching likes to keep, and CSS rules compete, so a correct rule can still lose. For edits to text, images and menus, see WordPress changes not showing; this guide is about CSS.

First, find out which problem you have

There are only two possibilities: the browser never received your new CSS, or it received it and another rule won. Your browser's developer tools tell you which. Right-click the element you changed, choose Inspect and look at the Styles panel.

What you seeWhat it meansWhere to look
Your rule isn't listed at allAn old stylesheet is being served, or your CSS isn't loadingCaches, optimisation plugins, Elementor files
Your rule is listed but crossed outAnother rule is overriding itLoading order and specificity
Your rule is active, but the page still looks wrongThe change is needed on a different element or screen sizeYour selector and media queries

If the rule is missing, click the stylesheet name beside any rule to open the file and check whether your edit is in it.

Browser cache and version numbers

Browsers keep CSS files for a long time because servers tell them to. A hard refresh (Ctrl+F5 or Ctrl+Shift+R on Windows, Cmd+Shift+R on Mac) fetches fresh copies, and ticking "Disable cache" in the developer tools Network tab keeps them fresh while the tools are open.

Your visitors won't hard-refresh, though. WordPress adds a version number to stylesheet addresses, such as style.css?ver=1.0.2, and when it changes, browsers and CDNs fetch the new file. Edit a child theme stylesheet without changing its version, and returning visitors may keep the old one. Update the version the child theme uses when it loads the stylesheet (often the Version line in its header), or use the file's modification time:

wp_enqueue_style( 'child-style', get_stylesheet_uri(), array( 'parent-style' ), filemtime( get_stylesheet_directory() . '/style.css' ) );

Replace parent-style with the handle your parent theme actually uses.

Page cache, server cache and CDN cache

A cached page stores the HTML, including the link to the stylesheet. If it points to an old file or version number, visitors keep loading the old CSS. A CDN may also hold its own copy of the CSS file.

  • Caching plugin: use its purge or clear all option
  • Hosting cache: purge it from the hosting panel or the admin bar button many hosts add
  • CDN: purge the changed file's address, or everything after a bigger redesign. Many CDNs also have a temporary development mode that bypasses the cache while you work

Purge rather than delete: removing cache folders by hand over FTP can leave a caching plugin in a broken state. Switch development modes off when you're done.

Minification and combination plugins

Optimisation plugins often minify stylesheets or combine several into one, saved as new files. Your edit changes the original, but visitors get the optimised copy until it's rebuilt. These files usually have their own clear button, separate from the page cache, so clear both.

Features that remove unused CSS or generate critical CSS are a special case. They build a trimmed stylesheet for each page and can strip out a new selector, especially one for a class added by JavaScript, such as an open mobile menu. If a style appears when you're logged in but not in a private window, turn CSS optimisation off briefly to confirm, then regenerate or add an exclusion for that selector.

Elementor's generated CSS

Elementor turns your design settings into CSS files in the uploads folder, which can go stale after updates, migrations or changes to global colours and fonts.

  • Use the option under Elementor → Tools to regenerate CSS files and data (the wording varies by version), then clear every cache
  • The CSS print method setting switches between external files and internal embedding. Trying internal embedding briefly is a quick way to rule out file caching
  • Check device views: a style set for tablet or mobile overrides the desktop value on those screens
  • Check the template: headers, footers and post layouts may come from the Theme Builder, not the page you edited

If the layout broke after an Elementor update rather than after your own edit, that's a different fix; see Elementor layout broken after an update.

Child theme and loading order

When two rules are equally specific, the one loaded last wins, so the order of stylesheets matters:

  • Child stylesheet loading too early: it should load after the parent's. Listing the parent stylesheet as a dependency when enqueueing sets that order; see WordPress child themes explained
  • Editing a file the theme doesn't load: many themes keep their real styles in a minified file in an assets folder, and style.css holds little more than the theme's details. Edits there do nothing, and edits to a parent theme are lost at the next update anyway
  • Additional CSS: CSS added in Appearance → Customize → Additional CSS, or the Site Editor's Styles panel for block themes, prints late in the page, so it usually wins ties
  • Block themes: styles saved in the Site Editor live in the database and can override the theme's files

Specificity, !important and small mistakes

A more specific selector beats a less specific one, wherever it loads. Page builders often use long, very specific selectors, so a short rule can lose without any warning.

/* Too weak: the builder's own rule wins */
.site-header a { color: #1a1a1a; }

/* More specific: scoped to a class you added */
.site-header .main-menu a { color: #1a1a1a; }

Adding your own class to an element (most builders have a CSS classes field in the advanced settings) gives you a clean hook to target. Use !important sparingly; once several rules rely on it, every later change gets harder.

Also look for small mistakes. One missing closing brace can break every rule after it, a rule inside a mobile media query won't show on desktop, and a mistyped class name matches nothing.

A safe order for clearing every layer

  1. Save or update the change, and confirm it's in the stylesheet or editor
  2. Inspect the element: is your rule missing, or overridden?
  3. Regenerate Elementor or other builder CSS
  4. Clear the optimisation plugin's minified and combined files
  5. Purge the page cache, then the hosting cache, then the CDN
  6. Check in a private window and on your phone using mobile data

Make bigger styling changes on a staging copy first, keep custom CSS in one place, and note where it lives. For error messages rather than styling problems, see common WordPress errors explained.
