WordPress CSS Changes Not Showing? Caches, Elementor and Overrides Explained

WordPress CSS changes not showing? Find out if it is browser, page, CDN or Elementor cache, a minify plugin, load order or specificity, and fix it.

Key takeaways
  • When CSS changes do not show, either an old copy of the file is being served by a cache, or the new rule is loading but another rule overrides it.
  • Use browser developer tools first: if your rule is missing, it is a cache or file problem; if it is crossed out, it is specificity or load order.
  • Clear caches from the inside out: plugin and Elementor CSS, then minify files, then server and CDN cache, then the browser.

If your WordPress CSS changes are not showing, there are only two possibilities: an old copy of the stylesheet is still being served by a cache (browser, caching plugin, server, CDN or Elementor's generated CSS), or the new CSS is loading but another rule is overriding it. Open the page in a private window and inspect the element with your browser's developer tools; that tells you which of the two you have in under a minute, and saves clearing every cache blindly.

Below: how to tell the difference, then each layer of caching and override in turn, and a safe order for clearing everything.

First, find out which problem you have

  1. Open the page in a private or incognito window, which ignores most of your browser cache.
  2. Right-click the element you changed and choose Inspect.
  3. In the Styles panel, look for your new rule.

Browser cache and version numbers

Browsers keep stylesheets for a while so pages load faster. WordPress adds a version number to each file URL, such as style.css?ver=1.2, and the browser fetches a fresh copy when that number changes. If you edit a theme file but the version stays the same, browsers may keep the old one.

  • Do a hard refresh: Ctrl+Shift+R on Windows, Cmd+Shift+R on Mac.
  • In developer tools, Network tab, tick "Disable cache" while the tools are open.
  • For a child theme, bump the version in the stylesheet header or use the file's modified time as the version when enqueuing it.

Clients on phones will not hard refresh, so a version change matters for anything visitors need to see straight away.

Page cache, server cache and CDN cache

A caching plugin stores the finished HTML of each page, including the links to the CSS files. If the HTML is cached, it may still point to an old combined CSS file even after you change the original. Then there may be a server-level cache from your host, such as LiteSpeed or Varnish, and a CDN like Cloudflare holding its own copies.

  • Purge the caching plugin's cache from its toolbar menu or settings.
  • Purge your host's cache from the hosting panel if they run one.
  • Purge Cloudflare or your CDN. In Cloudflare, "Purge Everything" or purge the specific CSS file URL; Development Mode bypasses the cache temporarily while you work. See the Cloudflare setup guide for WordPress.

WordPress caching explained covers how these layers stack and why one purge is not always enough.

Minification and combination plugins

Speed plugins often minify and combine CSS files into new files with random names stored in wp-content/cache or uploads. When you change the original, the combined file needs rebuilding. Most plugins rebuild when you clear their cache, but some keep the old file until a separate "clear minified files" button is used.

  • Clear the minified or optimised CSS separately if your plugin offers it.
  • Temporarily switch off CSS minify, combine and "remove unused CSS" features to test. Unused CSS removal in particular can strip a new class it did not see when it generated the reduced file.
  • Turn optimisation back on afterwards and regenerate.

Elementor's generated CSS

Elementor stores the styling you set in the editor as CSS files in wp-content/uploads/elementor/css, one per page plus global files. If these get out of sync, changes made in the editor do not appear on the live page.

  1. Go to Elementor > Tools and use the option to regenerate CSS and data (the button name has changed between versions).
  2. Check the CSS print method under Elementor's performance or advanced settings. External file is normal; internal embedding can help test whether the files are the problem.
  3. Clear all other caches afterwards, because they may hold the old Elementor file.

If the layout broke after an Elementor update rather than after your edit, see Elementor layout broken after an update. Too many plugin and Elementor CSS files also slow pages down; why Elementor sites get slow explains the trade-offs.

Child theme and loading order

Where you put your CSS decides when it loads, and later rules win when specificity is equal.

  • Additional CSS in the Customizer loads late, so it usually wins. It is tied to the active theme, so it disappears if you switch theme.
  • A child theme stylesheet survives parent theme updates, but must be enqueued correctly and after the parent's stylesheet. WordPress child themes explained shows how.
  • Editing the parent theme directly works until the next update wipes it, which is a common reason changes "disappear". Updating a premium theme safely covers moving edits out first.
  • Page builder custom CSS applies only where you added it, at page, section or widget level.

Check in developer tools which file your rule comes from. If it is the wrong file, or not loaded at all, the problem is placement rather than caching.

Specificity, !important and small mistakes

If your rule appears crossed out, a more specific rule is winning. A selector with an ID beats one with classes; more classes beat fewer; inline styles beat stylesheet rules; and !important beats everything except a later or more specific !important.

/* Loses to the theme's #header .menu a */
.menu a { color: #1a1a1a; }

/* Wins: equally specific, and loads later */
#header .menu a { color: #1a1a1a; }

Prefer matching the theme's selector over adding !important everywhere, which makes future changes harder. Also check the small things:

  • A missing closing brace or semicolon earlier in the file breaks the rules after it.
  • The rule sits inside a media query for a different screen size.
  • A typo in the class name, or a class the builder renamed.
  • The style is set inline by the page builder, which beats your stylesheet.

Habits that stop the problem coming back

Once your change is showing, a few working habits make the next one painless:

  • Keep custom CSS in one place. Pick the child theme stylesheet or the Additional CSS panel and stick to it, rather than spreading rules across theme options, page builder panels and plugins.
  • Comment your rules with what they change and why, so you or a developer can find them later.
  • Exclude the editor from caching. Make sure logged-in users and wp-admin are never cached, which most caching plugins do by default.
  • Know your purge buttons. Note which caches your site has (plugin, host, CDN, Elementor) so you clear the right ones after each change.
  • Check on a real phone. Mobile browsers and in-app browsers, such as the one inside WhatsApp or Instagram, can hold cached files longer than desktop ones.
  • Avoid stacking optimisation plugins. Two plugins both minifying CSS make cache problems much harder to trace.

A safe order for clearing every layer

  1. Confirm in developer tools whether the rule is missing or overridden.
  2. If overridden, fix specificity or placement; no cache clearing needed.
  3. If missing, regenerate Elementor CSS (if used).
  4. Clear the optimisation plugin's minified CSS, then its page cache.
  5. Purge the host's server cache.
  6. Purge Cloudflare or your CDN.
  7. Hard refresh, then check in a private window and on a phone using mobile data.

For larger CSS changes, work on a staging copy first so visitors never see a half-finished design; see staging sites explained.

FAQs

Why are my WordPress CSS changes not showing?

Either a cache is serving an old copy of the stylesheet or page, or your new rule is loading but is overridden by a more specific or later rule. Developer tools show which.

Why do CSS changes show for me but not for visitors?

When you are logged in, most caching plugins show you a fresh page. Visitors get the cached version, which still links the old CSS. Purge the page cache, server cache and CDN.

How do I clear Elementor CSS cache?

Use the regenerate CSS and data option under Elementor > Tools, then clear your caching plugin and CDN, because they may still hold the old file.

Should I use !important to force CSS changes?

Only as a last resort for a single stubborn rule. Matching or slightly beating the original selector is cleaner and easier to maintain.

Why did my CSS changes disappear after an update?

They were probably added directly to the parent theme or plugin files, which updates overwrite. Move custom CSS to a child theme or the Additional CSS panel.
