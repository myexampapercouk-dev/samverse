Hreflang Tags for India: Multilingual SEO for Hindi and Regional-Language Versions

Hreflang tags for India: codes for Hindi, Marathi, Tamil and other Indian languages, return tags, x-default, HTML vs sitemap, plugins and errors.

Key takeaways
  • Give each language its own URL, usually a subfolder like /hi/, and use valid codes such as hi, en-IN, hi-IN and x-default; a country code on its own, like IN, is not valid.
  • Hreflang must be reciprocal, point to canonical, indexable URLs and use one method (page head or XML sitemap); WPML, Polylang, TranslatePress and Weglot add it once translations are linked.
  • Human-reviewed translation and keyword research in Hindi, regional scripts and Hinglish matter more than the tags, and crawler checks now replace Search Console's retired International Targeting report.

Hreflang is a tag that tells Google which language, and optionally which country, each version of a page is for, so a Hindi-speaking searcher sees your Hindi page and an English-speaking searcher sees your English page. On an Indian site with English and Hindi versions, each page lists itself and its translation using codes such as en-IN and hi-IN, plus an x-default fallback, and every version must link back to the others. Get that right, pair it with translations people trust, and Google can show the right version to the right person.

This guide covers the SEO side. For whether you need a multilingual site at all, start with multilingual WordPress websites.

What hreflang does, and what it doesn't

Hreflang tells Google "this page also exists in these languages, at these addresses", so the versions aren't treated as competitors. But:

  • It doesn't boost rankings on its own; it helps Google choose the right version
  • It doesn't translate anything or detect a visitor's language
  • It can't fix a page that isn't really in that language. Google says it works out a page's language from its visible content, so a "Hindi" page that is mostly English will be treated as English

Language and region codes: hi, en-IN and x-default

Each hreflang value is a language code, optionally followed by a region code:

  • Language uses two-letter ISO 639-1 codes: hi Hindi, en English, mr Marathi, ta Tamil, te Telugu, bn Bengali, gu Gujarati, kn Kannada, ml Malayalam, pa Punjabi.
  • Region is optional, uses two-letter ISO 3166-1 country codes such as IN, US or GB, and comes after the language: en-IN, hi-IN.
  • x-default marks the page Google should show when no listed language matches the searcher, usually your main English page or a language-choice page.
CodeMeaningValid?
hi or hi-INHindi, or Hindi for users in IndiaYes
en-INEnglish for users in IndiaYes
x-defaultFallback when nothing matchesYes
INA country with no languageNo
inOften meant as "India", but not a valid language code hereNo
en-UKMeant as British English, but the country code is GBNo, use en-GB

Do you need the region at all? If your pages are for Hindi or English speakers anywhere, hi and en are enough. Add a region when you have versions for different countries, such as en-IN with rupee pricing and en-GB or en-US for overseas buyers; see selling internationally from an Indian WooCommerce store. Hreflang can't target a state or city, so a Marathi page is matched by language, not by Maharashtra.

For a page available in English, Hindi and Marathi, the head of every version would carry the same set of tags:

<link rel="alternate" hreflang="en-IN" href="https://www.example.in/contact/" />
<link rel="alternate" hreflang="hi-IN" href="https://www.example.in/hi/contact/" />
<link rel="alternate" hreflang="mr-IN" href="https://www.example.in/mr/contact/" />
<link rel="alternate" hreflang="x-default" href="https://www.example.in/contact/" />

Codes are not case-sensitive, but writing the language in lower case and the region in capitals, as above, is the usual convention and easier to scan for mistakes.

Return tags: every version lists every version

Hreflang works in sets. If the English page lists the Hindi page, the Hindi page must list the English page back. These are called return tags, and without them Google may ignore the pair. Each page should also list itself. For a page in two languages, both versions carry the same three lines:

<link rel="alternate" hreflang="en-IN" href="https://www.example.in/services/" />
<link rel="alternate" hreflang="hi-IN" href="https://www.example.in/hi/services/" />
<link rel="alternate" hreflang="x-default" href="https://www.example.in/services/" />
  • Use full URLs, with https and the right www or non-www version, not relative paths.
  • Point to the final, indexable URL: not a redirect, a noindexed page or a 404.
  • Each language version is its own canonical. Setting the Hindi page's canonical to the English page tells Google to ignore the Hindi one. See canonical tags explained.
  • Only pair true equivalents. If a service page exists only in English, don't point its hreflang at the Hindi homepage.

Page head, XML sitemap or HTTP header?

Google accepts hreflang in three places. Pick one method; mixing them makes errors harder to find, and conflicting values can cancel each other out.

MethodBest forWatch out for
Link tags in the page headMost WordPress sites; plugins add them automaticallyMany languages mean many extra lines on every page
XML sitemapLarge sites or many languages; keeps page code leanHarder to spot-check, and the sitemap must stay in sync with real pages
HTTP headerNon-HTML files such as PDF brochuresSet at server level, so it usually needs a developer

In a sitemap, each URL lists its alternates with xhtml:link entries, and the xhtml namespace must be declared at the top of the file:

<url>
  <loc>https://www.example.in/services/</loc>
  <xhtml:link rel="alternate" hreflang="en-IN" href="https://www.example.in/services/" />
  <xhtml:link rel="alternate" hreflang="hi-IN" href="https://www.example.in/hi/services/" />
  <xhtml:link rel="alternate" hreflang="x-default" href="https://www.example.in/services/" />
</url>

The Hindi URL gets its own entry with the same three alternates. For sitemap basics, see XML sitemaps explained.

Choose a URL structure

Each language version needs its own URL. Avoid showing different languages at the same address based on cookies or browser settings, because Google may only ever see one version.

StructureExampleNotes
Subfolderexample.in/hi/Simplest for most Indian businesses: one site, one hosting account, one domain building strength
Subdomainhi.example.inWorks, but needs more setup and is managed more like a separate site
Separate domainexamplehindi.inRarely worth it; more cost and more to maintain
URL parameterexample.in/?lang=hiNot recommended by Google; avoid if you can

Hindi slugs can use Devanagari or Roman script. Google handles both, but Devanagari URLs turn into long strings of percent-codes when copied into WhatsApp or email, so many sites keep slugs in Roman script; see SEO-friendly URLs. Be consistent, and don't automatically redirect visitors by IP address or browser language; offer a clear language switcher instead.

WordPress multilingual plugins and hreflang

On WordPress you rarely write hreflang by hand. The main multilingual plugins add it once pages are linked as translations of each other. At the time of writing:

  • WPML is a paid plugin that stores each translation as its own post and outputs hreflang tags.
  • Polylang has a free version and a paid Pro version, also stores translations as separate posts, and outputs hreflang tags.
  • TranslatePress lets you translate visually on the front end, has free and paid versions, and adds hreflang to the page head.
  • Weglot is a subscription service that stores translations on its own platform and handles hreflang for you.

Features, prices and defaults change, so check each plugin's current documentation for x-default, sitemap support and compatibility with your SEO plugin. Test the output either way; a misconfigured plugin can still miss return tags.

Hindi and regional-language sites

Indian businesses rarely need every language: a Pune clinic might add Marathi and Hindi, a Chennai manufacturer Tamil.

  • Only add languages you can maintain. An outdated Marathi price or opening time is worse than no Marathi page.
  • Hinglish has no separate code. Hindi typed in Roman script doesn't have a widely used hreflang value of its own, so most sites serve those searches from the English or Hindi pages rather than building a third version.
  • Fonts matter. Devanagari, Tamil and other scripts need fonts that display correctly and load quickly; see Hindi and Devanagari fonts on your website and web fonts and website speed.
  • Set the lang attribute on each page, such as lang="hi", which browsers and screen readers rely on. Multilingual plugins normally handle this.

Research keywords in each language

A translated page targets whatever words the translator happened to choose, which may not be what people type. Indians search in several ways at once:

  • Hindi or regional script: "घर के लिए सोलर पैनल"
  • Hinglish in Roman script: "ghar ke liye solar panel"
  • English with local terms: "rooftop solar subsidy Pune"

Decide which page should serve Hinglish searches; because they're typed in Roman script, a Devanagari page may not match them well. Check Google's autocomplete in each language, and once pages are live, filter Search Console's Performance report by the /hi/ folder to see real queries. See keyword research for small businesses for the method.

Translation quality matters more than tags

Perfect hreflang won't rescue a poor translation. Readers notice stiff, word-for-word Hindi immediately, and in medical, legal or financial content a mistranslation can mislead. Google's spam policies also list text translated by an automated tool without human review as an example of low-value, automatically generated content.

  • Use native speakers for the pages that matter most (homepage, key services or products, pricing, contact), and have a fluent reviewer edit any machine translation before it's published
  • Write the way your customers speak; everyday Hindi with familiar English words like "booking" is often clearer than very formal Hindi
  • Translate the whole experience: SEO titles, meta descriptions, alt text, menus, buttons, form labels and messages, and thank-you pages

Check that it's working

  1. View the source of an English and a Hindi page and confirm each lists the other, itself and x-default, as identical sets.
  2. Run an SEO crawler or site audit tool that reports hreflang issues such as missing return links, invalid codes and non-canonical targets.
  3. Use URL Inspection in Search Console on both versions to confirm each is indexed and that the Google-selected canonical is the page itself, not its translation. See Search Console page indexing errors for related statuses.
  4. Search in Hindi on a phone set to Hindi and see which version appears.

Search Console's old International Targeting report, which used to list hreflang errors, has been retired, so crawler checks and spot checks are now the main way to catch mistakes. Recheck after adding pages, changing slugs or switching plugins.

FAQs

Do I need hreflang if my site is only in English?

No. Hreflang is only for pages that exist in more than one language or regional version. A single-language site needs a correct canonical on each page, not hreflang.

Should I use hi or hi-IN?

Either is valid. Plain hi covers Hindi speakers anywhere; hi-IN targets Hindi speakers in India. For most Indian businesses with one Hindi version the difference is small, so pick one and use it consistently.

Is x-default required?

It isn't mandatory, but it's recommended. It tells Google what to show searchers whose language you don't cover, such as a Tamil speaker on a site with only English and Hindi.

Does hreflang help my Hindi pages rank higher?

Not on its own. It helps Google show the right version to the right searcher. The Hindi pages still need useful content, natural translation and links.
