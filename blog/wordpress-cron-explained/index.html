WP Cron Explained: Why Scheduled Posts, Emails and Backups Run Late, and How to Fix It With a Real Server Cron

WP Cron explained: why WordPress misses schedules on low-traffic sites, how to set DISABLE_WP_CRON with a server cron, Action Scheduler and WP-CLI checks.

Key takeaways
  • WP-Cron only runs when someone visits the site, so on quiet or heavily cached sites scheduled tasks run late or not at all.
  • The dependable fix is DISABLE_WP_CRON in wp-config.php plus a server cron job in hPanel or cPanel, tested afterwards.
  • Use WP-CLI, WP Crontrol and WooCommerce's Scheduled Actions screen to see what is due, what ran and what failed.

WP Cron (written WP-Cron in the WordPress code) is the system WordPress uses to run scheduled tasks: publishing scheduled posts, sending timed emails, running plugin backups and clearing old data. It does not run on a clock. It checks for due tasks only when someone loads a page, so on a low-traffic or heavily cached site, tasks run late or get missed. The reliable fix is to switch off the visitor-triggered check and let your server call WordPress on a fixed timetable.

This is one of the things I check on every site I take on for WordPress maintenance, because a missed backup is usually noticed only when you need it.

How WP Cron actually works

On a normal server, cron is the operating system's scheduler. WordPress cannot assume every host offers it, so it ships its own: on each page load it looks at a list of scheduled events stored in the database. If one is due, it sends a background request to its own wp-cron.php file, which runs the task.

What depends on it

  • Scheduled posts and pages
  • Plugin backups on a schedule (backups taken by your host are separate)
  • Newsletters, digests, reminders and follow-up emails
  • WooCommerce scheduled sale prices and background jobs
  • Update checks, security scans and log clean-ups
  • Imports and syncs with a CRM, inventory system or feed

Why WP Cron misses schedules on low-traffic sites

No visitors, no trigger

If nobody visits between 1 am and 8 am, a 2 am backup waits for the first visitor of the morning. Small business sites in India often see little traffic at night, so this is the most common cause.

Page caching

When a page is served straight from a cache, WordPress may not load fully, so that visit does not trigger WP-Cron. A well-cached site with modest traffic can go long stretches between runs. WordPress caching explained covers how caching layers work.

Blocked loopback requests

WP-Cron works by the site calling itself. Firewalls, security plugins, password protection on staging, SSL problems and some hosting setups block that call, and scheduled tasks quietly stop.

Disabled without a replacement

If DISABLE_WP_CRON is set but no server cron exists, nothing scheduled runs at all. This often happens after a migration, when the line comes across in wp-config.php but the cron job stays behind on the old host.

Long or broken tasks

A backup or import that runs out of time or memory can fail halfway, and an error in one plugin's task can hold up others. Removed plugins can also leave orphaned events.

Debugging missed schedules

First find out whether tasks are not being triggered, or are triggered but failing.

  1. Site Health: Tools, then Site Health, warns about failed loopback requests and late scheduled events.
  2. WP Crontrol: a free plugin that lists every event, when it is next due, and lets you run one manually.
  3. Posts list: "Missed schedule" next to a post means it was not published on time.
  4. Backup logs: check when backups actually ran, not when they were meant to.
  5. WooCommerce: WooCommerce, then Status, then Scheduled Actions shows pending, completed and failed jobs.

If events are overdue and never run, WP-Cron is not being triggered. If they run and fail, the task itself is the problem, and the plugin's own log or the PHP error log is the next place to look. If the trouble started after installing something, troubleshooting plugin conflicts helps narrow it down.

WP-CLI cron commands

If your host gives SSH access with WP-CLI (many hosts include it on some plans, so check yours), these commands show the picture quickly:

# Check that WP-Cron can spawn (tests the loopback)
wp cron test

# List scheduled events with their next run time
wp cron event list

# Run every event that is due now
wp cron event run --due-now

# Run one hook by name
wp cron event run wp_scheduled_delete

# List registered schedules (hourly, twicedaily, daily...)
wp cron schedule list

Only delete events you are sure belong to plugins you no longer use. Deleting a core or active plugin's event can stop things like update checks.

The fix: DISABLE_WP_CRON with a real server cron

  1. Take a full backup first; see WordPress backup and restore.
  2. Put this line in wp-config.php, higher up than the closing "stop editing" comment: 
    define( 'DISABLE_WP_CRON', true );
  3. Create a cron job in your hosting panel. Set it to run every 5 or 15 minutes.
  4. Test: schedule a post a few minutes ahead and confirm it publishes on time, then check that the next backup runs when expected.

On Hostinger (hPanel)

hPanel has a Cron Jobs section under Advanced. You can choose a PHP script or a custom command, set the interval and save. Menu names change from time to time, so follow Hostinger's current help article if the screen looks different. The Hostinger WordPress setup guide covers the panel in general.

On cPanel hosts

cPanel has a Cron Jobs icon under Advanced. Pick a common interval or enter one, then paste the command. Typical commands look like these; your host may recommend a specific PHP path:

# Call wp-cron.php over HTTP
wget -q -O - https://yourdomain.com/wp-cron.php?doing_wp_cron >/dev/null 2>&1

# Or run it through PHP directly
cd /home/USER/public_html && php wp-cron.php >/dev/null 2>&1

# Or with WP-CLI
cd /home/USER/public_html && wp cron event run --due-now >/dev/null 2>&1

Some shared plans limit how often cron jobs may run, so check with your host before setting a very short interval.

Action Scheduler for WooCommerce

WooCommerce and several plugins use Action Scheduler, a queue for background jobs such as webhooks, sale price changes, subscription renewals and email sequences. It is normally kicked off through WP-Cron, so when WP-Cron stalls, the queue grows. Check WooCommerce, then Status, then Scheduled Actions:

  • A long list of past-due pending actions points to WP-Cron not running
  • Many failed actions point to a problem in the task itself; open one to read the log
  • A very large completed list can bloat the database; WooCommerce clears old entries over time

With WP-CLI you can run the queue directly:

wp action-scheduler run

On busy stores, a server cron that runs regularly keeps this queue moving, which also helps with WooCommerce speed.

Does a server cron make the site faster?

Somewhat, mainly by making things predictable. With default WP-Cron, a visitor's page load can start a heavy job during a busy period. With a server cron, tasks run on a timetable and page loads no longer check the schedule. On its own it will not fix a slow site, but it removes one source of random slowdowns, and it is worth checking during WordPress speed optimisation work.

Common mistakes when switching to a server cron

  • Adding the line below "stop editing": constants defined after wp-settings.php loads are ignored, so the visitor-triggered check keeps running.
  • Wrong URL in the cron command: after moving from http to https or changing domain, the old address may redirect and the request silently fails.
  • Password-protected staging: an HTTP call to wp-cron.php gets blocked by the password prompt; use the PHP or WP-CLI form instead.
  • Several sites, one job: each WordPress install needs its own cron job pointing at its own folder or URL.
  • Interval too long: a once-an-hour job means a 9:05 scheduled post may appear at 10:00.

Moving hosts is the usual moment these slip; it is part of the checklist I follow for WordPress migration.

Monthly cron health checklist

  • Schedule a test post and confirm it publishes
  • Check the latest backup time in the plugin log
  • Look for overdue events in WP Crontrol or wp cron event list
  • Review failed actions in WooCommerce Scheduled Actions
  • After any migration or domain change, confirm the cron job points to the new path and URL

FAQs

What is wp cron in WordPress?

It is WordPress's built-in scheduler. It runs due tasks when someone visits the site, instead of at exact times.

Is it safe to set DISABLE_WP_CRON to true?

Yes, as long as a server cron job replaces it. Without that job, nothing scheduled will run.

How often should the server cron run?

Every 5 to 15 minutes suits most business sites. Busy stores with many background jobs may need the shorter end, if the host allows it.

Why does my post say "Missed schedule"?

Usually because WP-Cron was not triggered at the scheduled time, through low traffic, caching or a blocked loopback. A server cron fixes it.

Do I need SSH or WP-CLI to fix WP Cron?

No. The wp-config.php line and a cron job in hPanel or cPanel are enough. WP-CLI just makes debugging quicker.
