Custom Gutenberg Blocks for Agencies: Patterns, Synced Patterns, ACF Blocks or Native Blocks With block.json

Custom Gutenberg blocks explained for agencies: when a pattern is enough, when to build ACF blocks, when native React blocks pay off, and how to lock layouts.

Key takeaways
  • Most custom Gutenberg block requests can be met with a pattern or synced pattern; build a real block only when content needs structure, logic or a locked layout.
  • ACF blocks suit PHP teams and server-rendered sections, while native blocks built with block.json and React give the best editing experience for interactive pieces.
  • Plan the block library like a design system: name blocks clearly, restrict what editors can change with theme.json and locking, and document every block at handover.

Custom Gutenberg blocks are reusable content components you build for the WordPress block editor so clients can add a pricing table, team grid or enquiry banner without touching code. For an agency, the right choice is usually the lightest one that works: a block pattern for fixed layouts, a synced pattern for content that must stay identical everywhere, an ACF block for structured fields rendered in PHP, and a native block registered with block.json when you need live previews and rich interaction.

This guide walks through each option, how to decide between them on a real project, and how to stop editors breaking a design you spent weeks perfecting. It is written for agencies who hand WordPress builds to clients and want them to stay tidy for years.

The table hides one important point: these are not rivals. A good theme usually mixes them, with patterns doing most of the work and a handful of custom blocks covering what patterns cannot.

Block patterns: start here

A pattern is a saved arrangement of core blocks. In a modern theme you add a PHP file to the patterns folder with a header comment giving its title, slug and categories, and WordPress registers it automatically. Editors insert it from the pattern library and then change anything they like.

Patterns are ideal for hero sections, feature rows, testimonial layouts with placeholder text, and call-to-action bands. Because the output is plain core blocks, there is nothing to maintain when WordPress updates, and the content survives if the theme is ever switched. The trade-off is freedom: once inserted, the pattern is just blocks, so an editor can delete a column or change a colour and nothing stops them.

Use patterns when you want consistency at the starting point but the client is allowed to adapt. For most brochure sites built on block themes and full site editing, a library of ten to twenty well-named patterns covers the bulk of page building.

Synced patterns and overrides

Synced patterns (previously called reusable blocks) are stored once in the database and referenced wherever they are placed. Change the source and every instance updates. They are perfect for a footer enquiry strip, a standard disclaimer, or an offer banner that runs across many service pages.

Recent WordPress versions add pattern overrides, which let you mark specific blocks inside a synced pattern (for example a heading, paragraph, button or image) as editable per instance while the layout stays locked. That covers a surprising number of cases agencies used to solve with custom blocks, such as a team card where only the photo, name and role change.

The limits: overrides work only on supported core blocks, there is no field validation, and you cannot add logic such as hiding a section when a field is empty. When you need those, move to a real block.

ACF blocks: the quickest route for PHP teams

ACF Pro lets you register a block with a block.json file and render it with a PHP template, using field groups for the content. The editor sees a form (or inline preview) and the front end gets exactly the markup you wrote. For agencies whose developers are comfortable in PHP, this is the fastest way to ship a library of structured blocks.

Good fits for ACF blocks include:

  • Pricing or plan tables where each row has fixed fields and a highlight toggle.
  • Doctor, lawyer or staff profiles pulled from a custom post type with custom fields.
  • Location blocks showing address, timings and a click-to-load map.
  • Comparison tables, FAQ groups that also output FAQPage schema, and download lists with file sizes.

Watch two things. First, ACF blocks depend on a paid plugin, so the client's licence must be renewed and handed over properly. Second, the editor preview is server-rendered, which can feel slower than native blocks on large pages. Keep templates lean and avoid heavy queries inside the render file.

Native blocks with @wordpress/create-block

Native blocks are built in JavaScript with React components from the WordPress packages. The official scaffolding tool, @wordpress/create-block, generates a plugin with block.json, an edit component, a save function or render file, and a build setup. The result behaves like a core block: inline editing, toolbar controls, live preview and support for colours, spacing and typography from theme.json.

Choose native blocks when the editing experience matters most, for example a tabbed content block, an accordion with nested blocks inside each panel, a before-and-after image slider, or a block that pulls data from an external API. Dynamic blocks (with a PHP render callback) are usually safer than static ones for agency work, because changing the markup later does not trigger block validation errors on every existing post.

Native blocks need more time and a developer who knows modern JavaScript. If your team does not, this is a common area to bring in white-label WordPress development rather than learning on a client deadline.

How to decide on a real project

When a designer hands over a Figma file, go through each section and ask four questions in order:

  1. Can core blocks reproduce it? If yes, make it a pattern.
  2. Must it look identical on every page? If yes, make it a synced pattern, with overrides for the parts that change.
  3. Does the content have a fixed structure or come from elsewhere? If yes, an ACF block or a dynamic native block.
  4. Does the editor need to see and edit it visually with interactions? If yes, a native block.

On a typical service-business site this produces a handful of custom blocks and many patterns. If your list comes out the other way round, check whether the design is fighting the editor. Our notes on Figma to WordPress approaches cover how to set up designs so they map cleanly to blocks.

Stopping editors from breaking the design

The biggest complaint agencies hear after launch is that the client broke the layout. WordPress gives you several controls:

  • theme.json settings: limit the colour palette, font sizes and spacing options to your design tokens, and turn off custom colours and gradients.
  • Template locking: lock a custom block's inner blocks so editors can change content but not remove or move sections.
  • Allowed blocks: restrict which blocks can be inserted inside a container, or hide rarely needed core blocks from the inserter.
  • Content-only editing: lock a pattern so editors see only the text and images they are meant to change.
  • User roles: keep the Site Editor and template editing for administrators.

Locking is a balance. Lock too little and the site drifts; lock too much and the client calls you for every small change. Agree the level with the client before you build.

Naming, structure and a block library that scales

Agencies that build many sites benefit from a shared block plugin rather than putting blocks inside each theme. Keep blocks in a plugin with a consistent namespace (for example agencyname/pricing-table), so content survives a theme change and fixes can be rolled out across sites.

Name blocks in plain language for editors, give each a clear icon and description, and add example data so the inserter preview is useful. Keep styles in the block's own stylesheet so the front end only loads CSS for blocks actually used on a page.

Performance, maintenance and handover

Custom blocks can be faster than page builders, but only if you build them carefully. Register scripts only for blocks that need them, avoid loading slider libraries on every page, and use server rendering for anything that queries posts. Our guide to Elementor vs Gutenberg explains why block-based builds tend to produce lighter pages.

At handover, document each block: what it is for, which fields it has, and any limits. Include it in your developer handoff checklist, and agree who updates the block plugin when WordPress changes. Treat the block library as code with version control, a changelog and a staging test before each release.

FAQs

What are custom Gutenberg blocks?

They are components you create for the WordPress block editor, registered with a block.json file, so editors can add specific layouts or structured content in a few clicks. They can be built with JavaScript and React or with ACF and PHP templates.

Do I need a custom block or is a block pattern enough?

If core blocks can reproduce the layout and editors may change it freely, a pattern is enough. Build a custom block when you need fixed fields, logic, data from elsewhere, or a layout that editors must not be able to break.

Are ACF blocks slower than native blocks?

On the front end they can be just as fast, because both output plain HTML. The editor preview of ACF blocks is server-rendered, so it can feel slower on long pages; keep render templates simple to reduce that.

Should custom blocks live in the theme or a plugin?

A plugin is usually better. Content built with the blocks keeps working if the theme changes, and an agency can reuse and update one block plugin across many client sites.

Will WordPress updates break custom Gutenberg blocks?

Well-built dynamic blocks rarely break, but deprecated APIs and markup changes can cause validation errors in static blocks. Test updates on a staging site and keep block code under version control.

Can I convert Elementor sections into Gutenberg blocks?

There is no reliable automatic conversion. Each section is rebuilt as a pattern or custom block, which is a good moment to simplify the design and remove sections that no longer earn their place.
