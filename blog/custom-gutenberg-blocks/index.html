Custom Gutenberg Blocks for Agencies: Patterns, Synced Patterns, ACF Blocks or Native Blocks With block.json

Custom Gutenberg blocks for agencies: when block patterns are enough, when to use ACF or native blocks with create-block, and how to lock the design.

Key takeaways
  • Start with block patterns built from core blocks; move to custom blocks only when you need structured fields, dynamic data or markup editors must not change.
  • ACF blocks are the quickest route for PHP-focused teams, while native blocks built with create-block and block.json give the richest editing experience with no plugin dependency.
  • Lock the design with theme.json settings, template locks and allowed blocks, keep custom blocks in a plugin rather than the theme, and document them at handover.

Custom Gutenberg blocks give your client's editors on-brand components, such as service cards, testimonials or call-to-action bands, that they fill with content while the design stays intact. There are four ways to build them, in rising order of effort: block patterns made from core blocks, synced patterns, ACF blocks rendered with PHP, and native blocks scaffolded with @wordpress/create-block and described in block.json. Start with patterns, and build custom blocks only when you need structured fields, dynamic data or markup that editors must not be able to change.

For agencies, the right choice affects build time, quotes and how many "small change" requests come back after launch. When I build for agencies as a white-label WordPress developer, sites are built with global styles and a clean structure in Elementor or the block editor, so clients can edit without breaking the layout. On a block theme build, the editing experience comes from locked patterns and custom blocks; it is one of the three build approaches compared on my Figma to WordPress page. Here is how the options compare and when each makes sense.

Block patterns: start here

A pattern is a saved arrangement of core blocks, such as a group with a heading, paragraph and buttons, that editors insert from the pattern library. In a theme, each pattern is a PHP file in the /patterns folder with a header comment, and WordPress registers it automatically:

<?php
/**
 * Title: Call to action band
 * Slug: agency-theme/cta-band
 * Categories: call-to-action
 */
?>
<!-- wp:group {"className":"cta-band","layout":{"type":"constrained"}} -->
<div class="wp-block-group cta-band">
  <!-- wp:heading -->
  <h2 class="wp-block-heading">Ready to start your project?</h2>
  <!-- /wp:heading -->
  <!-- wp:paragraph -->
  <p>Tell us what you need and get a fixed quote.</p>
  <!-- /wp:paragraph -->
</div>
<!-- /wp:group -->

Patterns are quick to build and need no build step, and because they use core blocks, they survive a theme change as ordinary content. The trade-off is that once inserted, each copy is independent, and editors can restyle it freely unless you lock it.

Synced patterns and overrides

A synced pattern, called a reusable block in older WordPress versions, is one piece of content shown in many places: edit it once and every instance updates. That suits a site-wide call to action or a disclaimer. Pattern overrides, added in recent versions, let editors change specific content inside each instance, such as a heading or button text, while the layout stays synced. At the time of writing, overrides work only with certain core blocks, such as headings, paragraphs, images and buttons, so check the current support before designing around them.

ACF blocks: the quickest route for PHP teams

With Advanced Custom Fields PRO, a block is a block.json file, a field group and a PHP template. Editors fill in labelled fields, and the block renders on the server, so the front end is plain HTML. A minimal block.json looks like this:

{
  "name": "acf/testimonial",
  "title": "Testimonial",
  "category": "text",
  "acf": { "mode": "preview", "renderTemplate": "testimonial.php" },
  "supports": { "anchor": true, "align": false }
}

You register it with register_block_type pointing at the block's folder, then assign an ACF field group to that block. ACF blocks suit agencies whose developers are comfortable in PHP, components driven by structured fields, and sites already using ACF for custom post types and fields. The cost is a dependency on an ACF PRO licence, which should be held in the client's name, and an editing experience that is less fluid than a native block's.

Native blocks with @wordpress/create-block

Native blocks are built with WordPress's own block API. The official scaffolding tool sets up the folder, block.json and build scripts in one command:

npx @wordpress/create-block@latest service-card --variant dynamic
cd service-card
npm start

Everything WordPress needs to know about the block lives in block.json, which lets WordPress load the block's scripts and styles only on pages that use it:

{
  "$schema": "https://schemas.wp.org/trunk/block.json",
  "apiVersion": 3,
  "name": "agency/service-card",
  "title": "Service card",
  "category": "design",
  "attributes": {
    "heading": { "type": "string" },
    "summary": { "type": "string" }
  },
  "supports": { "html": false, "color": { "background": true, "text": false } },
  "editorScript": "file:./index.js",
  "style": "file:./style-index.css",
  "render": "file:./render.php"
}

The editor side is written in React. The front end is either saved as static HTML in the post content or, as here, rendered by PHP on each request. Dynamic rendering means you can change the markup later without "invalid block" warnings on existing content:

<div <?php echo get_block_wrapper_attributes(); ?>>
  <h3><?php echo esc_html( $attributes['heading'] ?? '' ); ?></h3>
  <p><?php echo esc_html( $attributes['summary'] ?? '' ); ?></p>
</div>

Native blocks give the best editing experience, with text typed directly into the block, live previews and toolbar controls, and they depend on nothing but WordPress. For front-end behaviour such as tabs or filters, the Interactivity API, added in WordPress 6.5, is the recommended approach. The cost is JavaScript tooling, a steeper learning curve and more care when a block's structure changes.

Stopping editors from breaking the design

"Blocks they can't break" is usually the real requirement. WordPress gives you several levers, and most projects use a combination:

  • theme.json settings that remove custom colours, gradients and font sizes, so editors choose only from the brand palette and type scale.
  • Block supports in block.json, enabling only the controls a block needs.
  • Locking so key blocks can't be moved or removed, and template locks on inner blocks so a card's structure stays fixed while its text is editable.
  • Allowed blocks lists that hide blocks editors don't need.
  • Sensible user roles, with Editors for content staff and Administrator access kept to a few people.
{
  "version": 3,
  "settings": {
    "color": { "custom": false, "customGradient": false, "defaultPalette": false },
    "typography": { "customFontSize": false }
  }
}

Which should an agency choose?

  1. Marketing site, layouts achievable with core blocks: patterns with theme.json restrictions. Quickest to build and hand over.
  2. A component repeated identically across the site: a synced pattern.
  3. Structured components, such as team members, specifications or pricing tables, built by a PHP team: ACF blocks.
  4. A design system used across many client sites, complex interactions or a product you'll maintain for years: native blocks, kept in a shared plugin.
  5. Content that is really data, such as listings or case studies shown in several places: a custom post type with fields and a template, not a block on each page.

If the client wants to drag layouts around freely, a page builder may suit them better; Elementor, block theme, Bricks or custom theme compares the build approaches, and block themes and full site editing explains where custom blocks fit in a block theme.

Performance, maintenance and handover

  • Keep custom blocks in a plugin, not the theme, so content still renders if the theme changes; custom plugin development covers structuring one.
  • Load assets per block through block.json, rather than one large stylesheet on every page.
  • Plan for change: prefer dynamic rendering for blocks whose markup may evolve, and add deprecations when a static block's saved HTML changes.
  • Use version control and a staging site, and test blocks against new WordPress releases before updating production.
  • Document each block for the client: what it's for, its fields and where it's used. The agency handoff checklist covers what to agree with your developer.

FAQs

Do I need React to build custom Gutenberg blocks?

For native blocks, the editor side is written in JavaScript, usually React. Patterns need no JavaScript, and ACF blocks let you build with PHP templates and ACF fields instead.

Are ACF blocks slower than native blocks?

On the front end, both can output clean HTML, so the difference is usually small when built well. ACF blocks render previews through the server in the editor, which can feel slightly less immediate for editors.

What happened to reusable blocks?

They were renamed synced patterns in WordPress 6.3. They work the same way, and pattern overrides now allow some content to differ per instance.

Should custom blocks live in the theme or a plugin?

A plugin, in most cases. Blocks hold content, and keeping them in a plugin means that content still displays properly if the client changes theme later.

Can custom blocks be built from a Figma design system?

Yes. Figma components usually map well to patterns or custom blocks, and Figma colour and text styles map to theme.json settings, so the build stays faithful to the design.
