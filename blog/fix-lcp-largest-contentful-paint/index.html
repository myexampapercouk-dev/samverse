How to Fix Slow Largest Contentful Paint (LCP) on WordPress

Fix slow Largest Contentful Paint in WordPress: find your LCP element, split the delay into four parts and fix server, hero image, CSS and fonts in order.

Key takeaways
  • LCP measures when the biggest visible element, usually a hero image or heading, finishes rendering, and good is 2.5 seconds or less for most real visitors.
  • Split LCP into server response, resource load delay, load time and render delay, then fix the largest part first instead of installing another speed plugin.
  • The most common WordPress fixes are page caching, a correctly sized and preloaded hero image that is never lazy-loaded, and less render-blocking CSS and font loading.

To fix slow LCP in WordPress, find which element is your Largest Contentful Paint, work out whether the delay comes from the server, the image download or render-blocking files, and fix that part first. On most business sites the answer is page caching, a properly sized hero image that loads early, and less CSS and JavaScript in the way.

This guide walks through that process in order, with the checks I use on WordPress and WooCommerce sites for Indian businesses where most visitors arrive on mid-range phones over mobile data. If you would rather hand it over, WordPress speed optimization covers LCP, INP and CLS together.

What counts as a good LCP

Largest Contentful Paint is one of the three Core Web Vitals. It records the moment the largest image, video poster or text block in the visible part of the screen finishes rendering. Google groups the result like this:

LCP timeRatingWhat it usually means
2.5 seconds or lessGoodThe main content appears quickly for most visitors
2.5 to 4 secondsNeeds improvementOne or two bottlenecks, often the hero image or server
Over 4 secondsPoorSeveral problems stacked together, common on builder-heavy pages

The rating that matters is the 75th percentile of real visits, shown as field data in PageSpeed Insights and the Core Web Vitals report in Search Console. Lab scores from a single test are useful for diagnosis but swing from run to run, so do not chase a perfect lab number.

Step 1: Identify your LCP element

You cannot fix LCP until you know what it is. Run the page through PageSpeed Insights and open the diagnostic for the Largest Contentful Paint element; it names the exact image or text block. In Chrome DevTools, the Performance panel shows the same thing with a timing marker.

Typical LCP elements on WordPress sites are:

  • A hero image or slider image at the top of the home page.
  • A background image set through a page builder section.
  • The main product image on a WooCommerce product page.
  • The H1 heading or first paragraph on blog posts with no featured image.

Check mobile and desktop separately. The LCP element is often different on each, because a desktop layout may show a wide banner while the phone layout shows the heading first. The tools that report these numbers are compared in website speed test tools explained.

Step 2: Work out which part is slow

LCP is not one delay but four in a row. PageSpeed Insights breaks it into these phases, and the biggest phase tells you where to work:

PhaseWhat it coversTypical WordPress cause
Time to first byteThe server building and sending the HTMLNo page cache, slow hosting, heavy plugins, far-away server
Resource load delayTime before the browser starts fetching the LCP imageImage set in CSS, lazy-loaded hero, image discovered late by JavaScript
Resource load durationDownloading the image itselfOversized file, wrong format, no CDN
Element render delayTime from download to the element appearingRender-blocking CSS, JavaScript, web fonts, sliders waiting to initialise

A text LCP element has no image phases, so for blog posts the work is almost always server response and render-blocking files.

Fix slow server response

If time to first byte takes a big share of LCP, nothing else will help much until it is fixed. Start with these:

  • Page caching. Serve ready-made HTML instead of rebuilding each page with PHP and database queries. WordPress caching explained covers page, object and browser caching.
  • Server location. For an Indian audience, a data centre in or near India usually responds faster than one in the US or Europe.
  • Plugin weight. Plugins that run on every page load, such as related-post engines, visitor counters and some security scanners, slow the first byte.
  • PHP version and database. An old PHP version and a bloated options table both add time.

The full process is in how to reduce server response time (TTFB). On a busy WooCommerce store, remember that cart, checkout and account pages cannot be fully cached, so hosting quality matters more there.

Fix the hero image

When the LCP element is an image, most of the gain comes from making the browser find it early and download less.

  1. Never lazy-load the LCP image. Lazy loading is for images further down the page. WordPress skips lazy loading for the first content image in many cases, but themes, builders and optimisation plugins can add it back. See lazy loading explained.
  2. Use a real image tag, not a CSS background. Background images set in a builder section are only found after the CSS loads. A normal image element is discovered as soon as the HTML arrives.
  3. Add a high fetch priority. The fetchpriority attribute set to high on the hero image, or a preload hint in the page head, tells the browser to fetch it first.
  4. Size it for the screen. A 2,500 pixel wide photo shown at phone width wastes data. Use responsive image sizes so phones get a smaller file.
  5. Use a modern format. WebP or AVIF usually gives a much smaller file than JPEG or PNG at similar quality.
  6. Drop the slider. Sliders load several images and a script before the first slide appears. A single strong image almost always paints faster.

The image steps are covered in detail in image optimization for WordPress.

Remove render-blocking CSS, JavaScript and fonts

If the image arrives in time but still appears late, files in the page head are blocking rendering. Typical culprits on WordPress sites are a full page builder stylesheet, icon font libraries, several Google Font families and scripts loaded in the head without defer.

  • Defer non-essential JavaScript, and delay chat widgets, pixels and heatmaps until after the page has loaded.
  • Inline a small amount of critical CSS for the top of the page and load the rest without blocking.
  • Remove CSS and scripts for plugins that only one page uses.
  • Limit fonts to one or two families and the weights you actually use, host them locally and use a font-display setting that shows text immediately.

Test after every change, because over-aggressive deferring can break menus, forms or checkout. The detail is in how to eliminate render-blocking resources.

When the LCP element is a text heading, the font is often what holds it back. Here is how to reduce font load on WordPress.

Confirm the fix worked

Re-run lab tests after each change to see whether the slow phase has shrunk. Then wait for field data: PageSpeed Insights field data and the Search Console report use a rolling 28-day window, so improvements take a few weeks to show fully. In Search Console you can click Validate fix on the LCP issue once you have deployed the changes.

Keep a short record of what you changed and when. If LCP gets worse again later, it is usually because someone added a new slider, a large uncompressed image or another tracking script.

FAQs

How do I fix slow LCP in WordPress?

Identify the LCP element in PageSpeed Insights, check which of the four phases is longest, then fix that part: page caching for server delay, a preloaded and correctly sized hero image for image delays, and deferred CSS, scripts and fonts for render delay.

What is a good LCP score?

Google treats 2.5 seconds or less as good, 2.5 to 4 seconds as needing improvement and over 4 seconds as poor, measured at the 75th percentile of real visits.

Why is my LCP worse on mobile than desktop?

Phones have slower processors and often slower connections, and the mobile layout may use a different LCP element. Large images, sliders and heavy scripts hurt phones far more than desktops.

Should the LCP image be lazy loaded?

No. Lazy loading delays the image until the browser decides it is needed, which slows LCP. Load the hero image eagerly and lazy-load only images below the fold.

Will a caching plugin alone fix LCP?

Caching fixes the server part, which often helps a lot, but it will not shrink an oversized hero image or remove render-blocking files. Most sites need caching plus image and CSS work.
