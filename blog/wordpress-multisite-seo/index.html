WordPress Multisite SEO: Sitemaps, Search Console, Canonicals and Hreflang

WordPress Multisite SEO explained: subdomains vs subdirectories, SEO plugins, sitemaps per site, Search Console, duplicate risks and hreflang across sites.

Key takeaways
  • Google treats each site in a network as a separate site, so every one needs its own SEO settings, sitemap and Search Console checks.
  • On a subdirectory network only the root robots.txt is read, so list or submit every site's sitemap and check each site's search engine visibility setting.
  • Avoid copied pages across sites, redirect old addresses after domain mapping, and use hreflang only when sites are true language versions of each other.

WordPress Multisite runs a network of sites from one installation. That is convenient for the team managing it, but Google doesn't see a network: it sees separate sites, each needing its own titles, sitemaps, indexing checks and clear signals about which pages are the originals. Most multi-site WordPress SEO problems come from forgetting that. If you're still deciding whether you need a network at all, start with when a business actually needs WordPress Multisite.

Subdomain vs subdirectory multisite for SEO

When a network is set up, you choose how sites are addressed: subdomains (delhi.example.com) or subdirectories (example.com/delhi/). Any site can also be given its own domain later through domain mapping, which is built into WordPress.

Google has said publicly that it can crawl and rank both structures, so neither is a ranking trick. The practical differences matter more:

SubdirectoriesSubdomains
How it looksOne site with sectionsSeparate sites under one brand
robots.txtOne shared file at the domain rootOne per subdomain
Search ConsoleOne property, plus optional per-folder propertiesA Domain property, or one property per subdomain
Best suited toBranches or departments of one organisationSites that are genuinely separate in content or audience

Choose before launch. Switching a live network from one structure to the other changes every URL, needs a full set of 301 redirects and is a project in itself. Subdirectory networks also usually add /blog/ to the main site's post URLs by default, to avoid clashes with site names, so check your permalinks before you publish.

SEO plugins on multisite

Popular SEO plugins such as Yoast SEO and Rank Math state Multisite support, but the details differ and change between versions, so check the current documentation before you commit. Points to understand:

  • Network activation switches a plugin on for every site at once, and individual site admins can't turn it off. Activating per site gives more control but more to keep track of.
  • Settings are mostly per site. Titles, meta descriptions, schema details, social images and the sitemap all need configuring on each site, even when the plugin is network-activated.
  • Network-level options in some plugins let a super admin set defaults for new sites or lock certain settings.
  • Use one SEO plugin across the network where you can. Two plugins outputting titles, canonicals or schema on the same site cause duplicate tags.

Also check each site's Settings → Reading → Search engine visibility box. Every site in a network has its own, and a site created for testing and later launched with the box still ticked will keep asking search engines not to index it.

Sitemaps per site

Each site in a network has its own sitemap, whether it comes from WordPress's built-in sitemap (/wp-sitemap.xml) or from your SEO plugin. On a subdirectory network that means addresses like example.com/sitemap_index.xml for the main site and example.com/delhi/sitemap_index.xml for a branch site. The exact file name depends on the plugin.

Search engines only read robots.txt at the root of a host. On a subdirectory network, example.com/delhi/robots.txt is ignored, so list every site's sitemap in the root robots.txt or submit each one in Search Console, and repeat the check whenever a new site is added. Subdomain and mapped-domain sites each serve their own robots.txt and sitemap. See XML sitemaps explained for what a healthy sitemap contains.

Search Console properties

A Domain property, verified with a DNS record, covers every subdomain and protocol of example.com, so it's the simplest starting point for a network. It shows the whole network's data together, though, which makes it hard to see how one branch site is doing.

  • Subdirectory sites: add a URL-prefix property for each site, such as https://example.com/delhi/, to get its own performance and indexing reports.
  • Subdomain sites: add a URL-prefix property per subdomain, or filter the Domain property's reports by page.
  • Mapped domains: each separate domain needs its own property.

Submit each sitemap in the property that covers it.

Canonical and duplicate risks across sites

Networks make copying easy, which is where most duplicate problems start:

  • Shared service or product pages copied to every branch site with only the city name changed
  • Content pushed to many sites by a syndication or duplication plugin
  • Template sites cloned with sample content or placeholder pages still published
  • Old addresses still live after domain mapping, so a site answers on both its subdomain and its new domain
  • Test or staging sites inside the network that were never hidden from search engines

The best fix is unique, useful content on each site: local contact details, team, reviews, photos and the services that branch really offers. Where the same article genuinely must appear on two sites, add a cross-domain canonical tag on the copy pointing to the original, remembering that Google treats it as a hint rather than an order. Old addresses should 301 redirect to the current one. See canonical tags explained for how canonicals, redirects and noindex differ.

Hreflang when sites are language versions

Some networks run one site per language, for example example.com/en/ and example.com/hi/. Google then needs hreflang tags that link each page to its translations, with return tags in both directions and an x-default where it fits.

WordPress core doesn't know that a page on one site is a translation of a page on another, so a network needs a plugin built to connect them (MultilingualPress is one designed for Multisite; check its current features) or custom code. Make sure the setup outputs hreflang, keeps the links updated when pages are added or removed, and works with your SEO plugin's sitemaps. For most businesses starting fresh, a multilingual plugin on a single site is simpler. Hreflang and multilingual SEO for Indian websites covers language codes and common errors.

When separate installs are better

Multisite doesn't help or hurt rankings by itself. It's an admin convenience, and it becomes a liability when the sites stop sharing much. Separate WordPress installs are usually better when:

  • Sites need different plugins, themes or hosting
  • One site has far more traffic or content than the rest
  • Sites belong to different businesses or clients who may move away later
  • Different teams want their own SEO plugins, staging sites and release schedules
  • A plugin you rely on doesn't support Multisite

Moving a site out of a network later is possible, but it means exporting content, users and media, re-creating settings, and redirecting URLs if they change.
