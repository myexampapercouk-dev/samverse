WordPress Multisite SEO: Sitemaps, Search Console, Canonicals and Hreflang for Multi Site WordPress

WordPress multisite SEO explained: subdomains vs subfolders, per-site plugin settings, sitemaps, Search Console, duplicate content, hreflang and speed.

Key takeaways
  • Google treats each site in a WordPress multisite network as its own website, so each needs its own sitemap, Search Console property, titles and unique content.
  • Audit SEO plugin settings site by site, because one subsite set to noindex or with a wrong canonical can quietly drop out of search.
  • Duplicate content across sites, wrong hreflang and a slow shared server are the main multisite-specific SEO risks.

WordPress multisite SEO works much like SEO for separate sites, because Google treats each site in the network as its own website. Each one needs its own sitemap, Search Console property, titles, internal links and unique content, and settings must be checked site by site rather than once for the network. The main extra risks are duplicate content across sites, plugin settings that differ between sites, and shared performance problems.

This guide covers the choices and settings that matter for multisite networks run by Indian businesses, such as franchise groups, school chains, multi-brand companies and sites with Hindi and English versions. If you are still deciding whether multisite is right at all, read when you actually need WordPress multisite first.

Subdomain vs subdirectory multisite for SEO

Multisite can run sites as subdomains (pune.example.com) or subdirectories (example.com/pune/), and the choice is made at setup. Both can rank well. The practical differences:

FactorSubdirectoriesSubdomains
How users see itPart of one siteRelated but separate site
Search ConsoleCan be covered by one domain property, or added separately as URL-prefix propertiesCovered by a domain property, or added separately
Best forLanguage versions, branches of one brandDistinct brands, departments or very different audiences
Changing laterHard: needs a migration and redirectsHard: needs a migration and redirects
Mapped custom domainsPossible with domain mappingPossible with domain mapping

Google has said both structures are fine. Choose based on how closely related the sites are, and avoid switching later, because that changes every URL in the network.

WordPress multisite SEO plugin settings

Popular SEO plugins support multisite, but they behave differently. Some let you set network-wide defaults that each site can override; others are configured site by site. After activating an SEO plugin network-wide, check each site for:

  • Title and meta description templates.
  • Whether the site is set to discourage search engines (often left on from staging).
  • Noindex settings for archives, tags and attachment pages.
  • Schema settings such as organisation name, logo and local business details.
  • Breadcrumbs and social sharing images.

A common problem is one site in the network being accidentally noindexed for months because its "Search engine visibility" setting was never changed after launch. Check each site individually. The SEO plugins comparison covers plugin differences.

Sitemaps per site

Each site in the network generates its own XML sitemap through WordPress core or the SEO plugin. Submit each sitemap in Search Console separately, and reference each in that site's robots.txt. Check that sitemaps only include URLs from their own site and do not include noindexed pages, redirects or staging addresses. If you use mapped domains, make sure sitemap URLs use the final mapped domain, not the internal network address. The XML sitemaps guide explains what a clean sitemap should contain, and fixing "sitemap couldn't fetch" helps when submission fails.

Each site in a network serves its own rules file. Read about robots.txt in WordPress to make sure no subsite is blocked by mistake.

Search Console properties

A domain property in Search Console covers every subdomain and protocol, which suits subdomain networks if you want one overview. Still add each site as its own URL-prefix property too, so you can see indexing, performance and errors per site. For subdirectory networks, URL-prefix properties for each site (such as https://example.com/hindi/) give a separate view of each section. Give access only to the people who manage each site. The guide to Search Console reports explains what to watch.

Canonical and duplicate risks across sites

Networks often reuse content: the same service descriptions for each franchise branch, the same product pages on several brand sites, or blog posts copied across. Google will usually pick one version to show and ignore the others, which may not be the one you want.

  • Write unique content for each site wherever possible, especially home pages and main service pages. For branch sites, include local details: address, team, local projects, timings and directions.
  • Use canonical tags when the same article must appear on two sites, pointing to the main version. Cross-domain canonicals are a hint, not a command, so unique content is still better.
  • Avoid duplicate location pages with only the city name changed; they rarely help and can look like doorway pages.
  • Check internal links so each site links to its own pages and links across the network only where it helps users.

Hreflang when sites are language versions

If your network has language versions, such as English and Hindi, or country versions, such as India and UAE, hreflang tags tell Google which page to show to which audience. Each page must list every version including itself, and the tags must be reciprocal. Multilingual plugins that support multisite can manage this, but test a few pages by viewing the source. The hreflang and multilingual SEO guide for India covers the details, and Hindi and English WordPress websites compares multisite with single-site language plugins.

Do not use hreflang for sites that are simply different branches in the same language; that is not what it is for.

Common multisite setups in India and their SEO needs

Different kinds of networks have different priorities:

  • School or coaching chains: each campus site needs its own address, admissions contact, facilities, results notices and events. The main site should carry shared content such as the curriculum and link to each campus, so campus pages are not copies of each other.
  • Franchise and multi-branch service businesses: each branch site should target its own city or area with local details, its own Google Business Profile link and its own reviews. Head office pages should not compete with branch pages for the same local searches.
  • Multi-brand manufacturers: each brand site targets different products and buyers, so overlap is usually small. The main risk is shared product descriptions; rewrite them for each brand.
  • Hindi and English, or regional language sites: these need hreflang, translated (not machine-dumped) content and language-appropriate titles and descriptions.

In each case, decide which site should rank for which searches before writing content. A simple sheet listing the main search phrases and the site and page meant to rank for each one prevents network sites from competing with each other, which is one of the quieter ways multisite networks lose traffic.

Performance and security affect every site

Every site in a multisite network shares the same WordPress installation, plugins and database. A slow plugin, a heavy theme or an overloaded server affects all of them, and a security problem on one site can put the whole network at risk. For SEO this matters because slow pages and hacked spam pages hurt rankings across the network. Keep plugins lean, use caching that supports multisite, choose hosting with enough resources for the whole network and run updates carefully on staging first. If the network has become slow, the guide on fixing a slow WordPress multisite walks through the usual causes.

When separate installs are better

Multisite makes sense when sites share code, users and design, and when one team manages them all. Separate installs are often better when:

  • Sites have different owners, such as franchisees who want control.
  • Sites need very different plugins, for example one runs WooCommerce and another is a simple brochure.
  • One site may be sold or moved separately later.
  • One site gets far more traffic and needs its own hosting.

Splitting a site out of a network later is possible but needs careful migration and redirects, so think about this early.

Multi site WordPress SEO: audit every site's settings

The most common multi site WordPress SEO problem I see is not strategy but drift: one site in the network was left with search engines discouraged after launch, another has an old SEO plugin configuration, a third points its canonical tags at the main site. Network admins rarely open every site's settings, so check them in a table like this:

SettingWhere to check itWhat correct looks like
Search engine visibilityEach site: Settings > Reading"Discourage search engines" unticked on every live site
SEO plugin activationNetwork Admin > Plugins, then each siteSame plugin on every site, configured per site
Titles and meta descriptionsSEO plugin templates on each siteSite name and wording specific to that site
XML sitemapEach site's own sitemap URLLists only that site's indexable URLs
Canonical tagsView source on a few pages per siteSelf-referencing, unless content is deliberately shared
robots.txtEach site's domain or subdomain /robots.txtNo leftover Disallow: / and the right sitemap line
Search ConsoleOne property per siteSitemap submitted, no spike in excluded pages

On a large network, WP-CLI saves opening every dashboard. This lists each site with its visibility setting, where 1 means search engines are allowed and 0 means discouraged:

for url in $(wp site list --field=url); do
  echo "$url"
  wp option get blog_public --url="$url"
done

Any site returning 0 that should be live needs fixing in Settings > Reading. Run it after launching a new site in the network and after migrations, because staging copies are usually set to 0.

A multisite SEO checklist

  1. Each site indexable, with search engine visibility checked.
  2. Unique titles, descriptions and main content per site.
  3. One sitemap per site, submitted in Search Console.
  4. A Search Console property per site, plus a domain property if useful.
  5. Canonicals set correctly, with no cross-site duplicates by accident.
  6. Hreflang only where there are true language or country versions.
  7. Fast, secure, shared hosting and plugins tested on staging.

Is your multisite network hurting rankings? Signs to check

Multisite rarely causes ranking problems on its own, but a few symptoms point to a network-level issue rather than a content one:

  • A subsite shows few or no pages in Search Console's indexing report, often because "discourage search engines" was left on after launch.
  • Several subsites rank for the same query in turn, which suggests near-duplicate pages competing with each other.
  • Google picks a canonical on another subsite instead of the page you wanted.
  • Crawl stats show slow response times across every site at once, which usually points to shared hosting or database load.
  • Sitemaps for one subsite list URLs from another, a sign of a misconfigured domain mapping or plugin.

Fix these per site, then request indexing for the key pages. If speed is the issue, the steps in why WordPress multisite gets slow apply to the whole network.

Franchise and branch networks deserve one more check: if each branch site uses the same service text with only the city name changed, Google may treat them as near-duplicates and show only one. Give each branch its own team, photos, reviews, services and local details, or merge thin branches into location pages on the main site.

FAQs

How do I do multi site WordPress SEO?

Treat each site as its own website: configure the SEO plugin, sitemap, Search Console property and content per site, then audit every site's settings regularly, because network-level changes and new sites often leave one site misconfigured.

Is WordPress multisite bad for SEO?

No. Google treats each site in the network as its own site. SEO problems come from duplicate content, misconfigured plugins, accidental noindex settings or a slow shared setup, not from multisite itself.

Subdomain or subdirectory: which is better for WordPress multisite SEO?

Both can rank. Subdirectories suit language versions or branches of one brand; subdomains suit distinct brands or audiences. Pick at setup and avoid changing later.

Do I need a separate sitemap for each site in a multisite network?

Yes. Each site produces its own sitemap; submit each one in Search Console and check it only lists that site's indexable URLs.

How do I avoid duplicate content across multisite sites?

Write unique content for each site, add genuine local or brand details, and use canonical tags when the same content must appear on more than one site.

If you run a multisite network and want its SEO checked or cleaned up, I handle this through WordPress SEO services, and you can hire a WordPress developer in India for setup, migration or splitting sites out.

Does WordPress multisite slow down SEO?

Only if the network is slow or misconfigured. A shared server under strain slows every subsite, which can affect crawling and Core Web Vitals. Size hosting for the whole network, add object caching, and check each site's response time.
