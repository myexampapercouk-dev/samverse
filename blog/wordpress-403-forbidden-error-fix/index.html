403 Forbidden on WordPress or wp-admin: Causes and a Safe Fix Order

Seeing "403 Forbidden" on your WordPress site or wp-admin? Find out who is blocking you: permissions, .htaccess, a security plugin, firewall, your CDN or host.

Key takeaways
  • Work out who is refusing before changing anything: the look of the error page, and whether it also happens on mobile data, point to the server, a security plugin, the host's firewall or a CDN.
  • Test .htaccess by renaming it and re-saving permalinks, keep folders at 755 and files at 644, make sure index.php exists and never use 777.
  • A 403 only when saving or submitting usually means a firewall rule such as ModSecurity; ask the host to allowlist that rule and send them the URL, time, your IP and a screenshot.

A "403 Forbidden" page means the server understood your request and refused it. Nothing is necessarily broken or deleted. Something between the visitor and WordPress has decided the request isn't allowed: a file permission, an .htaccess rule, a security plugin, the host's firewall or your CDN. So first work out who is refusing, rather than changing settings at random.

What the 403 page tells you

The look of the error page is your first clue, so take a screenshot before changing anything.

What you seeWho is probably blocking
A plain white page: "Forbidden. You don't have permission to access this resource"The web server itself: permissions, .htaccess rules, a missing index file or a server firewall
A page branded by your security plugin, or a message such as "Access denied" or "Your IP has been blocked"A WordPress security plugin
A page branded by your CDN, such as "Sorry, you have been blocked" with a reference IDA CDN or cloud firewall rule
A host-branded page mentioning security, a firewall or ModSecurityThe host's web application firewall

Then note where it happens: the whole site, only wp-admin and the login page, only when saving or submitting, or only on images. Each points somewhere different.

First checks: is it you, or everyone?

  1. Open the address on your phone using mobile data, not office Wi-Fi. If it works there, your IP address has probably been blocked, not the site
  2. Try a private window to rule out old cookies and browser extensions
  3. Think about what changed: a new security plugin, a migration, an .htaccess edit, a CDN setting or a permissions "fix" from a tutorial

Before editing anything, take a backup, including a copy of .htaccess.

Security plugins and IP blocks

Security plugins block IP addresses after repeated failed logins or patterns that look like attacks. Because many connections share or rotate IP addresses, you can inherit someone else's block, or one person's wrong passwords can lock out a whole office.

  • Most lockouts expire on their own after the time set in the plugin
  • If you can log in from another network, allowlist your office IP and check the plugin's block log for the reason
  • If you can't log in at all, renaming the plugin's folder in wp-content/plugins deactivates it; the login troubleshooting guide covers this step by step

Hosts also run server firewalls that can block an IP after repeated failed logins to email, FTP or the control panel, often triggered by an old email password saved on someone's phone. Only the host can lift that kind of block.

Bad or overly strict .htaccess rules

On Apache and LiteSpeed servers, .htaccess files can allow or deny access by IP address, folder or file type. Common causes of a 403:

  • A rule limiting wp-admin to one IP address, which stops working when your provider gives you a new one
  • "Deny from all" or "Require all denied" lines placed in the wrong folder by a plugin or tutorial
  • Extra .htaccess files in wp-admin, wp-includes or wp-content/uploads. Blocking PHP in uploads is good; blocking every file there breaks your images
  • Rules injected by malware

To test, rename the main .htaccess to .htaccess-old and reload. If the 403 disappears, re-save Settings → Permalinks to generate a fresh WordPress section, then copy back only the rules you still need. The standard rules are shown in the guide to pages showing 404. If an .htaccess edit produces a 500 error instead, see fixing a 500 Internal Server Error. Nginx servers ignore .htaccess, so there your host needs to check the server configuration.

File and folder permissions

The server won't serve files it isn't allowed to read. Wrong permissions or ownership are common after a migration, a manual upload or a malware clean-up.

  • Folders are usually 755 and files 644, with wp-config.php stricter; follow your host's recommendations
  • Check the main site folder itself. If it can't be read, the whole site returns 403
  • Make sure index.php exists in the main folder. With no index file and directory listing switched off, which is the safe default, the homepage returns 403
  • Never use 777. It's a security risk, and some servers refuse to run files with permissions that open

Many hosting panels can reset permissions in one go, while ownership problems need the host. See WordPress file permissions explained. Some hosts also lock files they've flagged as infected, which shows up as a 403; their notification email usually says so.

Firewalls, ModSecurity and saving content

If the site loads but you get a 403 when you click Update, save an Elementor page or submit a form, a web application firewall has probably mistaken your content for an attack. Host firewalls such as ModSecurity inspect each request, and code snippets, script tags or certain phrases in a post can match one of their rules.

  • Note the exact time, page and action, and ask your host to check the firewall log for that request
  • Ask them to allowlist that specific rule for that address, rather than switching ModSecurity off for the whole site
  • If your panel lets you turn ModSecurity off, do so only as a brief test

Security plugin firewalls can do the same, as can blocks on the WordPress REST API, which the block editor needs in order to save. For how the layers fit together, see WordPress firewalls explained.

CDN rules and hotlink protection

If you use a CDN or cloud firewall, search its security events log for the reference ID shown on the block page. Look for:

  • Country blocks or challenges that catch real customers, including travellers and VPN users
  • Rules that only allow certain IP addresses into wp-admin or wp-login.php
  • Bot protection or rate limiting tight enough to block payment gateway callbacks or your uptime monitor

Hotlink protection stops other websites displaying your images, but set up badly it blocks your own. If images return a 403 after a domain change, a move to https or adding www, check that every version of your domain is on the allowed list.

When to ask your host

Contact support if the 403 covers the whole site while .htaccess and permissions look right, if it only happens when saving or submitting, if your IP is blocked at server level, if the server runs Nginx or if file ownership needs fixing. Send the exact URL, the date and time, your public IP address (search "what is my IP"), a screenshot of the error page and what you've already tried, so they can find the matching log entry quickly.
