WooCommerce Checkout Not Working? Fixing Endless Spinners, Errors and a Dead "Place Order" Button

Fix a WooCommerce checkout that won't load, spins forever or ignores "Place order": caching, script conflicts, block checkout, gateways, SSL and sessions.

Key takeaways
  • Start with the browser's Console and Network tabs: a 403, 500 or 504 on the checkout request, or a response full of PHP warnings, points straight at the cause.
  • Keep cart, checkout and account pages out of every cache layer and out of JavaScript delay or combine features, because stale pages carry expired nonces and lost sessions.
  • Find conflicts on staging with a default theme and only WooCommerce plus your gateway active, check block checkout support for every checkout plugin, and finish with a real low-value order.

A broken checkout is one of the costliest faults a store can have, because the shoppers who reach it have already decided to buy. The checkout page won't load, a spinner never stops, the "Place order" button does nothing, or the shopper sees "There was an error processing your order". Here are the usual causes in a sensible order. WooCommerce changes quickly, so menu names may differ slightly on your version.

First, see what the browser is telling you

Open the checkout in a private window, add a product and press F12 to open the developer tools. Two tabs matter:

  • Console: red errors mean a script failed. One broken script anywhere on the page can stop the checkout's own scripts.
  • Network: click "Place order" and watch the requests. The classic checkout sends requests containing wc-ajax; the block checkout uses the Store API, with wc/store in the address. Click a failing request to see its status and response.
What you seeLikely cause
403 on checkout requestsA firewall, security plugin or CDN rule blocking them
500 errorA PHP error in a plugin or theme; check the logs
502 or 504The server timed out, often waiting on a gateway or shipping service
A response full of HTML or PHP warningsSomething printed output where the checkout expected clean data
No request at allA JavaScript error, or the button is covered or blocked

"There was an error processing your order" is a general message. It often means the server sent back something the checkout couldn't read, such as a PHP warning or fatal error. Check WooCommerce → Status → Logs, where fatal errors can be recorded, and your hosting error log at the time of your test.

Cart and checkout pages must not be cached

Cart, checkout and My Account pages are personal to each shopper, so they must never come from a page cache. WooCommerce tells caching plugins to skip them, and most do, but server caches, CDN "cache everything" rules and some optimisation plugins can still serve a stored copy. The result: an empty cart, "Sorry, your session has expired", or a spinner that never finishes because the page carries an expired security token.

Exclude these pages in every cache layer, including your host's cache and any CDN, and let shoppers with items in their cart bypass cached pages. Settings that combine, defer or delay JavaScript are just as common a cause: delaying jQuery, WooCommerce's scripts or the gateway's script often breaks checkout. Exclude the checkout from them, clear every cache and test again. WordPress caching explained covers each layer.

JavaScript and plugin conflicts

The checkout relies on JavaScript, so it's often the first thing a conflict breaks. Usual suspects:

  • Checkout field editors, pin code checkers and delivery date plugins
  • Captcha or anti-spam plugins on the checkout form
  • Pop-ups, chat widgets or cookie banners covering "Place order" on a phone
  • Tracking scripts with errors of their own
  • Outdated WooCommerce template copies in your theme; WooCommerce → Status flags these
  • Dull ones: a required field hidden by CSS, or an error shown above where the shopper has scrolled

To find the culprit, use a staging copy: switch to a default theme such as Storefront, deactivate everything except WooCommerce and your gateway, then reactivate plugins one at a time. The Health Check & Troubleshooting plugin can do this for your login session only. See how to find and fix plugin conflicts.

Block checkout or classic shortcode checkout?

Recent WooCommerce versions set up new stores with the block-based Checkout, while many older stores still use the classic [woocommerce_checkout] shortcode. WooCommerce → Settings → Advanced shows which page is your checkout; edit it to see which one it contains. A missing checkout page setting, or two pages competing for the job, is a fault in itself.

Block checkout problems to check:

  • Missing payment methods or fields: extensions built only for the classic checkout may not appear. Update them and check their block support.
  • Blocked REST API: the block checkout needs the WordPress REST API, so security settings that switch it off for visitors can stop orders.

If an essential plugin doesn't support blocks yet, going back to the classic checkout is a valid fix; recent versions offer a switch in the Checkout block's settings. Try it on staging first. The trade-offs are covered in WooCommerce checkout optimization.

Payment plugin issues

If the form submits but the payment step fails, suspect the gateway plugin: an outdated version, test keys on the live site, a store currency it doesn't support, or a payment popup blocked by the browser, an ad blocker or a strict content security policy. Turn on its debug log if it has one.

A quick staging test: temporarily enable an offline method such as Cash on Delivery. If orders go through with that but not with the gateway, the checkout is fine and the gateway plugin, its settings or its support team are your next stop. If customers pay but orders stay at "Pending payment", the cause is usually a missing webhook.

SSL, mixed content, sessions and nonces

Checkout scripts and payment forms need a clean HTTPS page. If files still load over http://, browsers block them and parts of the checkout silently fail. In Settings → General, both addresses should start with https:// and match the www or non-www form your site redirects to. Fix leftover http:// links at the source; see fixing mixed content warnings.

WooCommerce keeps each cart in a session linked to a browser cookie. Lose the cookie and the cart empties at checkout: typically a www mismatch, a cached page, a rule stripping cookies or a database problem.

Checkout forms also carry nonces, short-lived security tokens. Send an expired one from a cached or long-open page and WooCommerce rejects the order with a message such as "We were unable to process your order, please try again". Firewalls and bot protection can block the order request too, which shows as a 403; the firewall's log will name the rule.

A safe test routine

  1. Work on staging for anything beyond clearing a cache, and stop it emailing real customers.
  2. Use the gateway's test mode, logged out in a private window and on a phone over mobile data.
  3. Place a test order with each payment method while watching the Console and Network tabs.
  4. Check the result: order status, emails, stock and the gateway's order notes.
  5. Change one thing at a time, and note what you changed.
  6. Finish on the live site with a real low-value order, then refund it.

If checkout broke straight after an update, roll that update back first and investigate on staging.
