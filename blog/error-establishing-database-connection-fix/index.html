Error Establishing a Database Connection in WordPress: A Diagnosis Order That Finds the Cause, What to Tell Your Host, and How to Stop It Coming Back

Fix the WordPress database connection error in order: wp-config.php details, DB host, server load, damaged tables, migrations, and what to ask your host.

Key takeaways
  • Check causes in a fixed order: is the database server up, are the four details in wp-config.php right, do they work outside WordPress, and is the hosting account hitting limits.
  • Damaged tables and backup restores come last, and both need a fresh backup first because they change data rather than settings.
  • A short, specific message to your host and uptime monitoring with a keyword check turn a long outage into a short one.

"Error establishing a database connection" means WordPress tried to log in to its MySQL or MariaDB database and failed, so it has nothing to build the page from. Your posts, pages and orders are usually still there. The quickest route to a fix is to check causes in a fixed order: is the database server running, are the four connection details in wp-config.php correct, do those details work when tested outside WordPress, is the hosting account hitting a limit, and only then, are tables damaged or does the database need restoring.

If you would rather hand it to someone, this is exactly the kind of outage my WordPress maintenance plans are set up to catch, since uptime monitoring usually spots it before a customer rings you. If the error began straight after a move to new hosting, jump to the migration section further down, because that case has its own shorter list.

A note before you touch anything: download a copy of wp-config.php and take a database export if phpMyAdmin will open. With those two, every step below can be undone.

Two minutes of triage before you change anything

Answer four questions first.

  1. Does /wp-admin/ show the same message, or does it say "One or more database tables are unavailable"? The second message means the connection works and the problem is inside the database.
  2. Is the error constant, or does it appear and disappear when you reload?
  3. What changed in the last day or two: a migration, a password reset, a hosting renewal or plan change, a plugin update, a sudden burst of traffic?
  4. Are other websites on the same hosting account down as well?

Step 1: Is the database server running?

Log in to your hosting panel and try to open phpMyAdmin or the database manager. If it loads and you can see your WordPress tables, the server is up and you can move to Step 2. If phpMyAdmin also fails to connect, or the panel shows a maintenance banner, the problem is on the host's side. On shared hosting you cannot restart the database service yourself, so this is a support ticket, not a DIY fix. Check the host's status page too, and see the wider checks in what to do when your website is down.

Step 2: Check the four details in wp-config.php

wp-config.php sits in the main folder of your WordPress install. Open it through the hosting file manager or SFTP and find these lines (the values here are placeholders):

define( 'DB_NAME', 'account_wpdb' );
define( 'DB_USER', 'account_wpuser' );
define( 'DB_PASSWORD', 'the-password-here' );
define( 'DB_HOST', 'localhost' );

Now compare each one with the databases section of your hosting panel:

  • DB_NAME: the full name, including any account prefix the panel adds automatically. A missing prefix is a very common slip.
  • DB_USER: the user must exist and must be assigned to this database with full privileges. A user that exists but was never linked to the database will fail.
  • DB_PASSWORD: panels rarely display passwords, so reset the database user's password in the panel and paste the new one in. Keep the single quotes intact and check for a stray space at either end.
  • DB_HOST: usually localhost, but not always. See the note below.

Getting DB_HOST right

Some hosts run the database on a separate server and give you a hostname or an IP address instead of localhost. Others need a port number added after a colon, or a socket path. The correct value is in your host's documentation or the database section of the panel, so copy it from there rather than guessing. A host moving you to a new server can change it.

Never paste wp-config.php into a public forum, a group chat or a screenshot. It contains working passwords and, further down, your security keys.

Step 3: Test the details outside WordPress

If the details look right but the error stays, test them on their own. Create a file called dbtest.php in the same folder, with your own values in place of the placeholders:

<?php
$link = mysqli_connect( 'localhost', 'account_wpuser', 'the-password-here', 'account_wpdb' );
if ( ! $link ) {
  echo 'Failed: ' . mysqli_connect_error();
} else {
  echo 'Connected';
}

Open yoursite.in/dbtest.php in a browser, read the result, and delete the file straight away, because it contains your password in plain text. The message tells you which detail is wrong. Exact wording varies between server versions, but the patterns are consistent:

Step 4: Hosting limits and an overloaded server

An error that comes and goes is rarely a typo. More often the database server is refusing new connections because your account, or a noisy neighbour on the same shared server, is using too much. Typical triggers:

  • A traffic spike from a campaign, a news mention or a sale
  • Bots hammering the login page, XML-RPC or search, each request opening a database connection
  • A plugin running slow or repeated queries
  • Heavy scheduled tasks firing at the same time as real visitors

Check the resource usage section of your panel for CPU, memory or entry process limits being hit. Page caching helps a great deal, because cached pages are served without touching the database at all. If the site simply needs more than its plan offers, the comparison in shared vs VPS vs managed WordPress hosting explains what you get by moving up a tier.

Step 5: Damaged tables

Tables can be damaged by a server crash, a full disk or an update interrupted halfway. Take a database export first if you can, then use WordPress's built-in repair page. Add this line to wp-config.php, just above the line that says to stop editing:

define( 'WP_ALLOW_REPAIR', true );

Visit yoursite.in/wp-admin/maint/repair.php, choose Repair Database, and remove the line as soon as it finishes, because that page works for anyone, without a login.

A word on wp_options, the table that holds your site address and settings. When it is damaged, or swollen with old autoloaded data left behind by removed plugins, symptoms can include this error, a blank site or a very slow admin. Repair may help, but it is not guaranteed: the repair commands work best on older MyISAM tables, while InnoDB tables, which most current hosts use, usually recover through the server's own processes or a restore. If repair reports errors it cannot fix, stop there and ask your host before trying anything stronger. For keeping the table lean once the site is back, see WordPress database optimisation.

Step 6: Restore from a backup

If the database has been deleted or repair fails, restore the most recent good copy from your host's backups or your backup plugin, following the backup and restore guide. On a WooCommerce store or a booking site, anything that arrived after that backup was taken will be missing, so list recent orders, bookings and form enquiries from your emails and payment gateway dashboard before you restore, and re-enter or follow up on them afterwards.

After a migration: the separate checklist

A host move is the single most common trigger, and the causes are predictable. Work down this list:

  1. The new host created a new database, user and password. wp-config.php must use those, not the old ones.
  2. The import finished completely. Compare the number of tables with the old database; a timeout during import can leave some missing.
  3. The table prefix matches. If wp-config.php says $table_prefix = 'wp_'; but the imported tables start with something else, you will usually see the installation screen rather than this error.
  4. DNS has fully switched. Some visitors may still reach the old server, and if that hosting has already been cancelled, they see an error the rest of the world does not.
  5. DB_HOST is right for the new host, which may not use localhost.

Leave the old hosting account active for a week or two after the switch, as a fallback. A planned WordPress migration copies and tests everything on the new host before DNS is switched, which is how this error is avoided in the first place.

What to tell your host

Support teams answer faster when the first message rules things out. Something like this works well:

My WordPress site at yoursite.in has shown "Error establishing a database connection" since about 10:30 today. I have confirmed the database name, user and host in wp-config.php match the panel, and reset the user's password. A direct connection test returns "Too many connections". Could you check that the database service is running for my account, whether I am hitting a connection or resource limit, and share any database errors in the server logs from that time?

Do not send your database password in a support chat; a good host will never need it from you.

Prevention and monitoring

  • Set up uptime monitoring with a keyword check, so you are alerted if the homepage stops showing a word it should always contain; see uptime monitoring explained
  • Keep database details in a password manager, and whenever anyone resets the database password, update wp-config.php in the same sitting
  • Use page caching so ordinary visits do not hit the database
  • Block abusive bots and limit login attempts
  • Keep daily backups that include the database, stored away from the server
  • Watch renewal dates, since an expired or suspended hosting account takes the database with it

Other common messages, such as the critical error notice or a white screen, are covered in common WordPress errors and fixes.

FAQs

Have I lost my website content?

Usually not. The error means WordPress cannot reach the database, not that the database is gone. Only if the database was deleted or badly damaged do you need a backup, which is why a database export is the first thing to take when phpMyAdmin will open.

Why does the error appear and disappear?

Intermittent errors point to the server or your hosting limits rather than wrong settings. Traffic spikes, bots and slow plugin queries can exhaust the connections available to your account. Caching, bot blocking and, if needed, a bigger hosting plan are the usual fixes.

Can a plugin cause this error?

Indirectly, yes. A plugin that runs heavy or repeated queries can overload the database until new connections are refused. If the error began after a plugin update, rename that plugin's folder over SFTP to switch it off and see whether the site recovers.

Is it safe to leave WP_ALLOW_REPAIR switched on?

No. The repair page does not ask for a login, so anyone who knows the address could run it. Add the line, run the repair, and remove it straight away.

How can I tell whether it is my host's problem or my site's?

If phpMyAdmin will not connect either, or other sites on the same account are down, it is on the host's side. If phpMyAdmin works and the test script connects, the problem is in your WordPress settings or tables.

If your site is down with this error now, or you are planning a host move and want to avoid it, see WordPress maintenance and support or WordPress migration.
