Robots.txt Explained Simply: How It Works, Safe WordPress Examples and Mistakes to Avoid

Robots.txt explained simply: how crawlers read it, safe WordPress and WooCommerce examples, AI crawler rules, Search Console testing and common mistakes.

Key takeaways
  • Robots.txt controls which URLs crawlers may visit, not which pages appear in Google; to keep a page out of search results, use noindex and leave it crawlable.
  • Most WordPress sites need only a short file that blocks the admin area, allows admin-ajax.php and lists the sitemap, without blocking CSS, JavaScript or uploads.
  • Check the live file after every launch or migration, test important URLs with URL Inspection, and decide on AI crawlers deliberately rather than by accident.

Robots.txt is a small plain-text file at the root of your website that tells search engine crawlers which URLs they may and may not crawl. It controls crawling, not indexing: to keep a page out of Google you need a noindex tag on a page Google can crawl, not a robots.txt block. For most WordPress sites the right robots.txt is short, blocking only the admin area and pointing to your sitemap, and the biggest risks are rules that block too much, such as a leftover "Disallow: /" from a staging site.

Robots.txt and the XML sitemap are both part of the setup in my WordPress SEO services, because a single wrong line in this file can stop Google crawling a whole site. This guide explains how the file works, gives safe examples for WordPress and WooCommerce, covers AI crawlers and shows how to test it.

If Search Console is already showing "Indexed, though blocked by robots.txt" or "Blocked by robots.txt", see what those robots.txt statuses mean and how to fix them.

How robots.txt works

  • It lives at one address: https://example.com/robots.txt. Each host has its own, so a subdomain such as shop.example.com needs its own file, and http and https versions are treated separately (another reason to redirect everything to one version).
  • Crawlers read it before crawling. Google generally caches it for up to a day, so changes aren't picked up instantly.
  • It is a request, not a lock. Googlebot, Bingbot and other reputable crawlers follow it. Scrapers and malicious bots ignore it.
  • It is public. Anyone can read it, so listing a "secret" folder in it advertises that folder.
  • No file is fine. If robots.txt returns a 404, crawlers assume they may crawl everything. A server error is worse: Google may pause crawling until the file loads properly again.

The syntax, line by line

LineWhat it doesExample
User-agentNames the crawler the following rules apply to; * means all crawlersUser-agent: Googlebot
DisallowA path the crawler should not requestDisallow: /wp-admin/
AllowAn exception inside a disallowed pathAllow: /wp-admin/admin-ajax.php
SitemapThe full URL of your XML sitemap; can appear anywhere in the fileSitemap: https://example.com/sitemap_index.xml
#A comment, ignored by crawlers# Added at launch

A few rules that trip people up:

  • Rules match from the start of the path. "Disallow: /blog" blocks /blog/, but also /blog-tips/ and /blogging-guide/. Add the trailing slash if you mean the folder.
  • Paths are case-sensitive. /Images/ and /images/ are different.
  • Wildcards: Google and Bing support * for "any characters" and $ for "end of URL", so "Disallow: /*.pdf$" blocks URLs ending in .pdf.
  • The most specific rule wins. When an Allow and a Disallow both match, Google follows the longer rule; if they are equal, it follows the Allow.
  • Google ignores crawl-delay (Bing respects it), and Google stopped supporting noindex lines in robots.txt in 2019.

A safe robots.txt for WordPress

For a typical business site, this is all you need:

User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php

Sitemap: https://example.com/sitemap_index.xml

It keeps crawlers out of the dashboard while allowing admin-ajax.php, which some themes and plugins use to load content on the front end. Use your own sitemap address: sitemap_index.xml with Yoast or Rank Math, or wp-sitemap.xml with no SEO plugin; see XML sitemaps explained.

Resist adding more. Old advice to block /wp-includes/, /wp-content/plugins/ or /wp-content/themes/ now does harm, because Google renders pages like a browser and needs the CSS and JavaScript in those folders to see your layout. Blocking /wp-content/uploads/ hides your images from Google Images.

Virtual file or real file?

If there is no robots.txt file in your site's root folder, WordPress generates one on the fly, and SEO plugins often add their sitemap line to it. If a real robots.txt file exists, it replaces the generated one completely. To edit it, at the time of writing:

  • Yoast SEO: Yoast SEO > Tools > File editor, which can create the file if none exists.
  • Rank Math: Rank Math SEO > General Settings > Edit robots.txt. This only works when no physical file exists; if your edits don't appear on the live file, an old physical file is usually the reason.
  • Hosting file manager or FTP: upload or edit robots.txt in the same folder as wp-config.php.

Robots.txt for WooCommerce stores

Stores create endless URL variations: add-to-cart links, sorting options and every combination of filters. They are all crawlable by default, and on a new store with limited crawling attention they can soak up visits Google could spend on products. A common addition:

User-agent: *
Disallow: /wp-admin/
Allow: /wp-admin/admin-ajax.php
Disallow: /*?add-to-cart=
Disallow: /*?*orderby=
Disallow: /*?*filter_

Sitemap: https://example.com/sitemap_index.xml

Two cautions. First, adjust the filter rule to the parameters your filter plugin actually uses, and never block filtered pages you have deliberately built to rank, such as a "red sarees" category view; WooCommerce product filters and SEO explains that choice. Second, if filter URLs are already indexed, a robots.txt block stops Google seeing their canonical or noindex tags, so they can linger in results. Sort out canonicals first, then block. WooCommerce already asks search engines not to index the cart, checkout and account pages, so they don't need rules here.

Robots.txt blocks crawling, not indexing

This is the most misunderstood point. If other pages link to a URL you've blocked, Google can still index the bare URL without ever reading the page, and it can't see a noindex tag on a page it isn't allowed to crawl. Pick the tool that matches the goal:

Your goalUseWhy
Keep a page out of Google's resultsA noindex tag, with crawling allowedGoogle must crawl the page to see the noindex
Stop crawlers wasting time on endless URL variationsRobots.txtThis is what it is designed for
Keep private files or areas privateA login or password protectionRobots.txt is public and only a request
Keep a staging site out of GooglePassword protectionA blocked staging site can still be indexed from links; see staging sites explained
Remove a page already in GoogleDelete it (404 or 410) or noindex it, and leave it crawlableBlocking it freezes the old version in the index

AI crawlers and robots.txt

AI companies run their own crawlers, and robots.txt is how you opt out of the ones that respect it. User-agent names at the time of writing include GPTBot (OpenAI's training crawler), OAI-SearchBot (ChatGPT search), ClaudeBot (Anthropic), PerplexityBot, CCBot (Common Crawl) and Google-Extended, which controls whether Google may use your content for its Gemini models. Blocking Google-Extended does not remove you from Google Search, and Google treats AI Overviews as part of Search.

User-agent: GPTBot
Disallow: /

User-agent: Google-Extended
Disallow: /

Whether to block them is a business decision, not a technical one. A training crawler takes content without sending visitors; an AI search crawler is what lets assistants find and cite your pages. Many service businesses want to be cited, so they leave the search crawlers alone. AI search and your website covers the trade-off. If you use Cloudflare, check whether its AI crawler settings are adding lines to your robots.txt on your behalf, then look at the live file to see exactly what crawlers receive.

Common robots.txt mistakes

  • "Disallow: /" left over from development. The classic launch mistake, and one of the first causes to rule out in why a WordPress site isn't showing on Google.
  • Blocking theme, plugin or upload folders, which breaks how Google renders your pages and hides your images.
  • Blocking pages you want removed instead of noindexing them, which keeps them in results with no description.
  • Listing private paths, which tells everyone where they are.
  • A missing trailing slash, so a rule blocks far more URLs than intended.
  • Editing in a plugin while a physical file overrides it, so your changes never go live.
  • A wrong or old sitemap URL, such as the previous domain after a migration.

How to test your robots.txt

  1. Open the live file at https://example.com/robots.txt, and also try the www or non-www and http versions to confirm they redirect to the same place.
  2. Open the robots.txt report in Search Console, under Settings > Crawling. It shows the versions Google has fetched, when it last checked, any errors or warnings, and lets you request a recrawl after a fix. It replaced the old robots.txt Tester, which Google retired in 2023.
  3. Inspect your key URLs with the URL Inspection tool. Under the crawl details, "Crawl allowed?" should say Yes for every page you want in Google.
  4. Use Bing Webmaster Tools' robots.txt tester if you also care about Bing.
  5. Repeat after every launch, redesign or migration, as part of a wider check such as the WordPress technical SEO audit.

FAQs

What is robots.txt used for?

It tells search engine crawlers which parts of a site they shouldn't request, which helps them avoid admin areas and endless URL variations, and it tells them where your sitemap is. It isn't a security tool and it doesn't remove pages from search results.

Where is robots.txt in WordPress?

Usually nowhere on disk: WordPress generates a virtual one at /robots.txt on your domain. You can edit it through Yoast's file editor or Rank Math's robots.txt setting, or create a real file in the site's root folder, which then takes over completely.

Does robots.txt stop a page from appearing in Google?

Not reliably. A blocked page can still be indexed if other pages link to it, just without a description. Use a noindex tag on a crawlable page, or delete the page, if you want it gone from results.

Should I block AI crawlers like GPTBot?

It depends on whether you mind your content being used to train AI models, and whether you want AI assistants to cite you. Blocking training crawlers while allowing AI search crawlers is a common middle ground. Google-Extended affects only Google's AI models, not your Google Search rankings.

Do I need a robots.txt file at all?

No. Without one, crawlers assume everything is allowed, which is fine for many small sites. WordPress provides one anyway, and a short file with your sitemap line is useful.
